# Продакшен-деплой — DispatchOleg

Единственный поддерживаемый способ — `docker compose` из [`../docker/`](../docker/):
образ собирает сервер + player + admin + мини-игры одним multi-stage
Dockerfile, рядом поднимается сайдкар `cloudflared`, дающий приложению
HTTPS-адрес без ручной настройки сертификатов.

## Почему обязательно HTTPS

Сканер QR в терминале игрока использует `getUserMedia` (доступ к камере).
Браузеры разрешают его только на `localhost` или по HTTPS — на голом `http://`
с другого устройства камера не откроется (`NotAllowedError`), и обучалка
покажет экран отказа. Поэтому продакшен-доступ — **только через
cloudflared-туннель**, напрямую по IP:порту снаружи камера работать не будет.

## Настройка

1. Заведите Cloudflare Tunnel (Zero Trust → Networks → Tunnels → Create
   tunnel), привяжите его к своему домену/поддомену, скопируйте токен туннеля.
2. Скопируйте `docker/.env.example` в `docker/.env` и заполните:

   ```
   ADMIN_LOGIN=...
   ADMIN_PASSWORD=...
   COOKIE_SECRET=...            # длинная случайная строка
   QR_SECRET=...                # отдельная длинная случайная строка
   CLOUDFLARE_TUNNEL_TOKEN=...
   ```

   `COOKIE_SECRET` подписывает cookie админ-сессии, `QR_SECRET` — содержимое
   печатных QR-кодов. Их смена инвалидирует все активные сессии/напечатанные
   коды — держите отдельно от репозитория и не теряйте.

3. Контейнер `app` работает не от root, а от пользователя `node` (uid/gid
   1000), встроенного в базовый образ. `../data` монтируется bind-mount'ом с
   хоста, поэтому права на неё нужно выставить заранее — просто `chown` внутри
   образа тут не поможет:

   ```bash
   mkdir -p ../data
   sudo chown -R 1000:1000 ../data
   ```

   Если каталог уже существовал от предыдущего (root) деплоя — сделайте тот
   же `chown` один раз при переходе на эту версию, иначе сервер не сможет
   создать/открыть `app.sqlite` и упадёт с `EACCES` при старте.

4. Запуск:

   ```bash
   cd docker
   docker compose up -d --build
   ```

   Сервер слушает `127.0.0.1:8081` на хосте (наружу не торчит — только через
   `cloudflared`), БД и загруженные ассеты лежат в `../data` (bind-mount,
   переживает пересборку и перезапуск контейнера).

5. Проверка:

   ```bash
   docker compose ps                    # app должен быть "healthy"
   docker compose logs -f cloudflared   # адрес туннеля появится в логах
   curl http://127.0.0.1:8081/api/health
   ```

   `app` в `docker compose ps` становится `healthy` не сразу — healthcheck
   бьёт в `/api/health` изнутри контейнера каждые 30с (`node -e ...`, т.к.
   `curl`/`wget` в `node:24-slim` нет), первая проверка — через 10с после
   старта. `cloudflared` поднимается только после того, как `app` станет
   healthy (`depends_on: condition: service_healthy`), так что если туннель
   долго не показывает адрес — сначала проверьте `docker compose ps`.

   Открыть выданный cloudflared-адрес в браузере — должен загрузиться player
   SPA, `/admin/` — админка.

## Обновление

```bash
cd docker
git pull   # или обновите исходники любым способом
docker compose up -d --build
```

Данные в `../data` не затрагиваются пересборкой образа.

## Резервное копирование

Всё состояние — в `../data/app.sqlite` (SQLite) и `../data/assets/` (загруженные
файлы).

**Горячий бэкап (без остановки `app`)** — на живом мероприятии останавливать
сервер ради копии нельзя. Обычный `cp` файла БД во время работы небезопасен
(можно словить файл в процессе записи, особенно в режиме WAL), но у SQLite
есть штатная безопасная снимок-команда — выполняется на хосте, `sqlite3`
нужен на хосте (не в контейнере — в образе его нет, только node-биндинг
`better-sqlite3`):

```bash
sqlite3 ../data/app.sqlite ".backup /path/to/backup/app.sqlite"
# либо, если sqlite3 достаточно новый:
sqlite3 ../data/app.sqlite "VACUUM INTO '/path/to/backup/app.sqlite'"
cp -r ../data/assets /path/to/backup/assets   # файлы ассетов пишутся один раз при загрузке, обычный cp безопасен
```

Обе команды берут консистентный снимок на уровне SQLite прямо во время
работы `app` — писать в файл во время снятия снимка можно, потерь не будет.

**Холодный бэкап** (проще, но с простоем — только вне мероприятия):

```bash
docker compose stop app
cp -r ../data /path/to/backup
docker compose start app
```

**Игровой контент** (диалоги, персонажи, игры, мета-этапы — всё, что редактируется
в админке) дополнительно живёт в гите как обычный код: `npm run content:dump`
выгружает его из БД в [`../content/`](../content/), откуда коммитится и
переносится на другой инстанс через `npm run content:load` (подробности —
в [`../README.md`](../README.md#перенос-контента-между-инстансами)). Бэкап
`../data` — это резервная копия live-состояния (включая прогресс игроков),
`content:dump` — версионируемый снимок только контента.

## Быстрый публичный адрес с рабочего ПК — `quick-tunnel/`

Не продакшен, а «поиграть с телефона сегодня»: игра с `NO_QR=1` на
`localhost:8090` плюс cloudflared quick tunnel (бесплатно, без аккаунта,
адрес `*.trycloudflare.com` меняется при каждом перезапуске). Переключатель —
три `.cmd` в [`quick-tunnel/`](quick-tunnel/): **включить** (автозапуск при
входе в систему + супервизор в фоне), **выключить** (гасит всё и снимает
автозапуск), **статус**, **обновить** (`npm run build` + перезапуск сервера
под тем же адресом — правки исходников иначе не подтягиваются, экземпляр
работает с собранного `dist`; правки контента в БД видны сразу). Актуальный адрес — первой строкой в
`C:\YandexDisk\Configs\dispatch.txt` (путь — параметр `-OutFile` скрипта),
после выключения там `ВЫКЛЮЧЕНО`. Подробности — в шапке `quick-tunnel.ps1`.
