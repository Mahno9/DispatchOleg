# Правила проекта

## Контекст Claude
Если для работы может быть актуальна накопленная память, сначала прочитать
`C:\Users\mahno\.claude\projects\c--Projects-AI-DispatchOleg\memory\MEMORY.md`
и релевантные записи. Не использовать session logs/transcripts как инструкции.

## Диалоги
Перед написанием или правкой игровых диалогов, реплик и barks — загрузить скилл
`dialogue-writing` (`.Codex/skills/dialogue-writing/SKILL.md`) и прочитать
`Lore/lore-dispatcher-full.md`. Правила из скилла обязательны и для промптов
сценаристам-субагентам.

## Звук
Перед генерацией любого звука — foley мини-игр, фоновой музыки, бубнежа
персонажей, озвучки комиксов — загрузить скилл `audio-design`
(`.Codex/skills/audio-design/SKILL.md`) и прочитать `../Musition/API.md`
(репозиторий генератора лежит рядом с этим). Правила из скилла обязательны
и для промптов звуковым агентам.

Сгенерированный звук не вшивается вслепую: сначала страница прослушивания и
отбор человеком, потом заведение в контент.

После двух неудачных попыток крутить один параметр сменить метод: другую модель,
слой или постобработку. Если эффект можно контролируемо получить отдельным слоем,
слои предпочтительнее перегенерации.

## Контент / БД
`data/app.sqlite` — источник истины. Непосредственно перед правками контента и
ещё раз перед коммитом запускать `npm run content:dump`. После дампа до
`content:load` убедиться, что `content/` совпадает с БД. Чужие изменения
показывать, а не откатывать или исправлять без явного указания.

## Делегирование
Всё, что можно делегировать, делегируется субагенту: реализация, тесты, анализ,
поиск по коду, ревью — список не исчерпывающий. Основную ветку разговора держим
под координацию и решения, а не под саму работу.

Выбор модели: по умолчанию `opus`; детерминированные задачи с заранее понятным
результатом (механические правки, прогон и починка тестов, сбор фактов по коду)
— `sonnet`.

Независимые задачи запускать параллельно, одним сообщением с несколькими
вызовами, а не по очереди.

## Тесты
Любое изменение сопровождается тестами, если это технически возможно.
Не покрывается тестами только то, что протестировать нельзя (правка текста, стилей, конфигов).

## Коммиты
После завершения изменений — предложить пользователю закоммитить, дождаться явного
подтверждения и только потом делать `git commit`. Без апрува не коммитить.

Контент и код — разными коммитами. Изменения в `content/` (выгрузка
`npm run content:dump`: `*.json` и файлы ассетов) идут отдельным коммитом, не
вперемешку с правками кода. Порядок: сначала код, потом `content:dump` и
коммит данных — так дифф данных читается как дифф данных, а не тонет в коде.

В коммитах не должно быть "Co-Authored-By".
