# Мини-игра 06: cooking-orders (готовка для персонажей)

Игрок работает за кухонным терминалом диспетчерской: к окну выдачи выстраивается очередь супергероев,
каждый со своим заказом. Игрок читает рецепт, по шагам добавляет ингредиенты (часть — дозируемые,
с удержанием), затем варит блюдо в котле, удерживая нужное время по кольцевой шкале. Ошибка — блюдо
портится, заказ начинается заново. Три ошибки — «ВСЁ СГОРЕЛО» и вся смена с начала.

- **id мини-игры:** `cooking-orders`
- **Технология:** чистый DOM + CSS (**canvas не нужен**), SVG только для кольцевой шкалы варки.
- **Оценка трудоёмкости:** ~2.5–3 дня.
- **Контракт:** базовый `minigame_contract.md` + расширения платформы (`docs/platform.md` §3):
  `onProgress(text, percent?)` для прогресса по заказам, `onComplete({score, won, details})` со статистикой.
- **Стиль:** `STYLE.md` — карточки-досье для персонажей (портрет, имя, статусная полоса), угловатые
  панели, палитра терминала, янтарный/оранжевый — для активных и тревожных состояний.

Структура директории в репозитории:

```
minigames/cooking-orders/
  schema.json          # конфигурация для админки (SchemaForm)
  vite.config.ts       # сборка модуля
  src/
    engine.ts          # чистая машина состояний заказа, без DOM
    engine.test.ts     # vitest на FSM
    index.ts           # DOM-рендер, pointer-события, rAF, вызовы колбэков
```

## 1. Геймплей и состояния

### 1.1 Layout рабочей области

Вся рабочая область экрана `minigame` (контейнер из `init(container, …)`) делится на четыре зоны.
Нижняя панель терминала (камера / контекстный слот / кнопка) — не часть контейнера, игра её не трогает.

```
┌──────────────────────────────────────────────────────────────────────┐
│  ОЧЕРЕДЬ                                                             │
│  ┌────────┐ ┌────────┐ ┌────────┐          ОШИБКИ: ● ● ○   [ 🔇 ]    │
│  │ ВЕРА   │ │ МАКС   │ │ К-9    │                                    │
│  │ ▓ACTIVE│ │  WAIT  │ │  WAIT  │   ← карточки-досье, активная —     │
│  └────────┘ └────────┘ └────────┘     янтарная рамка + пульсация     │
├──────────────────┬───────────────────────────────────────────────────┤
│  РЕЦЕПТ          │                                                   │
│                  │                  ╭─────────╮                      │
│  ✔ 1. Молоко     │                 ╱  КОЛЬЦО   ╲    ← кольцевая      │
│      героя ×3    │                │   ВАРКИ     │      шкала (SVG)   │
│  ▶ 2. Сахар ×2   │                │  ┌───────┐  │                    │
│    3. Корица ×1  │                 ╲ │ КОТЁЛ │ ╱   ← зона удержания  │
│    4. ВАРКА 6 с  │                  ╰─────────╯                      │
│                  │            [ вертикальная шкала дозы ]            │
├──────────────────┴───────────────────────────────────────────────────┤
│  ПОЛКА ИНГРЕДИЕНТОВ                                                  │
│  [пыль] [мёд] [молоко] [корица] [уголёк] [сахар] [мята] [болт]       │
└──────────────────────────────────────────────────────────────────────┘
```

| Зона | Содержимое |
|---|---|
| **Верх — очередь персонажей** | Горизонтальный ряд карточек-досье, вплотную друг к другу. Каждая: статусная полоса сверху (`ГОТОВИТСЯ` / `ОЖИДАЕТ` / `ВЫДАНО`), портрет (`portrait`, asset), крупное имя снизу, под именем — название заказа (`orderName`) мелким моноширинным. Активная карточка — янтарная рамка + слабая пульсация индикатора; выполненные — приглушены, статусная полоса бирюзовая `ВЫДАНО`; ожидающие — серо-бирюзовые. Справа в этой же строке — индикатор ошибок (`failsAllowed` круглых маркеров, потраченные горят оранжевым) и кнопка mute. |
| **Лево — рецепт** | Панель со списком шагов текущего заказа. Каждый шаг: номер, название ингредиента, требуемая доза (`×N ложки` / `положить` для `amount = 0`). Выполненные шаги — с галочкой и приглушённые, текущий — янтарный с маркером `▶`, будущие — обычные. Последней строкой всегда финальный шаг «ВАРКА N с». |
| **Центр — котёл и кольцевая шкала** | Крупный котёл (контурная иллюстрация в стиле светящегося чертежа). Вокруг котла — кольцевая SVG-шкала варки, активная только на финальном шаге. Во время дозирования рядом с котлом (или поверх его правого края) показывается вертикальная линейная шкала уровня с янтарной зоной допуска. |
| **Низ — полка ингредиентов** | Горизонтальный ряд квадратных кнопок-ячеек по одной на каждый элемент `ingredients[]`: изображение (`image`, asset), название, единица измерения (`unitName`). Кнопки — физические элементы терминала: тонкая внешняя рамка, внутренний контур, подсветка рамки при наведении. |

### 1.2 Состояние текущего заказа

Игра держит указатель на текущий заказ (`orderIndex`) и текущий шаг внутри него (`stepIndex`).
Шаги выполняются **строго по порядку** массива `steps[]` — это не набор, а последовательность.

| Состояние (`phase`) | Что происходит |
|---|---|
| `idle` | Ждём действия игрока: клика по ингредиенту (простой шаг) или начала удержания (дозируемый шаг), либо начала варки, если `stepIndex === steps.length`. |
| `pouring` | Игрок удерживает указатель на ингредиенте, уровень дозы растёт по rAF. |
| `cooking` | Игрок удерживает указатель на котле, кольцевая шкала заполняется по времени. |
| `spoiled` | Проигрывается анимация испорченной еды (~1 с), ввод заблокирован. |
| `orderDone` | Короткая анимация выдачи заказа (~0.6 с), после чего активируется следующий персонаж. |
| `wiped` | «ВСЁ СГОРЕЛО»: экран-заглушка (~1.5 с), после — полный сброс смены. |
| `finished` | Все заказы выданы; вызван `onComplete`. |

### 1.3 Типы шагов

**Дозируемый шаг (`amount > 0`)** — «×N ложки». Игрок нажимает и **удерживает** указатель на нужной
ячейке полки. Уровень в котле растёт линейно со скоростью `fillRatePerSec` (единиц в секунду).
Отпустить нужно, когда уровень попал в янтарную зону допуска вокруг `amount`. Единица — абстрактная
«порция», её название для рецепта берётся из `unitName` ингредиента (ложка, щепотка, мерка…).

**Простой шаг (`amount = 0`)** — «просто положить». Одиночный клик (`pointerdown` + `pointerup` на той
же ячейке) по нужному ингредиенту. Ни шкалы, ни удержания. Используется для штучных предметов —
уголёк дракона, железный болт, листок мяты.

Определение типа шага — **только по `amount`**, никакого отдельного флага в схеме нет.

### 1.4 Финальный шаг: варка

Когда `stepIndex === steps.length` (все ингредиенты добавлены), рецепт подсвечивает строку «ВАРКА N с»,
полка ингредиентов гаснет (клики по ней в этой фазе — ошибка, см. §3), а котёл получает янтарную рамку
и подпись «ЗАЖМИ». Игрок удерживает указатель на котле; кольцевая шкала заполняется по часовой стрелке.
Полный оборот кольца = `cookSeconds × (1 + cookTolerancePct/100)` — то есть верхняя граница допуска
совпадает с замыканием кольца. Янтарный сектор — от `cookSeconds × (1 - cookTolerancePct/100)` до конца.
Отпустить нужно внутри сектора.

### 1.5 Переход между заказами

Успешный `endCook` → `phase = 'orderDone'`:

1. Начисляются очки за заказ (`pointsPerOrder`), звук успеха (`sounds.orderDone`).
2. Карточка текущего персонажа меняет статус на `ВЫДАНО`, приглушается; идёт короткая анимация
   (появление через маску, ~0.6 с) — по STYLE.md, без пружин и парения.
3. `orderIndex++`, `stepIndex = 0`. Карточка следующего персонажа получает янтарную рамку и статус
   `ГОТОВИТСЯ`, панель рецепта перерисовывается под новый заказ, котёл очищается.
4. Вызывается `onProgress('ЗАКАЗ 2/3 · ' + orderName, percent)`.
5. Если заказов больше нет — `phase = 'finished'`, экран итога и `onComplete` (см. §3.4).

Очередь **не** перемешивается и не сокращается: порядок персонажей — ровно порядок `characters[]` в конфиге.

## 2. Управление

Игра управляется одним указателем (мышь на ноутбуке-терминале; тач тоже работает — используются
`pointer`-события, не `mouse`/`touch`). Клавиатура не требуется.

### 2.1 Дозирование: `pointerdown` + rAF

1. `pointerdown` на ячейке ингредиента. Обработчик сразу вызывает `el.setPointerCapture(e.pointerId)` —
   удержание не срывается, если курсор ушёл за пределы ячейки (§6.1).
2. `startPour(ingredientId, t)` в движке. Если ингредиент неверный или текущий шаг простой — сразу
   ошибка (§3.1), rAF не запускается.
3. Запускается rAF-петля. Каждый кадр: `level += dt * fillRatePerSec`, где `dt` — дельта в секундах.
   Уровень рисуется на вертикальной шкале рядом с котлом; параллельно котёл «наполняется» цветом
   ингредиента, а ячейка ингредиента подсвечивается янтарным.
4. Шкала размечена так: **высота шкалы = `amount + doseTolerancePct/100`** единиц. Янтарная зона —
   от `amount - doseTolerancePct/100` до самого верха шкалы. То есть допуск читается как
   «долей до верха, но не через край».
5. `pointerup` (слушается на `window`, §6.1) → `endPour(t)`:
   - уровень внутри янтарной зоны → шаг засчитан, `stepIndex++`, очки `pointsPerStep`, звук `sounds.pourOk`;
   - уровень ниже зоны (недолил) → ошибка.
6. Если уровень **превысил** верх шкалы, ошибка засчитывается **немедленно, прямо в кадре rAF**, не
   дожидаясь отпускания (§6.4).

При `doseTolerancePct = 40` и `fillRatePerSec = 1.5` окно попадания = `0.8 / 1.5 ≈ 0.53 с` реального
времени — заметно, но требует внимания. Абсолютная ширина допуска **не зависит** от `amount`: чем больше
доза, тем меньше допуск в процентах от шкалы (×1 → зона занимает ~57 % шкалы, ×4 → ~18 %). Так сложность
рецепта регулируется прямо величиной доз.

### 2.2 Простой шаг: одиночный клик

Для шага с `amount = 0` игра не запускает rAF. Действие срабатывает на `pointerup` **при условии**, что
`pointerdown` был на той же ячейке (защита от «мазка» мимо). Движку отправляется `pickIngredient(id)`.
Верный ингредиент → шаг засчитан, короткий импульс свечения ячейки и звук `sounds.place`.
Неверный → ошибка.

Долгое удержание на простом шаге ничего не ломает: пока кнопка зажата, ячейка просто подсвечена,
шкала не появляется, результат определяется в момент отпускания.

### 2.3 Варка: удержание котла

Механика идентична дозированию, только цель — время, а индикатор — кольцевая шкала:

1. `pointerdown` на котле → `setPointerCapture` → `startCook(t)`.
2. rAF: `held += dt`, кольцо заполняется от 0 до `cookSeconds × 1.12` (при `cookTolerancePct = 12`).
   Янтарный сектор — последние 24 % оборота (от `×0.88` до `×1.12`).
3. `pointerup` на `window` → `endCook(t)`: время внутри сектора → заказ выполнен; раньше сектора
   (недовар) или позже (перевар) → ошибка. Перевар, как и перелив, фиксируется **немедленно** в кадре
   rAF при пересечении верхней границы — котёл вспыхивает оранжевым, не дожидаясь отпускания.

### 2.4 Выбор ингредиента с полки

Отдельного «выбора» с последующим подтверждением нет: нажатие на ячейку **и есть** выполнение текущего
шага. Это осознанное упрощение — исключает состояние «ингредиент выбран, но не применён» и все связанные
с ним edge-кейсы. Наведение подсвечивает рамку ячейки бирюзовым; активная (зажатая) — янтарным.

### 2.5 `setPointerCapture`

Захват ставится на **все** элементы, поддерживающие удержание (ячейки полки и котёл), в обработчике
`pointerdown`, и снимается автоматически при `pointerup`/`pointercancel`. Без захвата удержание рвалось
бы при малейшем сдвиге курсора за пределы ячейки — а элементы полки маленькие и стоят вплотную.
Дублирующий слушатель `pointerup` на `window` остаётся как страховка (§6.1).

## 3. Победа и пенальти

### 3.1 Что считается ошибкой

| Ситуация | Когда фиксируется |
|---|---|
| Нажат **не тот ингредиент** (не совпадает с `steps[stepIndex].ingredientId`) | В момент `pointerdown` / `pickIngredient` |
| **Неверный порядок**: нажат ингредиент из более позднего (или уже пройденного) шага | Там же — частный случай предыдущего пункта, проверка одна: «совпадает ли с текущим шагом» |
| **Промах дозы вниз** (недолил, уровень < нижней границы допуска) | В момент `endPour` |
| **Перелив** (уровень > верхней границы) | Немедленно в кадре rAF, не дожидаясь отпускания |
| **Недовар** (отпустил котёл раньше янтарного сектора) | В момент `endCook` |
| **Перевар** (время > верхней границы) | Немедленно в кадре rAF |
| Клик по полке в фазе варки / по котлу до завершения всех шагов | В момент `pointerdown` (действие не соответствует текущему шагу) |

### 3.2 Что происходит при ошибке

1. `phase = 'spoiled'`, весь ввод игнорируется.
2. **Анимация испорченной еды**, ~1 с (`spoilAnimationMs`): котёл мигает оранжево-красным (`#F0713E`),
   короткий цифровой сбой (glitch) по всей панели рецепта, мигающий круглый маркер тревоги,
   надпись `ИСПОРЧЕНО` на оранжевой статусной полосе, звук `sounds.fail`. Карточка активного персонажа
   на время анимации получает тревожную рамку.
3. **Заказ откатывается на шаг 1** (`stepIndex = 0`, котёл очищается). Это **не** рестарт всей игры и
   **не** пропуск заказа — тот же персонаж ждёт то же блюдо заново.
4. Очки, начисленные за уже выполненные шаги **этого** заказа, снимаются (иначе повтор шагов фармил бы
   очки). Очки за ранее выданные заказы не трогаются.
5. Глобальный счётчик `fails` увеличивается на 1, гаснет один маркер в индикаторе ошибок.
6. Через `spoilAnimationMs` — `phase = 'idle'`, игра продолжается.

### 3.3 «ВСЁ СГОРЕЛО»

Когда `fails` достигает `failsAllowed` (по умолчанию 3):

1. `phase = 'wiped'`. Полноэкранная (в пределах контейнера) заглушка: крупная надпись **«ВСЁ СГОРЕЛО»**
   оранжево-красным на почти чёрном, мигающие маркеры тревоги, звук `sounds.wipe`, ~1.5 с.
2. **Полный сброс смены**: `orderIndex = 0`, `stepIndex = 0`, `fails = 0`, `score = 0`, все карточки
   персонажей возвращаются в статус `ОЖИДАЕТ`, первая — снова активна. Все заказы проходятся заново.
3. Счётчик `wipes` (сколько раз всё сгорело за сессию) увеличивается на 1 и **не** сбрасывается —
   он попадёт в `details` и повлияет на `styleTag`.
4. `onProgress('ВСЁ СГОРЕЛО · СМЕНА С НАЧАЛА', 0)`.

Игра **не завершается** проигрышем сама по себе — это осознанное решение из плана: «ВСЁ СГОРЕЛО»
перезапускает смену внутри сессии, а не отдаёт `onComplete({won: false})`. Единственный путь наружу с
`won = false` — платформенная кнопка «ВЫЙТИ» в слоте 3 нижней панели, которая вызывает `onExit()`
(см. `docs/platform.md` §1.3). `post_lose_dialogue_id` в этой игре, соответственно, практически не
используется; сюжетная развилка делается через `styleTag` на победе.

### 3.4 Победа и очки

Все заказы выданы → `phase = 'finished'`, экран итога (~1.2 с: «СМЕНА ЗАКРЫТА», счёт, число ошибок),
затем `onComplete`:

```ts
callbacks.onComplete({
  score,               // pointsPerStep × всего шагов + pointsPerOrder × заказов − штрафы
  won: true,
  details: {
    orders: 3,         // выдано заказов
    fails: 1,          // ошибок за последнюю (успешную) смену
    wipes: 0,          // сколько раз всё сгорело за сессию
    styleTag: 'flawless'
  }
})
```

| Событие | Очки |
|---|---|
| Успешный шаг (дозируемый или простой) | `+pointsPerStep` (по умолчанию 10) |
| Успешная варка + выдача заказа | `+pointsPerOrder` (по умолчанию 50) |
| Ошибка | Снимаются очки за шаги текущего заказа (см. §3.2 п.4) |
| «ВСЁ СГОРЕЛО» | `score = 0` |

`styleTag` для `style_dialogue_map` (`docs/platform.md` §3.3):

| Значение | Условие |
|---|---|
| `flawless` | `wipes = 0` и `fails = 0` — ни одного испорченного блюда за всю смену |
| `steady` | `wipes = 0`, но были ошибки — справился, хоть и пересолил |
| `scorched` | `wipes ≥ 1` — смена начиналась заново, но заказы всё-таки выданы |

`onProgress` вызывается при смене шага, смене заказа, ошибке и вайпе — не каждый кадр:
`onProgress('ЗАКАЗ 2/3 · ШАГ 3/4', percent)`, где `percent` — доля выполненных шагов от общего числа
шагов всех заказов (включая шаги варки).

## 4. Настройки админки (`schema.json`)

### 4.1 Поля схемы

| Путь | Тип / `x-type` | Заголовок | Дефолт | Комментарий |
|---|---|---|---|---|
| `ingredients[]` | array | Ингредиенты | 8 шт., см. §4.2 | Общая полка на всю игру, минимум 2 |
| `ingredients[].id` | string | ID | — | kebab-case, уникален; на него ссылаются шаги |

## 5. Реализация

### 5.1 `src/engine.ts` — чистая машина состояний

Движок **не знает о DOM, времени и rAF**: все переходы получают текущую метку времени параметром и
возвращают новое состояние. Это делает FSM полностью детерминированной и тестируемой.

```ts
export type Step = { ingredientId: string; amount: number };
export type Order = { name: string; orderName: string; steps: Step[]; cookSeconds: number };

export type Config = {
  orders: Order[];
  fillRatePerSec: number;
  doseTolerancePct: number;
  cookTolerancePct: number;
  failsAllowed: number;
  pointsPerStep: number;
  pointsPerOrder: number;
};

export type Phase = 'idle' | 'pouring' | 'cooking' | 'spoiled' | 'orderDone' | 'wiped' | 'finished';

export type State = {
  phase: Phase;
  orderIndex: number;
  stepIndex: number;
  holdStartedAt: number | null;  // мс, метка начала удержания
  holdValue: number;             // единиц налито (pouring) или секунд варки (cooking)
  score: number;
  orderScore: number;            // очки за шаги текущего заказа — снимаются при ошибке
  fails: number;
  wipes: number;
};

export function initialState(): State;
```

Переходы (все — чистые `(state, config, …) => State`):

| Функция | Сигнатура | Что проверяет / делает |
|---|---|---|
| `pickIngredient` | `(s, cfg, ingredientId: string) => State` | Только для простого шага. Проверки: `phase === 'idle'`; текущий шаг существует; `step.amount === 0`; `step.ingredientId === ingredientId`. Любая непройденная проверка → `fail(s)`. Успех → `stepIndex++`, `+pointsPerStep`. Если шагов больше нет — состояние остаётся `idle`, но UI переключается на варку. |
| `startPour` | `(s, cfg, ingredientId: string, t: number) => State` | Только для дозируемого шага. Проверки: `phase === 'idle'`; шаг существует; `step.amount > 0`; `step.ingredientId === ingredientId`. Провал → `fail(s)`. Успех → `phase = 'pouring'`, `holdStartedAt = t`, `holdValue = 0`. |
| `tickHold` | `(s, cfg, t: number) => State` | Вызывается из rAF в фазах `pouring`/`cooking`. Пересчитывает `holdValue` от `holdStartedAt`. Если `pouring` и `holdValue > amount + tol` → `fail` (перелив). Если `cooking` и `holdValue > cookSeconds × (1 + cookTolerancePct/100)` → `fail` (перевар). Дельта кадра > 500 мс → `cancelHold` (§6.3). |
| `endPour` | `(s, cfg, t: number) => State` | Проверка: `phase === 'pouring'`. Считает финальный `holdValue`. Попадание в `[amount − tol, amount + tol]`, где `tol = doseTolerancePct/100` (в единицах) → `stepIndex++`, `+pointsPerStep`, `phase = 'idle'`. Иначе → `fail`. |
| `startCook` | `(s, cfg, t: number) => State` | Проверки: `phase === 'idle'`; `stepIndex === steps.length` (все ингредиенты добавлены). Если шаги ещё остались → `fail` (игрок полез варить рано). Успех → `phase = 'cooking'`, `holdStartedAt = t`, `holdValue = 0`. |
| `endCook` | `(s, cfg, t: number) => State` | Проверка: `phase === 'cooking'`. Время в `[cook × (1 − tol), cook × (1 + tol)]` → `+pointsPerOrder`, `orderIndex++`, `stepIndex = 0`, `orderScore = 0`, `phase = 'orderDone'` (или `'finished'`, если заказов больше нет). Иначе → `fail` (недовар). |
| `cancelHold` | `(s) => State` | Отмена удержания **без пенальти**: `phase = 'idle'`, `holdStartedAt = null`, `holdValue = 0`, `stepIndex` не меняется, `fails` не растёт. Используется при `blur`/`visibilitychange`/`pointercancel`/большой дельте rAF. |
| `resolveSpoiled` | `(s) => State` | Вызывается по окончании анимации порчи: `phase = 'idle'`. Если предыдущий `fail` довёл `fails` до `failsAllowed` — вместо этого движок уже находится в `wiped`, и переход делает `resolveWipe`. |
| `resolveWipe` | `(s) => State` | По окончании заставки «ВСЁ СГОРЕЛО»: полный сброс смены (`orderIndex = 0`, `stepIndex = 0`, `fails = 0`, `score = 0`, `orderScore = 0`), `wipes` сохраняется и уже увеличен. |

Внутренний хелпер (не экспортируется наружу как переход, но покрыт тестами через публичные функции):

```ts
function fail(s: State, cfg: Config): State  // score -= orderScore; orderScore = 0; stepIndex = 0;
                                             // fails++; phase = fails >= failsAllowed ? 'wiped' : 'spoiled';
                                             // при 'wiped' — wipes++
```

Селекторы для рендера (тоже чистые): `currentOrder(s, cfg)`, `currentStep(s, cfg)`,
`doseWindow(s, cfg) → {min, max, scaleMax}`, `cookWindow(s, cfg) → {min, max, ringMax}`,
`progress(s, cfg) → {text, percent}`.

### 5.2 `src/engine.test.ts` — vitest

Минимальный, но покрывающий все ветки набор:

- **Простой шаг:** верный ингредиент → `stepIndex` +1 и очки; неверный → `fails = 1`, `stepIndex = 0`.
- **Порядок:** ингредиент из шага 3, когда текущий шаг 1 → ошибка.
- **Дозирование:** `startPour` → `endPour` ровно на `amount / fillRatePerSec` секунд → успех;
  на границе допуска (`amount − tol`, `amount + tol`) → успех (границы **включительно**);
  на волосок за границей → ошибка.
- **Перелив:** `tickHold` за верхней границей → `phase = 'spoiled'` без вызова `endPour`.
- **Варка:** `endCook` в допуске → `orderIndex` +1; недовар и перевар → ошибка; `startCook` при
  непройденных шагах → ошибка.
- **Пенальти:** ошибка обнуляет `orderScore` и откатывает `stepIndex` на 0, но не трогает `orderIndex`
  и очки за прошлые заказы.
- **Вайп:** три ошибки подряд → `phase = 'wiped'`, `wipes = 1`; `resolveWipe` → всё с нуля,
  `wipes` остался 1.
- **Отмена:** `cancelHold` в середине наполнения → `fails` не изменился, `stepIndex` не изменился.
- **Победа:** полный прогон трёх дефолтных заказов → `phase = 'finished'`, ожидаемый `score`.
- **Пустой `steps[]`:** см. §6.6.

Тесты работают на синтетических метках времени (`endPour(s, cfg, 2000)`), никаких таймеров и фейковых
часов не требуется — движок чистый.

### 5.3 `src/index.ts` — DOM

Единственный модуль, знающий про DOM, время и звук. Экспортирует `init(container, config, callbacks)`
и возвращает `{ destroy }`.

**Рендер.** Всё строится один раз при `init` (стили — один `<style>` внутри контейнера, все селекторы
scoped под корневой класс игры, никаких глобальных стилей):

- **Очередь:** `<div class="queue">` с карточкой на каждый `characters[]` — статусная полоса, `<img>`
  портрета, имя, `orderName`. Обновление статуса — сменой класса, без перестроения DOM.
- **Рецепт:** `<ol class="recipe">`, перестраивается при смене заказа; при смене шага меняются только
  классы строк.
- **Котёл:** `<div class="pot">` + inline SVG-кольцо: два `<circle>` (фон-дорожка и прогресс через
  `stroke-dasharray`/`stroke-dashoffset`) плюс `<path>`-дуга янтарного сектора допуска, отрисованная
  один раз на заказ. Обновление в rAF — только `style.strokeDashoffset`, без пересборки SVG.
- **Шкала дозы:** `<div class="gauge">` с абсолютно спозиционированным заполнением (`height: %`) и
  янтарной полосой зоны допуска; в rAF меняется одна CSS-переменная.
- **Полка:** `<div class="shelf">` с кнопкой на каждый ингредиент.

**События.** Один делегирующий слушатель `pointerdown` на корневом элементе (определяет цель по
`data-*`-атрибутам), `pointerup` и `pointercancel` — на `window`, плюс `blur` и `visibilitychange`.
`setPointerCapture` ставится на конкретный элемент, по которому пришёл `pointerdown`.

**rAF-петля** запускается только на время удержания (в `idle` кадры не тратятся вовсе — экономия
батареи ноутбука-терминала). Каждый кадр: `state = tickHold(state, cfg, performance.now())`, затем
обновление шкалы; если `state.phase` сменилась на `spoiled`/`wiped` — петля останавливается и
запускается анимация.

**Таймеры анимаций** (`spoiled` → `resolveSpoiled`, `orderDone` → следующий заказ, `wiped` →
`resolveWipe`, экран итога → `onComplete`) — через `setTimeout` с сохранением id в массив, который
целиком чистится в `destroy()`.

**`destroy()`:** отменяет rAF, чистит все `setTimeout`, снимает слушатели с `window`/`document`,
останавливает и обнуляет `<audio>`-элементы, `container.innerHTML = ''`.

**Колбэки:** `onProgress` — при каждой смене шага/заказа/ошибке; `onComplete` — ровно один раз,
после экрана итога; `onExit` — игрой не вызывается (выход инициирует платформа).

## 6. Edge cases

### 6.1 `pointerup` мимо элемента

`pointerup` слушается **на `window`**, а не только на ячейке/котле. Плюс в `pointerdown` вызывается
`setPointerCapture(e.pointerId)`. Двойная защита нужна, потому что оба сценария реальны: курсор ушёл за
пределы маленькой ячейки полки (лечит capture) и курсор ушёл вообще за пределы окна браузера, где
кнопка была отпущена (лечит слушатель на `window`, capture там уже не помогает). Без этого «зависшее»
удержание продолжало бы наливать и мгновенно давало бы перелив — незаслуженную ошибку.

`pointercancel` (система отобрала указатель — например, жест браузера) трактуется как `cancelHold`,
то есть **без пенальти**.

### 6.2 `blur` / `visibilitychange` во время удержания

Если во время `pouring`/`cooking` окно теряет фокус или вкладка уходит в фон — вызывается `cancelHold`:
удержание отменяется, шаг **не** засчитывается и **не** штрафуется, `fails` не растёт, шкала
сбрасывается в 0. Причина прямая: `requestAnimationFrame` в фоновой вкладке замирает, реальное время
продолжает идти, и любой исход (перелив, недолив) был бы артефактом системного прерывания, а не
действия игрока. Штрафовать за это нечестно.

На экране показывается нейтральная плашка «ПРЕРВАНО — ПОВТОРИ ШАГ» (бирюзовая, не тревожная — визуально
это **не** ошибка), шаг остаётся текущим.

### 6.3 Дельта rAF больше 500 мс

Даже без событий `blur`/`visibilitychange` кадр может «провалиться»: свёрнутое окно, спящий ноутбук,
тяжёлый GC, переключение вкладки в браузере, который не шлёт `visibilitychange`. Поэтому в `tickHold`
есть страховка: если `t − lastFrameTime > 500`, удержание отменяется через `cancelHold` — тот же
сценарий, что и в §6.2, без пенальти. Порог 500 мс выбран заведомо выше любого нормального кадра
(16.7 мс при 60 FPS, ~33 мс при просадке до 30) и заведомо ниже, чем время, за которое можно случайно
перелить целую дозу.

Важно: `holdValue` считается **не** накоплением дельт, а как `(t − holdStartedAt) / 1000 × fillRatePerSec`
— от абсолютной метки старта. Дельта отслеживается отдельно, только ради этой проверки. Так удержание
не «отстаёт» из-за пропущенных кадров и остаётся честным по реальному времени.

### 6.4 Перелив за верхнюю границу шкалы

Фиксируется **немедленно в кадре rAF**, а не при отпускании. Как только `holdValue` превысил
`amount + doseTolerancePct/100`, `tickHold` возвращает состояние с `phase = 'spoiled'`: rAF
останавливается, играет анимация порчи, отпускание кнопки уже ни на что не влияет (обработчик
`pointerup` видит фазу `spoiled` и игнорирует событие). То же самое для перевара на кольцевой шкале.

Так игрок получает мгновенную обратную связь ровно в момент ошибки — держать зажатой кнопку над
сгоревшим котлом бессмысленно, а верхняя граница шкалы физически совпадает с её краем, что делает
правило читаемым без объяснений: «за край — испортил».

### 6.5 Клик по неактивной карточке персонажа

Карточки очереди — **не интерактивный элемент**: у них нет обработчиков, `cursor: default`,
`pointer-events: none` на всей зоне очереди (кроме кнопки mute). Клик по будущему или уже выданному
заказу просто игнорируется — ни ошибки, ни переключения активного заказа. Порядок очереди фиксирован
конфигом; выбирать, кого обслуживать, игрок не может — это не часть механики.

### 6.6 Пустой `steps[]` у заказа

Формально валидный конфиг (`minItems` на `steps` не ставим — админ может временно сохранить заказ без
шагов). Поведение: такой заказ состоит **только из варки** — `stepIndex === steps.length === 0`
выполняется сразу, панель рецепта показывает единственную строку «ВАРКА N с», полка ингредиентов
заблокирована с самого начала, любой клик по ней — ошибка (по общему правилу §3.1). Отдельной ветки в
движке для этого не требуется: условие `stepIndex === steps.length` в `startCook` истинно с нуля,
и это покрыто тестом.

Пустой `characters[]` (заказов нет вообще) — уже ошибка конфигурации: игра рендерит в контейнере
плашку «КОНФИГ ПУСТ: НЕТ ЗАКАЗОВ» и **не** вызывает `onComplete`, оставляя выход платформе (кнопка
«ВЫЙТИ» → `onExit()`). Молча отдавать `won: true` за несуществующую работу нельзя — это засчитало бы
игру пройденной и открыло следующие по `required_game_ids`.

### 6.7 Прочее

- **Ссылка на несуществующий `ingredientId`** в шаге: такой шаг невыполним. Игра при `init` валидирует
  конфиг и при битой ссылке показывает ту же плашку ошибки конфигурации, что и в §6.6 (с текстом, какой
  id не найден) — лучше явный отказ на этапе теста в админке, чем непроходимый уровень у игрока.
- **Повторный `pointerdown` во время удержания** (второй палец на тач-экране): игнорируется — движок
  принимает `startPour`/`startCook` только из фазы `idle`.
- **`amount` больше, чем помещается на экран:** высота шкалы дозы всегда нормируется под
  `amount + tol`, разметка делений — по единицам; при `amount > 10` деления рисуются без подписей.
  Разумный потолок доз — 5–6, это вопрос контента, а не кода.
