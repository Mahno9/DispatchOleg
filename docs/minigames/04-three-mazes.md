# Мини-игра 04: three-mazes (три лабиринта)

> `minigame_id`: `three-mazes` · Canvas · только мышь · ~3–4 дня разработки
>
> Базовый контракт — `GameService/minigame_contract.md` (`init(container, config, callbacks)`, обязательный
> `destroy()`, изоляция, 60 FPS, `schema.json`). Расширения платформы — `docs/platform.md` §3
> (`onProgress`, `onComplete.details`, ветвление пост-диалога по `styleTag` — §3.3).
> Визуальный стиль — `STYLE.md`: контурные светящиеся чертежи на почти чёрном фоне, бирюзовые линии,
> янтарные/оранжевые акценты для активных и тревожных элементов.

Игрок ведёт точку по трём лабиринтам подряд, не касаясь стен. Часть стен — ломаемые: их можно пробить
на скорости и срезать путь, но ценой риска. Игра не спрашивает игрока, какой стиль он выбирает — она
**наблюдает** и по итогу сообщает платформе `styleTag`: `"ghost"` (прошёл чисто) или `"breaker"`
(проламывался). Платформа по этому тегу подставляет разный пост-диалог — «какого персонажа ты отыграл».

---

## 1. Геймплей и состояния

### 1.1 Три лабиринта последовательно

Прохождение — линейная последовательность из ровно трёх лабиринтов, заданных в конфиге как `mazes[0..2]`.
Порядок фиксирован конфигом (админ задаёт его вручную, игра не перемешивает). Рекомендуемая — и
предполагаемая по умолчанию — топология:

| #   | `generatorParams.type` | Характер                                            | Роль в прогрессии                                                      |
| --- | ---------------------- | --------------------------------------------------- | ---------------------------------------------------------------------- |
| 0   | `square`               | Ортогональная сетка, стены строго по осям           | Обучающий: игрок нащупывает инерцию точки, ломаемые стены очевидны     |
| 1   | `hex`                  | Гексагональная сетка, стены под углами кратными 60° | Ломает «осевую» моторику — диагональные коридоры, срезки под углом     |
| 2   | `circular`             | Концентрические кольца + радиальные перемычки       | Дуги как полилинии; ломаемые стены на кольцах дают радиальные шорткаты |

Переход между лабиринтами — автоматический, без экрана-заставки: по достижении финиша играется короткая
вспышка финишной зоны (бирюзовый импульс, ~250 мс по `STYLE.md`), затем поле перерисовывается под
следующий лабиринт, и новый лабиринт входит в состояние «заморожен».

Прогресс сообщается платформе через `onProgress` (см. `docs/platform.md` §3.1) при каждой смене
лабиринта и при каждом сбросе:

```ts
callbacks.onProgress(`ЛАБИРИНТ ${i + 1} / 3`, Math.round((i / 3) * 100));
```

Внутри лабиринта `percent` не обновляется покадрово — доля пройденного пути в лабиринте не определена
формально (игрок может ходить назад), поэтому шкала дискретна: 0 / 33 / 66 / 100.

### 1.2 Состояния лабиринта

Каждый лабиринт — независимый экземпляр одной и той же машины состояний:

```
   ┌──────────┐  курсор вошёл в стартовую зону   ┌────────┐
   │ FROZEN   │ ───────────────────────────────▶ │ ACTIVE │
   │(заморожен)│                                  └───┬────┘
   └──────────┘                                       │
        ▲                                             ├── касание неломаемой стены
        │                                             │   (или ломаемой «вскользь»)
        │                                             ▼
        │                                       ┌──────────┐
        └────────────────────────────────────── │ SCREAMER │  ~screamerDurationMs
                    сброс на старт              └──────────┘
                                                      │
              достигнут финиш                         │
        ACTIVE ────────────────────▶ ┌────────┐       │
                                     │ FINISH │───────┴──▶ следующий лабиринт
                                     └────────┘            (или WIN, если он был третьим)
```

**FROZEN.** Лабиринт нарисован полностью, но точка не существует как физический объект — она не следует
за мышью и не проверяется на коллизии. Стартовая зона (круг радиусом `~24px` вокруг точки старта)
пульсирует янтарным. Как только курсор мыши попадает внутрь стартовой зоны — точка «материализуется»
ровно в позиции курсора (не в центре зоны: иначе на первом же кадре возникнет рывок пружины), и
лабиринт переходит в ACTIVE. Это состояние решает две задачи: во-первых, игрок не начинает движение с
непредсказуемой позиции курсора после смены лабиринта; во-вторых, после скримера у игрока есть время
убрать руку и собраться, а не получить второй скример мгновенно.

**ACTIVE.** Работает физика (§1.4), работают коллизии (§1.3), рисуются эффекты. Единственное состояние,
в котором `wallsBroken` может увеличиваться.

**SCREAMER.** Физика полностью остановлена (точка не двигается, коллизии не проверяются, ввод мыши
только запоминается). Поверх canvas рисуется оверлей: изображение `screamerImage` во весь контейнер
(`object-fit: cover`) + однократное воспроизведение `screamerSound` (если `!config.muted`), длительность
`screamerDurationMs` (по умолчанию 1200 мс). Если `screamerImage` не задан в конфиге — фолбэк: заливка
всего поля `#F0713E` (цвет «Тревога» из `STYLE.md`) с затуханием альфы от 0.85 до 0 за `screamerDurationMs`
и наложенным крупным контурным символом «!». По истечении времени лабиринт **сбрасывается на старт**:
точка удаляется, состояние → FROZEN, `wallsBrokenCurrentMaze = 0` (см. §3.2 и §6.4), к счёту применяется
`penaltyPerReset`.

**FINISH.** Точка коснулась финишной зоны (круг радиусом `~24px`). Ничего больше не считается,
`wallsBrokenCurrentMaze` фиксируется и прибавляется к глобальному `wallsBroken`, `scorePerMaze` этого
лабиринта прибавляется к счёту. Далее — следующий лабиринт (FROZEN) или общая победа.

### 1.3 Единая модель коллизий

Ключевое архитектурное решение: **все три формы лабиринта — это один и тот же тип данных.** Ни сетки,
ни ячеек, ни спецкода на форму в рантайме. Лабиринт после генерации — плоский массив отрезков:

```ts
type Wall = { x1: number; y1: number; x2: number; y2: number; breakable: boolean };
type Maze = { walls: Wall[]; start: { x: number; y: number }; finish: { x: number; y: number } };
```

- **square** — отрезки строго горизонтальные и вертикальные;
- **hex** — те же отрезки, но с направлениями кратными 60°; никакой особой математики шестиугольников
  в рантайме нет, гексагональность живёт только внутри генератора;
- **circular** — дуги аппроксимируются полилиниями с шагом **~10°** по дуге (то есть кольцевая стена
  длиной 90° = 9 отрезков). При радиусе кольца 200px хорда шага 10° отклоняется от дуги менее чем на
  0.8px — визуально и физически неотличимо от гладкой дуги при радиусе точки 6px.

Проверка коллизии — **одна функция на всю игру**:

```ts
distancePointSegment(px, py, x1, y1, x2, y2): number
```

Касание = `distancePointSegment(...) <= DOT_RADIUS` (`DOT_RADIUS = 6`). Функция возвращает также
параметр `t` проекции на отрезок — он нужен для вычисления нормали и точки контакта при отскоке.

Стоимость: перебор всех стен каждый субстеп. При типичном лабиринте (150–400 отрезков) и 3 субстепах
это ~1200 проверок расстояния за кадр — на порядок ниже бюджета 16 мс, никакого broadphase не нужно.
Если конкретный лабиринт из админки окажется существенно плотнее (>1500 отрезков), достаточно добавить
равномерную сетку-хэш — но по умолчанию **этого делать не надо**, преждевременная оптимизация.

### 1.4 Физика следования точки за мышью

Точка (радиус 6px) — не курсор. Она **тянется** к позиции курсора как груз на критически демпфированной
пружине с ограничением скорости. Это центральная механика: именно она делает игру игрой, а не тестом на
аккуратность мыши, и именно она не даёт резкому рывку мыши «прошить» стену.

```
a = k · (mouse − p) − c · v          // ускорение
c = 2 · √k                            // критическое демпфирование: без перелёта, без колебаний
v = clampLength(v + a · dt, vmax)     // кап скорости
p = p + v · dt                        // интегрирование (полушаг Эйлера)
```

Параметры:

| Символ       | Значение                             | Источник                                                                 |
| ------------ | ------------------------------------ | ------------------------------------------------------------------------ |
| `k`          | 120                                  | константа в коде (жёсткость пружины)                                     |
| `c`          | `2√k ≈ 21.91`                        | вычисляется, не настраивается — критическое демпфирование по определению |
| `vmax`       | `followSpeed`, по умолчанию 600 px/с | конфиг                                                                   |
| `DOT_RADIUS` | 6 px                                 | константа                                                                |

Критическое демпфирование (`c = 2√k`) выбрано намеренно: недодемпфированная пружина давала бы
«болтанку» вокруг курсора и случайные касания стен без вины игрока, передемпфированная —
вязкое, «мыльное» управление. Критическое — самое быстрое сближение без единого перелёта.

**Кап скорости `vmax`** — то, ради чего вся конструкция и существует. Как бы резко игрок ни дёрнул
мышь, точка не может пройти за кадр больше `vmax · dt`. При 60 FPS и `followSpeed = 600` это 10px за
кадр — меньше типичной ширины коридора.

**Сабстепы против туннелирования.** Даже 10px за кадр — это больше диаметра точки (12px), и коллизия,
проверяемая только в конечной позиции, может пропустить тонкую стену. Поэтому перемещение за кадр
дробится:

```ts
const steps = Math.min(3, Math.max(1, Math.ceil((speed * dt) / 3))); // шаг ≤ 3px
```

То есть шаг субстепа не превышает **3px**, но не более **3 субстепов** за кадр (при `vmax = 600` и
`dt = 16.7мс` смещение 10px → 4 шага, ограничиваем 3 → шаг 3.33px — приемлемо, всё равно вдвое меньше
радиуса точки). Каждый субстеп: интегрируем, проверяем все стены, при попадании — немедленно
прекращаем обработку кадра и переходим в обработку столкновения (§2.3). Кап на 3 субстепа защищает от
патологии: при аномально большом `dt` (см. §6.2) мы не уходим в тысячу итераций.

## 2. Управление

### 2.1 Только мышь

Единственное устройство ввода — **движение курсора мыши** внутри canvas. Ни клавиатуры, ни кликов, ни
касаний (игра ориентирована на ноутбук/десктоп, что соответствует сценарию терминала-диспетчерской с
камерой). Никаких кнопок «начать», «повторить», «пауза» внутри игрового поля: старт — вход в стартовую
зону, повтор после скримера — тоже вход в стартовую зону.

Обрабатывается ровно одно событие ввода:

```ts
canvas.addEventListener('pointermove', (e) => {
  const r = canvas.getBoundingClientRect();
  target.x = (e.clientX - r.left) * (canvas.width / r.width);
  target.y = (e.clientY - r.top) * (canvas.height / r.height);
});
```

Плюс `pointerleave` (§6.1) и `blur`/`visibilitychange` (§6.2) — но это обработка ухода фокуса, не ввод.

Единственный элемент UI внутри контейнера — обязательная по базовому контракту **кнопка mute**
(квадратная, в углу поля, по `STYLE.md`: тонкая рамка, контурная иконка динамика, бирюзовая подсветка
при наведении). Клик по ней не влияет на игровое состояние — она вне игрового поля, наведение на неё не
считается касанием стены.

### 2.2 Выбор стиля — поведением, а не меню

**Игра нигде не спрашивает, каким стилем игрок хочет пройти.** Нет экрана выбора, нет тумблера, нет
подсказки «сломай стену, чтобы срезать». Оба стиля физически возможны в каждом лабиринте, и решение
принимается моторно, много раз за прохождение:

- **Стелс (`ghost`)** — пройти, не задев ни одной стены. Генератор гарантирует (§5.3), что в каждом
  лабиринте существует **честный полный путь** от старта до финиша по открытым коридорам, без единого
  пролома. Путь длиннее, извилистее, требует аккуратности на поворотах.
- **Пробивание (`breaker`)** — тот же стелс, но игрок использует ломаемые стены как двери. Ломаемая
  стена — это всегда **срезка**: она соединяет два коридора, между которыми честный путь идёт в обход.
  Пробить = сэкономить расстояние и время.

Ломаемые стены визуально отличимы всегда и не требуют объяснения: они рисуются **янтарным пунктиром
(`#E9A928`) с наложенным рисунком трещин**, в отличие от сплошных бирюзовых линий (`#5DE2D0`)
неломаемых. Игрок читает это как «здесь тонко» без единого слова текста.

Ценой пробивания служит риск. Стена ломается только при **точном и быстром** ударе (§2.3): попадание
под углом или на малой скорости — это обычное касание стены, то есть скример и сброс всего лабиринта
с потерянным прогрессом. Плюс сам пролом отбрасывает точку назад с большой скоростью в момент, когда
пружина ослаблена, — игрок должен заранее увести курсор за стену, чтобы после отскока точка потянулась
в нужную сторону, а не влетела в стену напротив.

Так и получается драматургия: осторожный игрок медленно проползает честный маршрут и получает
`styleTag = "ghost"`; нетерпеливый таранит и получает `"breaker"`. Ни один из вариантов не «правильный»
— оба ведут к победе, но к разным пост-диалогам (§3.4).

### 2.3 Столкновение: слом или скример

При обнаружении касания (расстояние до отрезка ≤ `DOT_RADIUS`) решается ровно один вопрос: это **слом**
или **провал**.

Пусть `n` — единичная нормаль стены, направленная **в сторону точки** (от стены к точке), `v̂` —
единичный вектор скорости точки, `|v|` — её модуль.

Слом происходит, если стена ломаемая **И** выполнены оба условия:

| Условие        | Формула                                    | Смысл                            | Параметр                           |
| -------------- | ------------------------------------------ | -------------------------------- | ---------------------------------- |
| Угол удара     | `dot(v̂, −n) ≥ cos(breakAngleDeg)`          | Бить надо «в лоб», а не вскользь | `breakAngleDeg`, default 40°       |
| Скорость удара | `\|v\| ≥ breakMinSpeedRatio · followSpeed` | Бить надо разогнавшись           | `breakMinSpeedRatio`, default 0.55 |

При `breakAngleDeg = 40°` порог `cos(40°) ≈ 0.766` — конус допустимых направлений удара ±40° от
нормали. При `breakMinSpeedRatio = 0.55` и `followSpeed = 600` требуется ≥330 px/с — это заметный
осознанный рывок, случайно не наберётся.

**Если оба условия выполнены — слом:**

1. Стена удаляется из активного списка отрезков (проход открыт до конца попытки; при сбросе лабиринта
   стены восстанавливаются — §6.4).
2. `wallsBrokenCurrentMaze += 1`.
3. Точка получает **отскок**: `v = n · max(bounceSpeed, 1.15 · |v|)`, где `bounceSpeed` по умолчанию
   400 px/с. Формула с `max` гарантирует, что медленный (но всё же засчитанный) удар всё равно даёт
   ощутимый толчок, а быстрый — отскакивает пропорционально сильнее.
4. На `bounceDurationMs` (default 300 мс) **жёсткость пружины гасится**: эффективная `k` умножается на
   коэффициент, линейно интерполируемый `lerp(0.25 → 1)` за время отскока. Без этого пружина мгновенно
   съела бы отскок и вернула точку в проём — эффект пролома был бы неощутим. С гашением точка реально
   отлетает и игрок обязан заранее держать курсор **за** стеной, чтобы после восстановления пружины
   тяга пошла в нужную сторону.
5. Точка ставится вплотную к бывшей стене со стороны отскока (выталкивание из пересечения на
   `DOT_RADIUS + 0.5px`), чтобы на следующем кадре не сработала повторная коллизия с соседней стеной.

**Во всех остальных случаях — провал:** неломаемая стена (любой угол, любая скорость) или ломаемая,
задетая вскользь / на малой скорости. → SCREAMER → сброс лабиринта.

Именно наличие второй ветки делает пробивание рискованным: «почти сломал» = «не сломал» = потерял
весь лабиринт.

## 3. Победа, пенальти и результат

### 3.1 Условие победы

Победа = **финиш всех трёх лабиринтов**. Явных «жизней» в игре нет, лимита попыток нет, таймера нет.
Столкновение со стеной не приближает поражение — оно откатывает текущий лабиринт на старт и вычитает
очки. Следовательно:

> `won = true` при любом нормальном завершении игры — игрок физически не может проиграть, он может
> только пройти хуже или лучше.

Единственные пути завершения, при которых `won` не равен `true`:

- игрок нажал платформенную кнопку «ВЫЙТИ» в слоте 3 нижней панели — тогда вызывается `onExit()`
  (не `onComplete`), результат вообще не формируется (см. `docs/platform.md` §1.3 — кнопкой владеет
  платформа, не игра);
- ничего больше. `onComplete({won: false})` игрой **не вызывается никогда**.

Отсюда практическое следствие для админки: `post_lose_dialogue_id` для игры на `three-mazes` можно
не заполнять — он недостижим. Ветвление идёт только по `style_dialogue_map`.

### 3.2 Подсчёт очков

```
score = Σ mazes[i].scorePerMaze  −  penaltyPerReset · resetsTotal
score = max(0, score)   // счёт не может уйти в минус (контракт требует целое >= 0)
```

- `scorePerMaze` задаётся **на каждый лабиринт отдельно** — третий (circular) сложнее первого и
  логично оценивается дороже. Начисляется в момент FINISH.
- `penaltyPerReset` — штраф за каждый сброс (каждый скример), суммарно по всей игре, без потолка,
  кроме общего клампа в ноль. Дефолт: 50.
- **Пробивание стен само по себе очки не отнимает.** Это принципиально: игра не оценивает стиль, она
  его фиксирует. `breaker` — не «плохое прохождение», а другой характер. Разница между стилями
  проявляется в сюжете (пост-диалог), а не в цифре.
- Косвенно `ghost` обычно даёт счёт не выше `breaker`: честный путь длиннее, дольше и даёт больше
  шансов задеть стену. Это осознанный баланс — игра не подталкивает ни к одному стилю.

### 3.3 Счётчик `wallsBroken`

`wallsBroken` — **сколько стен игрок сломал в тех прохождениях, которые засчитались**, то есть сумма
`wallsBrokenCurrentMaze` по трём финишированным лабиринтам.

Ключевое правило: при сбросе лабиринта его счётчик обнуляется. Считается только **финальное, успешное**
прохождение каждого лабиринта (подробнее — §6.4). Логика: если игрок сломал две стены, влетел в третью
и получил скример, а потом прошёл лабиринт чисто — он прошёл его чисто. Иначе одна неудачная попытка
навсегда лишала бы игрока возможности получить `ghost`, что превращало бы игру в «перезапусти всю
игру ради концовки» — худший вид фрустрации.

`totalBreakable` — сумма ломаемых стен по всем трём лабиринтам (по исходной, несломанной конфигурации).
Это знаменатель для админки/аналитики: `2 / 5` читается осмысленно, `2` — нет.

### 3.4 `details` и `styleTag`

```ts
callbacks.onComplete({
  score,
  won: true,
  details: {
    wallsBroken, // number, 0..totalBreakable
    totalBreakable, // number
    styleTag, // "ghost" | "breaker"
  },
});
```

Правило вычисления тега:

```ts
const styleTag = wallsBroken < breakerThreshold ? 'ghost' : 'breaker';
```

При `breakerThreshold = 1` (default) это ровно формулировка плана: `wallsBroken === 0` → `"ghost"`,
иначе → `"breaker"`. Параметр вынесен в конфиг на случай, если по итогам плейтеста окажется, что
случайный пролом одной стены не должен считаться сменой характера — тогда админ ставит `2`.

**Связь с платформой.** По `docs/platform.md` §3.3 при `won = true` платформа смотрит в
`style_dialogue_map` игры (хранится в `config_json`):

```json
"style_dialogue_map": { "ghost": 12, "breaker": 13 }
```

Если `details.styleTag` есть в карте — показывается диалог оттуда; иначе — обычный
`post_win_dialogue_id`. То есть админ может:

- заполнить обе ветки — полноценная развилка «призрак» / «крушитель»;
- заполнить одну (например, только `breaker`) — тогда «призраку» достанется общий пост-вин;
- не заполнять карту вовсе — игра будет работать, `details` просто уйдёт в статистику.

Игра **ничего не знает** про диалоги и не должна знать: её ответственность заканчивается на честном
`styleTag` в `details`.

Форма генерируется SchemaForm по JSON Schema draft-07 с расширениями `x-type` (см. базовый контракт).

### 4.4 Виджет-превью генератора

Отдельный кастомный виджет SchemaForm для группы `mazes[i]` (регистрируется по `x-type:
"maze-generator"` на объекте лабиринта). Устройство:

```
┌─ ЛАБИРИНТ 2 ────────────────────────────────────────┐
│  ТИП       [ hex ▾ ]     РАЗМЕР      [  8 ]          │
│  ПЛОТНОСТЬ [ 0.15 ]      SEED        [ 48211 ] [🎲]  │
│                                                      │
│  ┌──────────────────────┐   СТЕН:          312       │
│  │                      │   ЛОМАЕМЫХ:       9        │
│  │   canvas-превью      │   ЧЕСТНЫЙ ПУТЬ:  ЕСТЬ ✓    │
│  │   400×400            │   ДЛИНА ПУТИ:    1840 px   │
│  │                      │                            │
│  └──────────────────────┘   [ СГЕНЕРИРОВАТЬ ]        │
│                              МАСШТАБ [1.0]           │
│                              ОЧКИ    [ 100 ]         │
└──────────────────────────────────────────────────────┘
```

Поведение:

- Кнопка **«СГЕНЕРИРОВАТЬ»** вызывает `generateMaze(generatorParams)` — **тот же самый код из
  `engine.ts`**, который используется игрой и тестами. Не копия, не порт: админка импортирует функцию
  из пакета мини-игры. Это единственный способ гарантировать, что превью не разойдётся с рантаймом.
- Результат немедленно пишется в поля `walls` / `start` / `finish` формы и рисуется на canvas-превью
  ровно теми же цветами, что и в игре: неломаемые — `#5DE2D0`, ломаемые — янтарный пунктир `#E9A928`,
  старт — бирюзовый маркер, финиш — янтарный.
- **Детерминизм:** повторный клик «Сгенерировать» с тем же `seed` и теми же параметрами даёт
  идентичный результат. Чтобы получить другой лабиринт, надо изменить `seed` — для этого рядом кнопка
  «🎲» (перебросить сид случайным числом). Это делает работу админа воспроизводимой: понравившийся
  лабиринт достаточно записать как четвёрку (type, size, density, seed).
- Панель справа от превью показывает валидацию: число стен, число ломаемых, **наличие честного пути**
  (генератор не должен возвращать лабиринт без него — если индикатор красный, это баг, а не
  нормальный исход) и длину честного пути в пикселях (помогает оценить, не слишком ли короткий или
  длинный лабиринт вышел).
- Пока `walls` пуст, форма помечает лабиринт ошибкой валидации «не сгенерирован» — сохранить игру с
  пустым лабиринтом нельзя.

## 5. Реализация

Структура (по общей конвенции репозитория):

```
minigames/three-mazes/
  schema.json
  vite.config.ts
  src/
    engine.ts        # чистая логика, ноль DOM
    engine.test.ts   # vitest
    index.ts         # init/destroy, canvas, ввод, звук
```

### 5.1 `engine.ts` — чистые функции

Ни одного обращения к DOM, `window`, `Date.now()` или `Math.random()` — всё детерминировано и
тестируемо. Состав:

**Геометрия**

```ts
distancePointSegment(px, py, x1, y1, x2, y2): { dist: number; t: number; cx: number; cy: number }
```

Классическая проекция точки на отрезок с клампом `t ∈ [0,1]`. Возвращает расстояние, параметр и
ближайшую точку — из неё же берётся нормаль `n = normalize(p − c)`. Одна функция обслуживает все три
формы лабиринта.

**Физика**

```ts
stepPhysics(state, target, dt, params): { state, collision?: { wallIndex, n, speed } }
```

Внутри — расчёт числа субстепов (`≤3px`, `≤3` штук), интегрирование пружины с текущим множителем
жёсткости (`bounceRelax`), проверка всех стен на каждом субстепе, ранний выход при первой коллизии.
Возвращает новое состояние и, если было столкновение, — индекс стены, нормаль и модуль скорости на
момент удара.

**Классификация удара**

```ts
classifyHit(wall, n, v, params): 'break' | 'fail'
```

Ровно две проверки из §2.3. Отдельная функция, потому что это самая тюнингуемая (и самая
тестируемая) часть игры.

```ts
applyBounce(state, n, params): state
```

`v = n · max(bounceSpeed, 1.15|v|)`, взвод `bounceRelax` в 0.25 с таймером на `bounceDurationMs`,
выталкивание точки из стены.

**Генератор**

```ts
generateMaze(params: GeneratorParams): Maze
```

Общий алгоритм для всех трёх типов, различие — только в построении графа ячеек:

1. **Граф ячеек.** `square` — 4-связная сетка `size × size`; `hex` — 6-связная гексагональная сетка
   (offset-координаты); `circular` — кольца по `size` штук, в кольце `i` число секторов растёт с
   радиусом (примерно `6 + 4i`), соседство: по кольцу и между кольцами.
2. **Остовное дерево.** Итеративный DFS с seeded-ГПСЧ (`mulberry32(seed)` — 4 строки, не тянуть
   зависимость). Даёт идеальный лабиринт: между любыми двумя ячейками существует ровно один путь.
   Это и есть **гарантия честного пути** — по построению, а не проверкой постфактум.
3. **Старт/финиш.** Старт — ячейка в начале обхода; финиш — ячейка с максимальным расстоянием от
   старта по дереву (BFS). Так гарантированно получается длинный, содержательный маршрут, а не
   «два шага и всё».
4. **Стены → отрезки.** Все рёбра графа, не вошедшие в остов, материализуются как стены; плюс внешний
   контур. Для `circular` кольцевые стены разбиваются на полилинии по ~10° (§1.3).
5. **Ломаемые стены.** Из всех стен отбираются **кандидаты на срезку**: стена между двумя ячейками,
   расстояние между которыми **по дереву** больше порога (по умолчанию ≥ 6 шагов) — то есть пролом
   реально срезает крюк, а не открывает соседнюю клетку. Из кандидатов случайно (seeded) берётся доля
   `breakableDensity`. Дополнительный фильтр — **коридор напротив** (§6.5).
6. Возврат `{ walls, start, finish }` в координатах, нормализованных к квадрату (масштабирование под
   контейнер — задача `index.ts` с учётом `scale`).

**Прочее**

```ts
computeStyleTag(wallsBroken, breakerThreshold): 'ghost' | 'breaker'
computeScore(mazes, resets, penaltyPerReset): number
solvePath(maze): { x, y }[] | null   // BFS по открытым коридорам — для тестов и для админ-превью
```

### 5.2 `index.ts` — canvas и жизненный цикл

Отвечает за всё нечистое: DOM, `requestAnimationFrame`, ввод, звук, вызовы колбэков.

**Рендер** (60 FPS, всё в одном `<canvas>`, размер — по `container.getBoundingClientRect()` с учётом
`devicePixelRatio`):

| Слой             | Как рисуется                                                                                                                                                                                                                                                  |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Фон              | Заливка `#030B0C`, поверх — едва заметная техническая сетка `#0A3435` (шаг ~40px)                                                                                                                                                                             |
| Неломаемые стены | `strokeStyle = '#5DE2D0'`, `lineWidth = 2`, `lineCap = 'round'`, слабое свечение через `shadowBlur = 6` того же цвета. Контурный чертёж, без заливок                                                                                                          |
| Ломаемые стены   | `strokeStyle = '#E9A928'`, `setLineDash([6, 4])`, поверх — 2–3 коротких «трещины» (отрезки под случайными, но **детерминированными по индексу стены** углами), лёгкая пульсация альфы (период ~1.5с) — по `STYLE.md`, «активные области окрашивай в янтарный» |
| Сломанная стена  | Первые ~400 мс после пролома — осколки (4–6 коротких отрезков, разлетающихся с затуханием альфы), затем ничего                                                                                                                                                |
| Стартовая зона   | Круг `r = 24`, бирюзовый контур; в FROZEN — пульсирует янтарным (`#E9A928`) с периодом ~1с                                                                                                                                                                    |
| Финишная зона    | Круг `r = 24`, янтарный двойной контур, статичный                                                                                                                                                                                                             |
| Точка            | Круг `r = 6` `#D3DED5` с бирюзовым ореолом; при `                                                                                                                                                                                                             | v   | > breakMinSpeedRatio · followSpeed` ореол становится янтарным — **бесплатная и честная подсказка**, что скорости хватает для пролома |
| Скример          | Оверлей поверх всего: `drawImage(screamerImage)` на весь canvas, либо фолбэк-заливка `#F0713E` с затуханием                                                                                                                                                   |
| Mute             | Квадратная кнопка 32×32 в правом верхнем углу, тонкая рамка `#C8A878`, контурная иконка                                                                                                                                                                       |

Общий CRT-оверлей платформы (`STYLE.md`) лежит выше контейнера и рисуется платформой — игра его не
дублирует.

**Игровой цикл**

```ts
function frame(now: number) {
  const dt = Math.min((now - last) / 1000, 0.05); // dt-кап 50 мс, см. §6.2
  last = now;
  if (state.phase === 'ACTIVE') {
    /* stepPhysics → classifyHit → ... */
  }
  render(dt);
  raf = requestAnimationFrame(frame);
}
```

**Масштабирование.** Лабиринт приходит из конфига в нормализованных координатах; `index.ts` вписывает
его в контейнер по меньшей стороне с полями 5%, домножая на `mazes[i].scale`. Пересчёт — при
`ResizeObserver` на контейнере; при пересчёте позиция точки и цель масштабируются вместе с полем,
чтобы ресайз окна не убивал прохождение.

**Жизненный цикл.** `init` возвращает `{ destroy }`; `destroy` снимает `pointermove`/`pointerleave`,
`blur`/`visibilitychange`, `ResizeObserver`, отменяет `requestAnimationFrame`, чистит `container.innerHTML`.
Звук останавливает избирательно: `ambient` — всегда; одноразовые SFX (`live`) — только при выходе на
полпути, а после штатного финиша не трогает их, чтобы хвост `gameComplete` доиграл. `onComplete`
вызывается ровно один раз, после короткого fade-out (~300 мс по базовому контракту); флаг `finished`
защищает от повторного вызова.

### 5.3 Тесты (vitest)

Тестируется `engine.ts` — весь, целиком, потому что он чистый. `index.ts` не тестируется (DOM/canvas —
не окупается).

**Генератор — гарантия пути (главный тест):**

```ts
it.each([...seeds])('честный путь существует: %s', (type, size, density, seed) => {
  const maze = generateMaze({ type, size, breakableDensity: density, seed });
  expect(solvePath(maze)).not.toBeNull(); // BFS игнорирует ломаемые стены как проходимые? НЕТ:
  // считает их СТЕНАМИ — путь должен быть без проломов
});
```

Прогон по всем трём типам × размерам 3..20 × плотностям 0 / 0.15 / 0.5 / 1.0 × 50 сидов. Это ~1200
кейсов и секунды времени — дёшево и полностью закрывает главный риск игры («сгенерировался лабиринт,
который нельзя пройти честно»).

Дополнительно по генератору:

- **детерминизм**: два вызова с одним сидом дают идентичный JSON;
- **старт ≠ финиш** и расстояние между ними не меньше половины поля;
- `breakableDensity = 0` → ни одной ломаемой стены (стиль `breaker` физически невозможен);
- каждая ломаемая стена реально срезает: расстояние по дереву между её ячейками ≥ порога;
- у каждой ломаемой стены есть коридор напротив (§6.5) — проверяется рейкастом по нормали.

**Физика и коллизии:**

- `distancePointSegment` — на известных значениях, включая вырожденный отрезок (`x1==x2, y1==y2`) и
  проекцию за пределы отрезка (кламп `t`);
- **туннелирование**: точка с целью по ту сторону тонкой стены на максимальной скорости и `dt = 50мс`
  (худший случай) обязана дать коллизию, а не оказаться за стеной;
- **пружина не перелетает**: с нулевой начальной скоростью и целью на расстоянии 200px точка
  монотонно приближается и не пересекает цель ни на одном шаге (проверка критического демпфирования);
- **кап скорости**: ни на одном шаге `|v| > followSpeed`;
- `classifyHit` — таблица: лобовой быстрый удар в ломаемую → `break`; тот же удар в неломаемую →
  `fail`; удар под 41° при `breakAngleDeg = 40` → `fail`; лобовой на `0.54 · followSpeed` при пороге
  `0.55` → `fail`; граничные значения ровно на пороге → `break`;
- `applyBounce`: направление скорости после отскока совпадает с нормалью; модуль ≥ `bounceSpeed`;
  точка вытолкнута из стены (расстояние > `DOT_RADIUS`); `bounceRelax` восстанавливается до 1.0
  ровно за `bounceDurationMs`;
- **двойной слом**: при коллизии с двумя стенами на одном субстепе выбирается стена с минимальным
  расстоянием (§6.3);
- `computeStyleTag` / `computeScore` — таблица значений, включая `score < 0 → 0`.

## 6. Edge cases

### 6.1 `pointerleave` — заморозка цели

Курсор ушёл за пределы canvas → цель пружины **замораживается** в последней известной позиции.
Физика продолжает работать: точка доезжает до замороженной цели и останавливается. Мы намеренно **не**
ставим игру на паузу и **не** сбрасываем лабиринт: точка просто плавно тормозит там, где игрок её
оставил, и коллизии на этом торможении честно работают (если игрок ушёл мышью «сквозь» стену — точка
доедет до стены и получит скример; это справедливо, он сделал именно то движение).

При возврате курсора (`pointerenter`/`pointermove`) цель обновляется обычным образом. Отдельного
состояния для этого нет — это просто «цель перестала обновляться».

### 6.2 `blur` / `visibilitychange` — пауза и dt-кап

Потеря фокуса окна или сворачивание вкладки → **пауза**: физика не считается, `requestAnimationFrame`
продолжает крутиться (или останавливается — браузер и так его тормозит), звуки приглушаются, поверх
поля рисуется полупрозрачная панель «ПАУЗА» по `STYLE.md`. Возврат фокуса → снятие паузы **без**
восстановления в ACTIVE напрямую: если лабиринт был ACTIVE, он остаётся ACTIVE, но `last` сбрасывается
на текущий `now`, чтобы первый кадр после паузы не получил гигантский `dt`.

Независимо от паузы действует жёсткий **кап `dt = 50 мс`** в самом начале кадра:

```ts
const dt = Math.min((now - last) / 1000, 0.05);
```

Это страховка от «прыжка времени» (переключение вкладки, спящий режим, тормоза на слабой машине,
подключение внешнего монитора). Без него один кадр в 3 секунды переместил бы точку на 1800px сквозь
пол-лабиринта. С капом худший случай — 30px за кадр, что при 3 субстепах даёт шаг 10px: чуть больше
идеальных 3px, но всё ещё меньше диаметра точки, и туннелирование не происходит. Этот худший случай
явно покрыт тестом (§5.3).

### 6.3 Двойной слом за кадр

На одном субстепе точка может оказаться в пределах `DOT_RADIUS` сразу от двух стен — например, в углу
или в месте стыка ломаемой стены с неломаемой. Правило: **берётся только ближайшая стена** (минимум
`dist` по всем найденным). Обработка второй стены в этом кадре не производится вовсе; если после
отскока точка всё ещё пересекает вторую стену, это выяснится на следующем кадре штатным путём.

Практический смысл: в углу «ломаемая + неломаемая» игрок не может случайно сломать обе одним ударом,
и не может «проскочить» неломаемую за счёт того, что рядом оказалась ломаемая. Побочный эффект —
если неломаемая ближе, удар классифицируется как `fail`, что честно: игрок промахнулся.

### 6.4 Рестарт лабиринта сбрасывает только его счётчик

При сбросе (после скримера) восстанавливается **полное исходное состояние текущего лабиринта**:

- все сломанные в этой попытке стены возвращаются в список отрезков;
- `wallsBrokenCurrentMaze = 0`;
- точка удаляется, состояние → FROZEN.

Что **не** сбрасывается:

- `wallsBroken` уже пройденных лабиринтов (они зафиксированы на FINISH);
- накопленный `score` за пройденные лабиринты;
- счётчик `resetsTotal` (штрафы копятся честно, за всю игру).

То есть игрок может пройти первый лабиринт как «крушитель», а второй и третий — идеально; итоговый
`wallsBroken > 0` и `styleTag = "breaker"`. Но если он ломал стены и провалился, а с новой попытки
прошёл чисто — эти проломы не считаются. Считается только то, что он в итоге сделал.

### 6.5 Гарантии генератора: коридор напротив ломаемой стены

Ломаемая стена бесполезна и неприятна, если сразу за ней — другая стена: игрок пробивает, получает
отскок... в стену, и мгновенно ловит скример за то, что всё сделал правильно. Поэтому генератор
проверяет каждую стену-кандидата **рейкастом по нормали в обе стороны**: свободное расстояние с обеих
сторон должно быть не меньше `MIN_CLEARANCE` (по умолчанию 3 · `DOT_RADIUS` ≈ 18px, но не меньше
половины ширины ячейки). Кандидаты, не прошедшие проверку, отбрасываются до жеребьёвки по
`breakableDensity`.

Побочный эффект: при высокой `size` и низкой плотности ломаемых стен может оказаться меньше, чем
запрошено. Это допустимо — генератор возвращает сколько получилось, а виджет-превью честно показывает
итоговое число («ЛОМАЕМЫХ: 9»), чтобы админ мог поднять `breakableDensity` или сменить сид. Что
генератор **не** делает никогда — не ослабляет проверку ради выполнения квоты.

Две другие гарантии, обеспеченные по построению (§5.1, шаг 2 и 5): честный путь существует всегда
(остовное дерево связно), и каждая ломаемая стена реально является срезкой (расстояние по дереву между
её ячейками ≥ 6 шагов). Обе покрыты тестами.

### 6.6 Игрок вообще не двигает мышь

Никакого таймаута нет. Если курсор не заходит в стартовую зону — лабиринт вечно висит в FROZEN,
пульсируя янтарным маркером старта. Если курсор стоит внутри поля неподвижно — точка доезжает до него
и замирает. Игра не завершается сама, не показывает подсказок-нотификаций и не начисляет штрафов за
бездействие.

Это осознанное решение: игра, где цена ошибки — скример, обязана позволять игроку остановиться,
выдохнуть и собраться сколько угодно долго. Выход из зависшей сессии — платформенная кнопка «ВЫЙТИ»
в слоте 3 нижней панели (`onExit()`, `docs/platform.md` §1.3), которой владеет платформа, а не игра.

### 6.7 Прочее

- **Ресайз контейнера во время прохождения** — поле пересчитывается, позиция точки и цель
  масштабируются пропорционально. Коллизии на кадре ресайза пропускаются (один кадр без физики),
  чтобы пересчёт координат не породил ложное касание.
- **`config.muted = true`** — ни один звук не воспроизводится, включая скример. Визуальная часть
  скримера остаётся: он и без звука делает свою работу.
- **`screamerImage` не загрузился** (битый URL) — молча уходим в фолбэк «красная вспышка», игра не
  падает. Загрузка изображения — при `init`, лениво, но с `onerror`.
- **`mazes` содержит меньше трёх элементов** (кривой конфиг из админки) — игра проходит столько
  лабиринтов, сколько есть, и корректно завершается победой. Пустой `mazes` — немедленный
  `onComplete({score: 0, won: true, details: {wallsBroken: 0, totalBreakable: 0, styleTag: 'ghost'}})`.
  Валидация формы должна этого не допускать, но игра не имеет права зависнуть на плохом конфиге.
