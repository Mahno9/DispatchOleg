# Мини-игра 01: Обучалка (OnboardingFlow)

> **Статус:** платформенный сценарий, а не мини-игра из общего бандла `/minigames/`.
> Регистрируется в таблице `games` как system-игра с `is_tutorial = true` и собственным `schema.json`,
> чтобы тексты и ассеты настраивались в админке обычной SchemaForm. Из меты не запускается и в
> прогресс-баре не учитывается (см. `docs/platform.md` §6).

**Обоснование выбора.** Обучалке нужны три вещи, которых нет и не должно быть у изолированной мини-игры:
регистрация пользователя (сетевой запрос к платформенному API), запрос доступа к камере
(`getUserMedia` + singleton `camera.ts`) и переключение глобального UI (нижняя панель терминала, слот
камеры). Всё это — платформенные зоны ответственности, запрещённые контрактом мини-игры
(`minigame_contract.md`, раздел «Изоляция»). Если вынести обучалку в бандл, внутри бандла осталось бы
ноль игровой логики, а контракт пришлось бы дырявить. Поэтому логика живёт в `web/player` как компонент
`OnboardingFlow`, а от мини-игры берётся только `schema.json` — ради бесплатной админ-формы.

Стиль всех экранов — по `STYLE.md`: почти чёрный фон `#030B0C`, бирюзовый `#16A69B`, янтарные акценты
`#E9A928`, угловатые панели со срезанными углами, CRT-оверлей, узкий прописной шрифт.

---

## 1. Геймплей и состояния

Обучалка — линейный сценарий из пяти состояний. Он проходится один раз за всю жизнь аккаунта.

```
   ┌──────┐  скип / таймаут   ┌────────────┐  имя принято  ┌─────────────┐
   │ boot │ ────────────────▶ │ name-entry │ ────────────▶ │ camera-hint │
   └──────┘                   └────────────┘               └──────┬──────┘
                                    ▲                              │ getUserMedia OK
                                    │ 409 (имя занято)             ▼
                                    │                       ┌──────────┐
                                    └───────────────────────│ scanning │◀─┐
                                                            └─────┬────┘  │ повтор
                                            валидный QR обучалки  │       │ (ошибка)
                                                                  ▼       │
                                                            ┌─────────┐   │
                                                            │ success │───┘
                                                            └────┬────┘
                                                                 │ onboarded = true
                                                                 ▼
                                                               meta
```

Возврат назад по стрелкам вручную не предусмотрен: единственный «шаг назад» — возврат из `camera-hint`
в `name-entry` при отказе сервера по имени (см. §6.6) и остановка в `scanning` при ошибках камеры.

### 1.1 `boot` — заставка

**Рабочая область.** Полноэкранная имитация загрузки терминала: построчный вывод `bootText`
typewriter-эффектом (моноширинный шрифт, бирюзовый `#16A69B`), мигающий блок-курсор, усиленный CRT-эффект
(скан-линии + редкие цифровые помехи по `STYLE.md` «Эффект старого дисплея»). Строки появляются с
интервалом `bootLineDelayMs`; после последней строки — пауза `bootHoldMs` и автоматический переход.
В нижнем правом углу рабочей области — приглушённая подпись «ПРОБЕЛ — ПРОПУСТИТЬ».

**Нижняя панель.**

| Слот | Содержимое |
|---|---|
| 1 (камера) | Заглушка «NO SIGNAL» — контурная иконка камеры, статичный шум, янтарная статусная полоса (`docs/platform.md` §1.1) |
| 2 (контекст) | Строка статуса `СИСТЕМА: ИНИЦИАЛИЗАЦИЯ` без прогресс-бара |
| 3 (кнопка) | Пусто |

**Переход.** Автоматически по завершении вывода, либо немедленно по скипу (§2.1) → `name-entry`.

### 1.2 `name-entry` — ввод имени = регистрация

**Рабочая область.** Центральная панель-«досье» с двойной рамкой: заголовок из `namePrompt`, под ним одно
текстовое поле в стилистике терминала (подчёркивание вместо бордера, курсор-блок, ввод в верхнем
регистре — визуально; в БД имя сохраняется как введено), справа/снизу — квадратная кнопка «ПОДТВЕРДИТЬ».
Под полем — зарезервированная строка для ошибки валидации/сервера (оранжево-красный `#F0713E`, мигающий
круглый маркер), чтобы панель не «прыгала» при появлении ошибки.

Камера здесь **не запрашивается** — сначала регистрация, потом железо.

**Нижняя панель.**

| Слот | Содержимое |
|---|---|
| 1 | «NO SIGNAL» (без изменений) |
| 2 | `ИДЕНТИФИКАЦИЯ ОПЕРАТОРА` |
| 3 | Пусто (подтверждение — кнопкой внутри панели, чтобы фокус ввода и действие были рядом) |

**Переход.** `POST /api/auth/register` (find-or-create, §5.4) → успех → `camera-hint`. Ошибки — §6.6–6.8.
Во время запроса поле и кнопка заблокированы, кнопка показывает `…ПРОВЕРКА`.

### 1.3 `camera-hint` — подсказка про коробку

**Рабочая область.** Двухколоночная панель:
- слева — изображение `qrHintImage` (фото коробки с QR-кодом) в рамке-«досье» с угловыми маркерами;
  если ассет не задан — вместо фото контурная иконка-плейсхолдер QR, панель не ломается;
- справа — текст `qrHintText` и крупная кнопка **«ВКЛЮЧИТЬ КАМЕРУ»** (янтарная рамка, активное состояние
  по `STYLE.md`, короткий импульс свечения при наведении).

Это единственная точка, где запрашивается доступ к камере, и он запрашивается **по клику** — браузеры
показывают permission-prompt только в ответ на жест пользователя, а спонтанный prompt на заставке
выглядит как атака и чаще получает «Блокировать».

**Нижняя панель.**

| Слот | Содержимое |
|---|---|
| 1 | «NO SIGNAL» — визуально это и есть «то, что надо починить» |
| 2 | `ТРЕБУЕТСЯ ВИДЕОКАНАЛ` |
| 3 | Пусто |

**Переход.** Клик → `camera.acquire()` → успех → `scanning`. Отказ/ошибка — остаёмся здесь с текстом
ошибки и кнопкой повтора (§6.1–6.3).

### 1.4 `scanning` — сканирование QR

**Рабочая область.** Видео с камеры на весь центр + оверлей-прицел: угловые скобки рамки (бирюзовые),
бегущая горизонтальная скан-линия (анимация по `STYLE.md` «движение сканирующей линии»), затемнение вне
рамки. Под рамкой — короткая подсказка `qrHintText` (сокращённая до одной строки) или статичное
«НАВЕДИТЕ КАМЕРУ НА КОД». При неопознанном коде поверх рамки на `scanFailFlashMs` вспыхивает оранжевая
плашка `scanFailText` — сканирование при этом не останавливается (§6.4).

**Нижняя панель.**

| Слот | Содержимое |
|---|---|
| 1 | **Первое включение живой камеры**: панель выезжает сдвигом (`STYLE.md` «появление панели через сдвиг», 180 мс) и показывает `<video>` из `camera.ts`. Ровно тот же стрим, что в рабочей области — второго `getUserMedia` нет (`docs/qr-flow.md` §3.3) |
| 2 | `ПОИСК КОДА…` + бесконечный «сканирующий» индикатор (не процентный — прогресс неизвестен) |
| 3 | Пусто. Кнопка **«ПРОПУСТИТЬ»** появляется здесь только при `allowSkipScan = true` (§2.4) |

> Проектное решение: камера-панель слота 1 включается уже на `scanning`, а не после успеха — игрок должен
> видеть, что канал жив, пока целится. Формулировка плана «камера-панель выезжает» относится к моменту
> получения стрима; на `success` панель уже на месте и просто остаётся.

**Переход.** Декод → `POST /api/qr/verify` → `ok: true` и `gameId` принадлежит игре с `is_tutorial = true`
→ `success`. Любой другой результат — §6.4.

### 1.5 `success` — успех

**Рабочая область.** Короткий (≈`successHoldMs`) экран подтверждения: `successText` крупным прописным
шрифтом на бирюзовой статусной полосе, поверх — импульс свечения и однократный цифровой сбой (glitch),
затем затемнение и передача управления мете.

**Нижняя панель.**

| Слот | Содержимое |
|---|---|
| 1 | Живое видео (уже выехало на `scanning`, остаётся навсегда) |
| 2 | Переключается на мета-прогресс `0 / M ИГР ПРОЙДЕНО` вместе с переходом в meta |
| 3 | Появляется кнопка **START** |

**Переход.** `onboarded = true` в локальном стейте → sync (§3) → экран `meta` (`docs/platform.md` §2.2).
`OnboardingFlow` размонтируется; нижняя панель при этом не размонтируется — она живёт уровнем выше
(`docs/platform.md` §1).

## 2. Управление

Ввода мышью/клавиатурой минимум: обучалку проходят один раз и в первый запуск, любое «спрятанное»
управление здесь недопустимо.

### 2.1 Скип BOOT-заставки

- **Клавиши:** `Space`, `Enter`, `Esc`.
- **Мышь/тач:** клик/тап по любой точке рабочей области.
- Скип мгновенный, без анимации доигрывания: заставка декоративна, повторный запуск игры не предусмотрен,
  так что уважение к нетерпеливому игроку важнее драматургии.
- Подсказка «ПРОБЕЛ — ПРОПУСТИТЬ» появляется через `bootSkipHintMs` после старта (чтобы не спойлерить
  скип в первую же секунду и не портить эффект тем, кто хочет посмотреть).

### 2.2 Ввод имени

- Одно поле `<input type="text">` с автофокусом при входе в состояние.
- Подтверждение — `Enter` в поле **или** клик по кнопке «ПОДТВЕРДИТЬ». Оба пути ведут в один обработчик.
- Клиентская валидация до отправки: `trim()`, длина 2–24 символа, запрещены управляющие символы; при
  нарушении кнопка неактивна, а под полем — подсказка (§6.7).
- Во время запроса — `disabled` на поле и кнопке (защита от двойного `Enter`, §6.8).
- Пробелы по краям срезаются, внутренние сохраняются («ОЛЕГ ДИСПЕТЧЕР» — валидное имя).

### 2.3 «ВКЛЮЧИТЬ КАМЕРУ»

- Один клик по кнопке. Клавиатурный эквивалент — `Enter`/`Space` на сфокусированной кнопке (кнопка —
  настоящий `<button>`, фокус видим бирюзовой рамкой: базовая доступность не приносится в жертву стилю).
- Кнопка переходит в состояние `…ЗАПРОС ДОСТУПА` и `disabled` на время промиса `getUserMedia`
  (§6.9 про двойной клик).
- После ошибки кнопка возвращается в активное состояние с подписью **«ПОВТОРИТЬ»**.

### 2.4 `allowSkipScan` — аварийный рычаг

Флаг из `schema.json`, по умолчанию `false`. Нужен не игроку, а тем, кто проводит мероприятие:

- **демонстрация без коробки** (показ платформы там, где физических QR нет);
- **сломанная/отсутствующая камера** на конкретном ноутбуке — чтобы игрок не застрял навсегда;
- **отладка** меты и последующих экранов без прохождения обучалки каждый раз.

Активация:
1. Админ включает чекбокс в карточке system-игры обучалки (вкладка «Игры»).
2. При `allowSkipScan = true` в слоте 3 нижней панели на состояниях `camera-hint` и `scanning`
   появляется кнопка **«ПРОПУСТИТЬ»** (оранжевая рамка — опасное/служебное действие по `STYLE.md`).
3. Клик по ней ведёт напрямую в `success` с той же записью `onboarded = true`, но **без** обязательного
   получения стрима: если камеры нет, слот 1 остаётся в «NO SIGNAL» с кнопкой «ПЕРЕПОДКЛЮЧИТЬ»
   (`docs/platform.md` §1.1), и игрок сможет включить камеру позже, на экране `qr-scan`.

Никаких секретных комбинаций клавиш: скрытый чит-код — это лишний код и лишний способ выстрелить в ногу
на публичном мероприятии. Рычаг переключается в админке и виден в UI, когда включён.

## 3. Победа/пенальти

Классических `score`/`lives` здесь нет — это не мини-игра, а сценарий инициализации.

**Что считается завершением.** Достижение состояния `success`, то есть выполнены оба условия:
1. пользователь зарегистрирован (есть `users.id`, сессия установлена);
2. успешно верифицирован QR обучалки **или** сработал `allowSkipScan` (§2.4).

**Как фиксируется.** Флаг `onboarded` живёт в двух местах, оба обязательны:

| Место | Кто пишет | Зачем |
|---|---|---|
| `users.onboarded` (BOOLEAN) | сервер, в момент успешной верификации QR обучалки | «Жёсткий» признак: не теряется при очистке браузера |
| `game_states.payload.onboarded` | клиент, через обычный offline-sync (`docs/platform.md` §6) | Позволяет решить, показывать ли `OnboardingFlow`, ещё до ответа сети |

Порядок записи: клиент выставляет `onboarded = true` в локальном стейте, обновляет `client_updated_at` и
уходит в `meta` **не дожидаясь** ответа sync — сеть не должна держать игрока на экране успеха. Sync
догоняет в фоне по обычным правилам client-authoritative merge.

Запись `gameResults[<tutorialGameId>]` **не создаётся**: обучалка исключена из прогресса
(`is_tutorial = true`, см. `docs/platform.md` §6 — мета-прогресс считается только по `is_tutorial = false`),
и создавать для неё псевдо-результат означало бы засорять статистику игроков.

**Пенальти нет.** Ошибочные действия ничего не стоят: неопознанный QR, отказ в доступе к камере, занятое
имя — всё это возвращает игрока на тот же шаг с текстом ошибки и возможностью повторить неограниченное
число раз. Счётчиков попыток нет ни локально, ни на сервере — единственный «счётчик» здесь дебаунс
повторных декодов (§6.4), и он про нагрузку, а не про наказание.

**Повторное прохождение.** Не предусмотрено для игрока. Админ может сбросить `onboarded` во вкладке
«Игроки» (сброс прогресса) — тогда при следующем запуске `OnboardingFlow` покажется снова, начиная с шага
`scanning` (имя уже есть, §6.5).

## 4. Настройки админки (`schema.json`)

Файл лежит рядом с обучалкой как у обычной игры, чтобы админка отрисовала форму без спецкода:
`web/player/src/onboarding/schema.json` (регистрируется под `minigame_id = "onboarding"`).
Расширения `x-type` — по `minigame_contract.md`.

| Поле | Тип | `x-type` | Описание | Дефолт |
|---|---|---|---|---|
| `bootText` | `string` (multiline) | — | Текст BOOT-заставки; каждая строка выводится отдельно typewriter-эффектом | `ДИСПЕТЧЕРСКИЙ ТЕРМИНАЛ ОЛЕГ v1.7\nПРОВЕРКА ПИТАНИЯ......... OK\nПРОВЕРКА ПАМЯТИ.......... OK\nВИДЕОКАНАЛ............... НЕ НАЙДЕН\nБАЗА ОПЕРАТОРОВ.......... OK\nОЖИДАНИЕ ИДЕНТИФИКАЦИИ` |
| `namePrompt` | `string` | — | Заголовок над полем ввода имени | `ПРЕДСТАВЬТЕСЬ, ОПЕРАТОР` |
| `qrHintText` | `string` (multiline) | — | Подсказка на экране `camera-hint` | `НА КОРОБКЕ НАПЕЧАТАН СЛУЖЕБНЫЙ КОД.\nВКЛЮЧИТЕ КАМЕРУ И ПОКАЖИТЕ ЕГО ТЕРМИНАЛУ.` |
| `qrHintImage` | `string` | `asset:image` | Фото коробки с QR-кодом — что именно искать в реальном мире | *(пусто — рисуется контурный плейсхолдер)* |
| `scanFailText` | `string` | — | Вспышка при декоде чужого/неопознанного QR | `КОД НЕ ОПОЗНАН` |
| `noCameraText` | `string` | — | Камера не найдена (`NotFoundError`/`OverconstrainedError`) | `ВИДЕОУСТРОЙСТВО НЕ ОБНАРУЖЕНО. ПОДКЛЮЧИТЕ КАМЕРУ И ПОВТОРИТЕ.` |
| `deniedText` | `string` | — | Доступ запрещён пользователем или политикой (`NotAllowedError`/`SecurityError`) | `ДОСТУП К ВИДЕОКАНАЛУ ОТКЛОНЁН. РАЗРЕШИТЕ КАМЕРУ В НАСТРОЙКАХ БРАУЗЕРА И ПОВТОРИТЕ.` |
| `busyCameraText` | `string` | — | Камера занята другим приложением (`NotReadableError`/`AbortError`) | `ВИДЕОКАНАЛ ЗАНЯТ ДРУГОЙ ПРОГРАММОЙ. ЗАКРОЙТЕ ЕЁ И ПОВТОРИТЕ.` |
| `successText` | `string` | — | Экран успеха | `ОПЕРАТОР ПОДКЛЮЧЁН. ДОБРО ПОЖАЛОВАТЬ В СМЕНУ.` |
| `allowSkipScan` | `boolean` | — | Аварийный рычаг: кнопка «ПРОПУСТИТЬ» на `camera-hint`/`scanning` (§2.4) | `false` |
| `bootLineDelayMs` | `integer` | — | Пауза между строками BOOT (0 — вывести всё сразу) | `320` |
| `bootHoldMs` | `integer` | — | Пауза после последней строки перед авто-переходом | `900` |
| `bootSkipHintMs` | `integer` | — | Через сколько показать подсказку о скипе | `1500` |
| `scanFailFlashMs` | `integer` | — | Длительность вспышки `scanFailText` | `1200` |
| `successHoldMs` | `integer` | — | Длительность экрана успеха до перехода в meta | `1800` |
| `nameMinLength` | `integer` | — | Минимальная длина имени (валидация клиента и сервера) | `2` |
| `nameMaxLength` | `integer` | — | Максимальная длина имени | `24` |
| `bootSound` | `WeightedAudio[]` | `asset:audio` | Звук загрузки терминала (гудение/щелчки реле) | *(пусто)* |
| `scanSuccessSound` | `WeightedAudio[]` | `asset:audio` | Звук успешного распознавания кода | *(пусто)* |
| `scanFailSound` | `WeightedAudio[]` | `asset:audio` | Звук отказа | *(пусто)* |

`required`: `bootText`, `namePrompt`, `qrHintText`, `scanFailText`, `noCameraText`, `deniedText`,
`busyCameraText`, `successText`.

Заметки:
- `busyCameraText` добавлен сверх списка полей из плана: план перечисляет `NotReadableError` в edge cases
  как случай со «своим текстом», а свободного поля под него в списке схемы не было — иначе его пришлось бы
  хардкодить.
- Звуки — `asset:audio` (взвешенный список, `pickSound(val)` по `minigame_contract.md`), все опциональные;
  глобальный mute платформы применяется так же, как к мини-играм. Пустой список = тишина, отдельного флага
  «без звука» не нужно.
- Все таймауты вынесены в схему, потому что реальный темп чтения на мероприятии подбирается на месте, а не
  в коде: BOOT, который смотрится идеально у разработчика, у очереди из десяти человек слишком длинный.

## 5. Реализация

### 5.1 Где живёт

```
web/player/src/onboarding/
  OnboardingFlow.tsx     # state machine + рендер состояний
  schema.json            # конфиг для админки (§4)
  steps/                 # BootScreen, NameEntry, CameraHint, Scanning, SuccessScreen
```

Это обычные React/TS-компоненты `web/player`, а **не** бандл в `/minigames/`: у них есть доступ к
платформенным сторам, к `camera.ts`, к API-клиенту и к нижней панели — всё то, что мини-игре запрещено
контрактом. Никакого `init(container, config, callbacks)` здесь нет и не должно быть.

От «мини-игры» остаётся только строка в `games` (`minigame_id = "onboarding"`, `is_tutorial = true`,
`required_game_ids = []`) и `schema.json`, который админка находит по общему механизму и рисует форму.
`config_json` этой строки — источник всех текстов обучалки; на старте приложения он приходит вместе с
bootstrap-данными платформы.

### 5.2 Когда показывается

В корневом `Terminal` (`docs/platform.md` §2): если `state.onboarded !== true` — рендерится
`OnboardingFlow` вместо стейт-машины экранов; иначе — обычный роутинг `meta → qr-scan → …`.
Проверка идёт по **локальному** стейту (мгновенно, без ожидания сети), который при первом запуске на
устройстве догружается с сервера (`users.onboarded` + `game_states.payload`) — см. §6.5 про возобновление.

Нижняя панель `BottomBar` монтируется **выше** этой развилки и живёт всё время работы приложения. Обучалка
управляет слотами через тот же проп-интерфейс, что и остальные экраны, — отдельного «режима панели для
обучалки» не заводится.

### 5.3 Камера и сканер

- `camera.ts` (singleton, `docs/qr-flow.md` §3.3) — единственный владелец `MediaStream`. Обучалка первой
  вызывает его `acquire()` по клику на «ВКЛЮЧИТЬ КАМЕРУ»; все последующие потребители (`CameraPanel`,
  `QrScanner` на экране `qr-scan`) переиспользуют тот же стрим без второго permission-prompt.
- `QrScanner` (`docs/qr-flow.md` §3) используется как есть: `BarcodeDetector` → фолбэк `jsQR` через
  динамический `import()`. Обучалка подписывается на `onDecode(text)` и шлёт `POST /api/qr/verify`.
  Своего декодера у обучалки нет.
- Ошибки `getUserMedia` `QrScanner` прокидывает наверх (`docs/qr-flow.md` §6) — их разбор и тексты —
  зона обучалки (§6.1–6.3).
- При уходе из `scanning` вызывается только `stop()` цикла декодирования; трек камеры не останавливается —
  он нужен слоту 1 нижней панели.

### 5.4 Регистрация

```
POST /api/auth/register
  { "name": "Олег" }
→ 200 { "userId": 12, "name": "Олег", "onboarded": false }   // сессионная кука ставится сервером
→ 409 { "error": "name_taken" }
→ 400 { "error": "invalid_name" }
```

Find-or-create по имени, без пароля — та же модель, что в GameService: имя это идентификатор оператора, а
не секрет. Сервер нормализует имя (`trim`, схлопывание внутренних пробелов) и ищет по
`name UNIQUE COLLATE NOCASE` (`docs/platform.md` §4). Валидация длины дублируется на сервере — клиентская
проверка (§2.2) это UX, а не граница доверия.

Про 409: «find-or-create» и «имя занято» уживаются потому, что занятость определяется не самим фактом
существования записи, а привязкой её к **другому устройству/сессии**. Найденная свободная запись
переиспользуется (игрок вернулся с того же ноутбука, или админ заранее завёл оператора); запись, за которой
уже закреплена активная сессия другого устройства, отдаёт 409 и просит выбрать другое имя (§6.6). Конкретное
правило «занятости» — реализационная деталь фазы кодирования; на уровне контракта важен код ответа и текст.

### 5.5 State machine

Состояние потока — локальный `useReducer` внутри `OnboardingFlow` (в глобальный стор оно не выносится:
никто снаружи о шагах обучалки знать не должен):

```ts
type OnboardingState =
  | { step: 'boot' }
  | { step: 'name-entry'; error?: string; pending?: boolean }
  | { step: 'camera-hint'; error?: string; pending?: boolean }
  | { step: 'scanning'; flash?: string }
  | { step: 'success' }
```

Переходы — ровно те, что в диаграмме §1: `boot → name-entry → camera-hint → scanning → success`, плюс
`camera-hint → name-entry` при 409 и петли-повторы внутри `camera-hint`/`scanning`. Все асинхронные
операции (`register`, `acquire`, `verify`) снимают `pending` в `finally`, чтобы отказ сети не оставлял
кнопку залипшей навсегда.

## 6. Edge cases

### 6.1 `NotFoundError` / `OverconstrainedError` — камеры нет

**Когда.** На ноутбуке нет камеры, она отключена в диспетчере устройств, или заклеена/выключена аппаратным
переключателем так, что устройство не перечисляется.

**UX.** Остаёмся на `camera-hint`. Под кнопкой появляется панель ошибки: оранжево-красная рамка `#F0713E`,
мигающий круглый маркер, текст `noCameraText`. Кнопка меняет подпись на **«ПОВТОРИТЬ»** и остаётся
активной — игрок может подключить USB-камеру и нажать снова, перезагрузка страницы не нужна.
Если `allowSkipScan = true`, рядом видна кнопка «ПРОПУСТИТЬ» (§2.4) — на практике именно этот сценарий
и есть основная причина существования рычага.

### 6.2 `NotAllowedError` / `SecurityError` — доступ запрещён

**Когда.** Игрок нажал «Блокировать» в permission-prompt, либо сайт открыт по `http://` не на localhost
(браузер не даёт `getUserMedia` в небезопасном контексте), либо доступ запрещён политикой.

**UX.** Текст `deniedText` + вторая строка мелким приглушённым шрифтом: «ЗНАЧОК КАМЕРЫ В АДРЕСНОЙ СТРОКЕ →
РАЗРЕШИТЬ». Кнопка «ПОВТОРИТЬ» активна, но с честной оговоркой: после явного «Блокировать» браузер не
покажет prompt повторно, пока разрешение не изменят в настройках сайта — поэтому подсказка про значок
обязательна, иначе игрок будет бесконечно жать кнопку, на которую браузер молча отвечает тем же отказом.

### 6.3 `NotReadableError` / `AbortError` — камера занята

**Когда.** Камеру держит Zoom/Skype/OBS или другая вкладка.

**UX.** Текст `busyCameraText`, кнопка «ПОВТОРИТЬ». Это самая «чинимая» ошибка: закрыть программу и нажать
кнопку. Никакого автоповтора по таймеру — фоновые дёрганья `getUserMedia` создают гонки с чужим
приложением и мигание индикатора камеры.

### 6.4 Чужой QR в кадре

**Когда.** В кадр попал сторонний QR (визитка, реклама на упаковке), либо QR другой игры платформы,
отсканированный на этапе обучалки.

**UX.** Поверх рамки-прицела вспыхивает `scanFailText` («КОД НЕ ОПОЗНАН») на `scanFailFlashMs`, играет
`scanFailSound`. Сканирование **не останавливается** — в отличие от экрана `qr-scan`
(`docs/qr-flow.md` §5), где отказ выводит на отдельный экран с кнопкой «ОК». Причина различия: на обучалке
игрок ещё не умеет пользоваться сканером и физически водит коробкой перед камерой; выкидывать его в
модальный отказ на каждый неудачный кадр — верный способ сорвать первый контакт.

**Дебаунс.** Один и тот же декодированный текст не отправляется на `/api/qr/verify` повторно, пока код не
пропадёт из кадра или не пройдёт интервал (`docs/qr-flow.md` §5.1). Дополнительно: строки, не начинающиеся
с `dispatch:`, отсеиваются локально, без обращения к серверу, но вспышку `scanFailText` показывают —
игроку нужна обратная связь «я вижу код, но он не тот», серверу — нет.

**QR не той игры.** Валидный по подписи код обычной (не tutorial) игры на этапе обучалки трактуется так же:
`scanFailText`, продолжаем сканировать. Пускать в игру мимо обучалки нельзя — камера и регистрация ещё не
доведены до конца, а мета не показана.

### 6.5 Перезагрузка посреди потока

Возобновление — **по серверному состоянию**, не по локальному черновику. При старте приложение спрашивает
`GET /api/auth/me` (или общий bootstrap-эндпоинт) и решает:

| Серверное состояние | Куда попадает игрок |
|---|---|
| Нет сессии / пользователь не найден | `boot` (полный поток с начала) |
| Есть пользователь, `onboarded = false` | Сразу `scanning`, минуя `boot`, `name-entry` и `camera-hint`… |
| Есть пользователь, `onboarded = true` | `meta` — `OnboardingFlow` не монтируется вовсе |

…с одной оговоркой: при возобновлении на `scanning` стрим камеры после перезагрузки страницы потерян, и
`getUserMedia` снова требует жеста пользователя. Поэтому фактически показывается `camera-hint`
с уже включённым «ПОВТОРИТЬ»-семантикой кнопки; если браузер помнит выданное разрешение, клик проходит без
prompt и игрок оказывается в `scanning` за одно нажатие. Имя повторно не спрашивается никогда — это ключевое
требование плана: игрок, перезагрузивший вкладку, не должен думать, что придумал имя зря.

Прогресс внутри `boot`/`name-entry` не сохраняется — там нечего сохранять.

### 6.6 Имя занято (409)

**UX.** Возврат (или сохранение) на `name-entry`: поле не очищается — игроку удобнее дописать символ,
чем набирать заново; текст в поле выделяется целиком, чтобы одним нажатием стереть. Под полем —
«ИМЯ УЖЕ ЗАНЯТО. ВЫБЕРИТЕ ДРУГОЕ.» в оранжево-красном. Кнопка снова активна.
Никаких автоматических предложений вида «Олег2» — на мероприятии имя это то, как оператора будут звать
вслух, и подставлять его молча за игрока неправильно.

### 6.7 Слишком короткое / длинное / пустое имя

- Пустое или короче `nameMinLength` (после `trim`) — кнопка «ПОДТВЕРДИТЬ» неактивна, под полем приглушённая
  подсказка «МИНИМУМ 2 СИМВОЛА». Ошибка не мигает тревожным цветом: это ещё не ошибка, а недобор.
- Длиннее `nameMaxLength` — ввод обрезается на уровне `maxLength` у `<input>`, показывается счётчик
  `24/24` приглушённым шрифтом. Молча резать по факту отправки нельзя — игрок не поймёт, почему в мете
  висит обрубок.
- Только пробелы/управляющие символы — трактуется как пустое.
- Сервер повторяет обе проверки и отвечает `400 invalid_name`; клиент показывает тот же текст, что и при
  локальной валидации, чтобы не плодить формулировок.

### 6.8 Разрыв сети при регистрации

**Когда.** `POST /api/auth/register` отвалился по таймауту/`fetch` reject (Wi-Fi мероприятия, спящий
сервер).

**UX.** Остаёмся на `name-entry`, поле разблокируется, текст ошибки «СВЯЗЬ С ЦЕНТРОМ ПОТЕРЯНА. ПОВТОРИТЕ.»,
кнопка меняет подпись на «ПОВТОРИТЬ». Автоматических ретраев нет: регистрация не идемпотентна с точки
зрения игрока (он ждёт результата здесь и сейчас), а тихий ретрай с той же формой скрывает от него, что
что-то не так. Повторная отправка того же имени безопасна — find-or-create вернёт ту же запись.

Отдельно: если запрос **успел** дойти, а ответ потерялся — повторная отправка того же имени даст того же
пользователя (find-or-create), а не 409, потому что «занятость» определяется чужой активной сессией
(§5.4), а не самим фактом существования записи.

### 6.9 Двойной клик по «ВКЛЮЧИТЬ КАМЕРУ»

Кнопка переводится в `disabled` синхронно в обработчике, до `await`. Дополнительно `camera.ts` кэширует
промис `getUserMedia`: параллельные вызовы `acquire()` получают один и тот же промис и один и тот же
стрим — второго permission-prompt и второго трека не возникает даже при гонке
(`docs/qr-flow.md` §3.3). Это свойство singleton'а, а не обучалки — обучалка на него опирается.

### 6.10 Камера пропала во время `scanning`

Трек выдал `ended` (USB-камеру выдернули, крышка ноутбука закрыта, устройство перехвачено другой
программой). Рабочая область показывает `busyCameraText`/`noCameraText` (по причине, если она известна из
события) поверх замершего кадра, слот 1 переходит в «SIGNAL LOST» с кнопкой «ПЕРЕПОДКЛЮЧИТЬ»
(`docs/platform.md` §1.1), кнопка «ПОВТОРИТЬ» возвращает на `camera-hint`.

### 6.11 Отказ `/api/qr/verify` по сети

Декод прошёл, но запрос верификации не дошёл. Показывается вспышка «НЕТ СВЯЗИ С ЦЕНТРОМ» (по стилю — как
`scanFailText`, но своим текстом), сканирование продолжается: следующий же кадр с тем же кодом (после
истечения интервала дебаунса) отправит запрос заново. Здесь автоповтор уместен — в отличие от §6.8, игрок
физически держит код перед камерой и повтор для него бесплатен.

### 6.12 `BarcodeDetector` недоступен и `jsQR` не загрузился

Динамический `import('jsqr')` упал (нет сети, битый кэш). Показывается вспышка
«МОДУЛЬ РАСПОЗНАВАНИЯ НЕ ЗАГРУЖЕН», сканирование останавливается, кнопка «ПОВТОРИТЬ» пытается загрузить
модуль снова. При `allowSkipScan = true` доступна кнопка «ПРОПУСТИТЬ». Это единственный случай, когда
обучалка может оказаться непроходимой без рычага — поэтому фолбэк-путь стоит держать в кэше
service worker'а вместе с основным бандлом.

### 6.13 Два устройства с одним именем

Второй ноутбук вводит имя, уже привязанное к активной сессии первого → `409` → §6.6. Иначе прогресс двух
игроков склеился бы в одно `game_states.payload`, а client-authoritative merge (`docs/platform.md` §6)
молча затёр бы прогресс того, кто синхронизировался раньше.

### 6.14 Ассет `qrHintImage` не загрузился

Битый URL или удалённый ассет: `onError` у `<img>` переключает панель на контурный плейсхолдер-QR, текст
`qrHintText` и кнопка остаются на месте. Обучалка не должна вставать из-за картинки.

### 6.15 Очень длинный `bootText`

Текст из админки длиннее рабочей области: блок BOOT скроллится к последней строке автоматически
(прокрутка внутри панели, страница целиком не скроллится — `docs/platform.md` §1, layout фиксирован).
Скип по-прежнему доступен и решает проблему за одно нажатие.
