# Мини-игра 03: task-sort (сортировка задач диспетчера)

Идентификатор: `task-sort`. Директория: `minigames/task-sort/`.
Базовый контракт — `minigame_contract.md` (GameService), расширения (`onProgress`, `details`) — `docs/platform.md` §3.
Оформление — `STYLE.md` (карточки-досье, цветные статусные полосы, угловатые панели, CRT-оверлей платформы).

Технически: **DOM + pointer-events**, без canvas, без HTML5 Drag&Drop. Чистая логика зачёта вынесена в
`src/engine.ts` и покрыта vitest. Оценка трудоёмкости — **~2 дня**.

Суть: Олег принимает смену. На стол падает стопка входящих тикетов диспетчерской. Часть из них — его
собственные активные задачи, их надо выстроить в очередь по срочности. Остальное — чужие задачи и
уже закрытые тикеты, им место в шреддере. Приоритет на карточке есть, но заштрихован — его надо
**запросить** наведением и подождать, пока поле догрузится (§1.2).

## 1. Геймплей и состояния

### 1.1 Три зоны

Рабочая область делится на три вертикальные (на широком экране — колонки, на узком — стек) зоны-панели.
Каждая зона — угловатая панель с двойной рамкой и заголовком в верхнем регистре узким шрифтом.

| Зона | Заголовок | Назначение | Порядок значим |
|---|---|---|---|
| Входящие | `ВХОДЯЩИЕ` | Стартовая стопка всех задач в перемешанном порядке | Нет |
| Очередь | `ОЧЕРЕДЬ ОЛЕГА` (подставляется `playerName`) | Упорядоченный список слотов: верх = самое срочное | **Да** |
| Архив | `АРХИВ // ШРЕДДЕР` | Всё, что не касается смены игрока | Нет |

- **ВХОДЯЩИЕ** — карточки лежат в случайном (детерминированно перемешанном при `init`) порядке. Зона
  визуально «стопка на столе»: карточки вплотную, лёгкое смещение по вертикали, без сортировки.
- **ОЧЕРЕДЬ ОЛЕГА** — нумерованные слоты `01`, `02`, `03`… сверху вниз. Номер слота рисуется моноширинным
  приглушённым текстом слева от карточки. Сверху зоны — подпись-напоминание `↑ СРОЧНОЕ` / `↓ МОЖЕТ ПОДОЖДАТЬ`
  тонким приглушённым шрифтом. Количество слотов не фиксировано — зона растёт по мере наполнения.
- **АРХИВ** — визуально шреддер: заголовок на оранжевой полосе, зубчатая (clip-path) верхняя кромка панели,
  карточки внутри отрисованы приглушённо (opacity ~0.55, десатурация). Это **не** удаление: карточку
  можно вытащить обратно во ВХОДЯЩИЕ или сразу в ОЧЕРЕДЬ в любой момент до подтверждения смены.

### 1.2 Карточка-досье

Карточка строится по разделу «Карточки» из `STYLE.md`. Что на ней **есть**:

| Элемент | Где | Содержание |
|---|---|---|
| Полоса статуса | Верхняя кромка, во всю ширину | `АКТИВНО` (бирюзовый `#16A69B`) либо `ВЫПОЛНЕНО` (приглушённый `#759C96`) |
| Бейдж исполнителя | Правый верхний угол, поверх полосы | Имя: `ОЛЕГ` — янтарный `#E9A928`; `МАРИНА` / `ТИМУР` — приглушённый серо-бирюзовый |
| Тело карточки | Центр | Текст задачи, 1–2 предложения, узкий шрифт, основной цвет `#D3DED5` |
| Номер тикета | Левый нижний угол | Моноширинный псевдо-id вида `TK-0417` (генерируется из индекса, чисто декоративный) |
| Слот приоритета | Там же, после номера тикета | Заштрихованная плашка (та же диагональная штриховка, что у ручки драга). После запроса — `P1`…`P4` бежевым `#C8A878` |
| Угловые индикаторы | 4 угла | Мелкие геометрические засечки (уголки 6×6 px), рамка `#C8A878` |
| Ручка перетаскивания | Правый нижний угол | Три косые линии-насечки, `cursor: grab` |

Чего на карточке **нет** и быть не должно:

- Правильного места. Карточка не подсвечивается «правильно/неправильно» до проверки.

### 1.2.1 Запрос приоритета

Приоритет на карточке **есть**, но не выдаётся даром. Раньше его не было вовсе: срочность полагалось
вычитывать из текста (кайдзю на мосту важнее кота на тополе). На практике правило оказалось нечитаемым —
игрок не знал, что вообще является шкалой. Просто напечатать `P2` тоже нельзя: тогда стопка разбирается
по меткам, не читая текстов.

Компромисс — платный доступ к полю:

| Состояние | Когда | Вид |
|---|---|---|
| Заштриховано | По умолчанию | Плашка 20×9 px, диагональная штриховка `#C8A878`, `opacity: 0.5` — «поле не подгружено» |
| Запрос | Курсор на карточке (`pointerenter`) либо карточка в фокусе | Янтарный спиннер `\| / — \` с шагом 90 мс |
| Загружено | Спустя 500…1200 мс (случайно) | `P1`…`P4` бежевым `#C8A878` |

- Задержка случайна в диапазоне: постоянные 800 мс игрок отсчитывает механически.
- `pointerleave` / `blur` **обрывают** запрос без прогресса — иначе достаточно провести курсором по всей
  стопке и вернуться за готовыми ответами, а это ровно то, что механика должна исключить.
- Загруженный приоритет **остаётся на карточке до конца смены**: и при переносе между зонами (`place`),
  и при сдвиге внутри очереди (`swapInQueue`). Раньше он протухал при каждом движении — «запросил один
  раз и разложил по памяти» из игры уходило, но вместе с ним уходила и сама раскладка: чтобы поставить
  карточку на место, её надо подвинуть, а после сдвига сравнивать уже нечего. Цену за подсказку берёт
  первый запрос, повторный ничего не проверяет.
- Слот стоит и на чужих/выполненных карточках: пустое место само работало бы подсказкой «эту в архив».
- В `aria-label` карточки приоритета нет — скринридер читает состояние слота (`приоритет не запрошен` /
  `приоритет запрашивается` / `приоритет N`), то есть проходит тот же запрос через фокус.
- Реализация: один `setInterval` на карточку (он же спиннер, он же отсчёт), `PROBE_TICK_MS = 90`,
  число тиков считает чистая `probeTicks(random)` из `engine.ts` — она и покрыта тестом на диапазон.

Текст задач по-прежнему согласован с приоритетом: метка подтверждает интуицию, а не заменяет чтение.

### 1.3 Состояние «смена»

Игра — одна сессия («смена»), состоящая из фаз:

```
init ──▶ РАСКЛАДКА ──▶ СОРТИРОВКА ──▶ [ПРОВЕРКА] ──┬──▶ ИТОГ (onComplete)
                            ▲                       │
                            └── ПРАВКА (попытка 2) ◀┘
```

| Фаза | Что происходит |
|---|---|
| `РАСКЛАДКА` | ~600 мс: карточки «падают» во ВХОДЯЩИЕ по одной с шагом 40 мс (сдвиг + маска, без пружин). Ввод заблокирован. |
| `СОРТИРОВКА` | Основная фаза. Игрок раскидывает карточки, меняет порядок в очереди. Кнопка подтверждения неактивна, пока ВХОДЯЩИЕ не пусты. |
| `ПРОВЕРКА` | Нажата `ПОДТВЕРДИТЬ СМЕНУ`. Вызывается `evaluate`. Короткая анимация «сканирующая линия» по всем зонам (~400 мс). |
| `ПРАВКА` | Только если попытка не последняя и результат неидеален: ошибочные карточки получают полосу `ALERT`, ввод разблокирован, счётчик попыток уменьшен. |
| `ИТОГ` | Вызывается `onComplete`. Дальнейший ввод заблокирован. |

Состояние в памяти — три массива id: `inbox[]`, `queue[]` (упорядоченный), `archive[]`. Инвариант: их
объединение всегда равно множеству всех `tasks`, пересечения пусты. Любая операция перемещения —
атомарное «удалить из исходного массива, вставить в целевой на позицию».

### 1.4 Кнопка `ПОДТВЕРДИТЬ СМЕНУ`

Крупная прямоугольная кнопка в подвале рабочей области (не в нижней панели платформы — слот 3 игре
недоступен, см. `docs/platform.md` §3.6). Внешняя тонкая рамка + внутренний контур, подпись в верхнем
регистре, слева контурная иконка «печать/штамп».

| Состояние | Условие | Вид |
|---|---|---|
| Неактивна | `inbox.length > 0` | Рамка приглушённая, текст `#759C96`, `cursor: not-allowed`, подпись под кнопкой: `ОСТАЛОСЬ ВО ВХОДЯЩИХ: N` |
| Активна | `inbox.length === 0` | Янтарная рамка `#E9A928`, короткий импульс свечения в момент активации, подпись: `ПОПЫТКА 1 ИЗ 2` |

Условие ровно одно — **пустые ВХОДЯЩИЕ**. Игра не проверяет заранее, правильно ли всё разложено, и не
мешает подтвердить заведомо провальную раскладку (см. §7).

Прогресс в слот 2 нижней панели платформы через `onProgress`:

```
onProgress(`РАЗОБРАНО: ${total - inbox.length} / ${total}`, ((total - inbox.length) / total) * 100)
```

Вызывается при каждом изменении `inbox.length`, не каждый кадр. После первой неудачной проверки текст
меняется на `ИСПРАВЬТЕ ОТМЕЧЕННОЕ · ПОПЫТКА 2 ИЗ 2` без процента.

## 2. Управление

### 2.1 Почему pointer-events, а не HTML5 DnD

Перетаскивание реализуется на `pointerdown` / `pointermove` / `pointerup` + `setPointerCapture`.
HTML5 Drag&Drop (`draggable`, `dragstart`, `dragover`, `drop`) **не используется** по причинам:

- на мобильных браузерах HTML5 DnD не работает или работает непредсказуемо, а платформа — терминал,
  который может открываться и на планшете;
- браузерный «призрак» перетаскиваемого элемента не стилизуется — он ломает вид карточки-досье из `STYLE.md`;
- `dragover` требует `preventDefault` в каждом таргете и даёт неточные координаты, а нам нужна
  попиксельная вставка между слотами очереди;
- pointer-events унифицируют мышь, тач и стилус одним кодом — отдельная тач-ветка не нужна.

Обязательные детали реализации: `touch-action: none` на карточках (иначе тач-скролл перехватит жест),
`setPointerCapture(e.pointerId)` на `pointerdown` (жест не теряется при выходе курсора за карточку),
порог начала перетаскивания 5 px (иначе обычный клик по карточке засчитается как микро-drag).

### 2.2 Перетаскивание между зонами

1. `pointerdown` на карточке → запоминаем `pointerId`, стартовые координаты, исходную зону и индекс.
2. После сдвига > 5 px карточка переходит в режим drag: `position: fixed`, следует за курсором,
   слегка приподнята (усиленная рамка + бирюзовое свечение, `transform: rotate(-1.5deg)`), на её месте
   в исходной зоне остаётся пунктирный плейсхолдер.
3. Зона под курсором (определяется через `elementFromPoint` по центру карточки, а не по курсору —
   так поведение предсказуемее) подсвечивается: рамка ярче, фон чуть светлее.
4. `pointerup` → карточка вставляется в зону под курсором. Если курсор вне всех зон — карточка
   возвращается на исходное место анимацией 160 мс.
5. `pointercancel` (системное прерывание, входящий звонок) — эквивалент возврата на место.

### 2.3 Порядок внутри ОЧЕРЕДИ

Реордер — то же самое перетаскивание, но с расчётом точки вставки. Пока карточка тащится над зоной
`ОЧЕРЕДЬ`, вычисляется индекс вставки: перебираются прямоугольники карточек очереди, находится первая,
чей вертикальный центр ниже центра перетаскиваемой. На этом месте раздвигается щель (анимация высоты
120 мс) и рисуется горизонтальная янтарная линия-указатель. Отпускание вставляет карточку туда.

Реордер работает и для карточки, уже находящейся в очереди (перетаскивание внутри зоны), и для карточки,
приходящей из ВХОДЯЩИХ или АРХИВА — вставка сразу в нужную позицию, а не в конец.

### 2.4 Дублирующие кнопки (без drag)

Каждая карточка несёт ряд компактных квадратных кнопок (24×24, контурная иконка, тонкая рамка) —
полный дубль drag-функционала. Нужны для доступности (клавиатура, screen reader, тремор/тачпад),
для e2e-тестов и просто как более быстрый способ разгрести очевидное.

| Кнопка | Иконка | Видна в зонах | Действие |
|---|---|---|---|
| `→ В ОЧЕРЕДЬ` | стрелка вправо в рамке | ВХОДЯЩИЕ, АРХИВ | Переносит карточку в **конец** очереди |
| `→ В АРХИВ` | зубцы шреддера | ВХОДЯЩИЕ, ОЧЕРЕДЬ | Переносит карточку в архив |
| `→ ВО ВХОДЯЩИЕ` | стрелка влево | ОЧЕРЕДЬ, АРХИВ | Возвращает карточку в конец входящих |
| `▲` | треугольник вверх | ОЧЕРЕДЬ | Меняет местами с карточкой выше; неактивна на первой позиции |
| `▼` | треугольник вниз | ОЧЕРЕДЬ | Меняет местами с карточкой ниже; неактивна на последней |

Требования: каждая кнопка — настоящий `<button>` с `aria-label` (`«В очередь: кайдзю-краб…»`), карточка
достижима табом, кнопки внутри карточки — по стрелкам/табу. Все действия кнопок проходят через те же
функции мутации состояния, что и drop — параллельной логики нет.

Клавиатурный эквивалент реордера: на сфокусированной карточке в очереди `Alt+↑` / `Alt+↓` = `▲` / `▼`.

### 2.5 Обратное вытаскивание из архива

Архив не финализируется до подтверждения смены. Карточка достаётся из него drag-ом либо кнопками
`→ В ОЧЕРЕДЬ` / `→ ВО ВХОДЯЩИЕ`. Визуально при вытаскивании карточка мгновенно возвращает нормальную
непрозрачность и цвет (переход 120 мс) — «бумага вынута из приёмника, не измельчена».
Никакой анимации уничтожения при попадании в архив нет — это было бы враньём об обратимости.

## 3. Победа и пенальти

### 3.1 Чистая функция `evaluate`

```ts
type Task = {
  id: string;            // проставляется движком по индексу в config.tasks
  text: string;
  assignee: string;      // "Олег" | "Марина" | "Тимур"
  done: boolean;
  priority: 1 | 2 | 3 | 4;
};

type Mistake =
  | { kind: 'archived-own-active'; id: string }
  | { kind: 'queued-foreign-or-done'; id: string }
  | { kind: 'order-inversion'; id: string; afterId: string };

type Evaluation = {
  mistakes: Mistake[];
  mistakeIds: string[];   // уникальные id карточек для ALERT-подсветки
  score: number;
  correctPlacements: number;
  correctPairs: number;
  maxScore: number;
  percent: number;        // round(score / maxScore * 100)
  perfect: boolean;       // mistakes.length === 0
};

function evaluate(
  queueIds: string[],
  archiveIds: string[],
  tasks: Task[],
  playerName: string
): Evaluation;
```

Функция **чистая**: не читает DOM, не знает про конфиг, не мутирует аргументы. Всё, что ей нужно —
три массива и имя игрока. Сравнение исполнителя с `playerName` — регистронезависимое, с `trim()`
(в админке легко ввести `«олег »`).

«Своя активная задача» = `task.assignee === playerName && !task.done`. Всё остальное — «лишнее».

### 3.2 Три типа ошибок

| Тип | `kind` | Когда фиксируется | Подсвечиваемая карточка |
|---|---|---|---|
| Своя активная в архиве | `archived-own-active` | Задача игрока со статусом АКТИВНО оказалась в АРХИВЕ | Она сама, в архиве |
| Чужая или выполненная в очереди | `queued-foreign-or-done` | В ОЧЕРЕДИ карточка чужого исполнителя **или** со статусом ВЫПОЛНЕНО | Она сама, в очереди |
| Инверсия порядка | `order-inversion` | В ОЧЕРЕДИ карточка с бо́льшим числом приоритета (менее срочная) стоит **выше** карточки с меньшим | Обе карточки пары |

Правила порядка:

- Приоритет — целое 1…4, где **1 = самое срочное**. Правильный порядок — неубывание номера приоритета
  сверху вниз.
- **Равные приоритеты — любой взаимный порядок.** Три задачи P1 могут стоять в любой из шести
  перестановок, ошибкой это не является. Игра проверяет упорядоченность, а не совпадение с эталонным
  списком, — иначе игрок был бы обязан угадать авторскую вкусовщину внутри одного уровня.
- Инверсии считаются по **всем парам** `(i < j)`, у которых `priority[i] > priority[j]`, а не только по
  соседним. Так карточка, заброшенная одна на самый верх, даёт честную картину, а не одну «дешёвую»
  ошибку. Для подсветки берутся id обеих карточек каждой найденной инвертированной пары.
- Карточки, попавшие в очередь ошибочно (`queued-foreign-or-done`), из проверки порядка **исключаются** —
  иначе одна лишняя карточка каскадом порождала бы кучу мнимых инверсий и делала бы подсветку
  нечитаемой. Ошибка за неё уже начислена своим типом.
- Задача, оказавшаяся в АРХИВЕ и там ей и место (чужая или выполненная), ошибкой не является и вообще
  не упоминается в результате.

Карточка, забытая во ВХОДЯЩИХ, невозможна: без пустых входящих нельзя нажать подтверждение.
Тем не менее `evaluate` не полагается на это — задачи, не попавшие ни в `queueIds`, ни в `archiveIds`,
трактуются как «не размещённые»: они не приносят очков за размещение, но и не порождают ошибок
(защита от вызова функции из тестов/отладки с неполными массивами).

### 3.3 Попытки

Число попыток — из конфига (`attempts`, по умолчанию **2**).

1. Первая проверка. Если `perfect === true` — сразу итог, победа.
2. Если нет и попытки остались:
   - каждая карточка из `mistakeIds` получает полосу статуса `ALERT` (оранжево-красный `#F0713E`) вместо
     своей обычной, мигающий круглый маркер в правом верхнем углу и предупреждающий символ `!`;
   - **что именно не так — не сообщается**. Ни правильная зона, ни правильная позиция, ни приоритет.
     Только «здесь ошибка». Сообщение в шапке: `ОБНАРУЖЕНЫ НЕСООТВЕТСТВИЯ: N. ПРОВЕРЬТЕ ОТМЕЧЕННОЕ.`;
   - раскладка **сохраняется как есть** — это правка на месте, а не пересдача с нуля. Ничего не
     перемешивается, ничего не возвращается во ВХОДЯЩИЕ;
   - ввод разблокируется, кнопка подтверждения снова активна (входящие пусты), подпись `ПОПЫТКА 2 ИЗ 2`;
   - ALERT-подсветка снимается с карточки, как только игрок её тронул (перетащил или нажал кнопку), —
     чтобы не путать «отмечена» с «до сих пор не так»; со всех остальных — при следующей проверке.
3. Если попытки кончились — итог с текущим результатом, `won` считается по правилу из §3.5.

### 3.4 Очки

| За что | Сколько |
|---|---|
| Верно размещённая карточка (своя активная в очереди / лишняя в архиве) | **+10** |
| Каждая верно упорядоченная пара карточек в очереди (не инвертированная) | **+5** |

`maxScore` считается по этой же формуле для идеальной раскладки: `10 × N_всего + 5 × C(K, 2)`, где
`K` — число своих активных задач. Для дефолтного контента: `10 × 30 + 5 × C(12,2) = 300 + 330 = 630`.

Штрафов вычитанием нет: ошибка просто не приносит очков (и рушит пары, в которых участвует).
Отрицательный `score` невозможен, что удобно — контракт требует `score: number >= 0`.

Число попыток на очки **не влияет**: считается финальная раскладка. Иначе игрок, который со второго раза
собрал всё идеально, получал бы меньше того, кто угадал наполовину с первого, — и это ощущалось бы
несправедливо в игре про исправление ошибок.

### 3.5 Условие победы и `onComplete`

```
won = perfect || (winThresholdPercent > 0 && percent >= winThresholdPercent)
```

По умолчанию `winThresholdPercent = 100`, то есть по умолчанию побеждает только безошибочная раскладка.
Админ может смягчить (например, 85 — «смена принята с замечаниями»).

```ts
callbacks.onComplete({
  score,
  won,
  details: {
    mistakes: mistakes.length,
    archivedOwnActive: /* число ошибок типа 1 */,
    queuedForeignOrDone: /* число ошибок типа 2 */,
    orderInversions: /* число ошибок типа 3 */,
    attemptsUsed,
    percent,
    styleTag: /* см. ниже */
  }
});
```

`styleTag` для ветвления пост-диалога (`docs/platform.md` §3.3) — вычисляется только при `won`:

| `styleTag` | Условие | Смысл для пост-диалога |
|---|---|---|
| `flawless` | `perfect && attemptsUsed === 1` | Олег разобрал смену с первого раза |
| `corrected` | `perfect && attemptsUsed > 1` | Разобрал со второго — «ну, бывает» |
| `sloppy` | `!perfect` (прошёл по порогу) | Смена принята с замечаниями |

## 5. Реализация

```
minigames/task-sort/
  schema.json
  vite.config.ts
  src/
    engine.ts        # чистая логика, ноль DOM
    engine.test.ts   # vitest
    index.ts         # init/destroy, DOM, pointer-events
    style.css        # scoped-стили (префикс .ts- , монтируются внутрь container)
```

### 5.1 `engine.ts`

Никаких импортов из браузерного окружения. Экспортирует:

| Функция | Назначение |
|---|---|
| `normalizeTasks(rawTasks, playerName): Task[]` | Валидация конфига: проставляет `id` (`t0`, `t1`, …), приводит `priority` к 1…4 (клампом), `assignee`/`done` к нормальному виду, выбрасывает записи с пустым `text`. |
| `isOwnActive(task, playerName): boolean` | Единственное место, где сравнивается исполнитель. |
| `shuffle(ids, seed): string[]` | Детерминированный Фишер–Йейтс на seed'е (для воспроизводимости в тестах; в проде seed — `Date.now()`). |
| `evaluate(queueIds, archiveIds, tasks, playerName): Evaluation` | Основная функция зачёта, §3.1. |
| `maxScoreFor(tasks, playerName): number` | `10 × N + 5 × C(K,2)`. Отдельно — чтобы UI мог показать потолок и чтобы тест на `percent` не дублировал формулу. |
| `styleTagFor(evaluation, attemptsUsed): string` | §3.5. |
| `probeTicks(random): number` | Сколько шагов спиннера крутить при запросе приоритета, §1.2.1. Отдельно — чтобы диапазон 500…1200 мс проверялся тестом, а не глазами. |

Порядок вычислений внутри `evaluate` (важен для читаемости и для тестов):

1. Индексация `tasks` по `id` в `Map`.
2. Разбор `archiveIds`: своя активная → ошибка `archived-own-active`; иначе `correctPlacements++`.
3. Разбор `queueIds`: чужая или выполненная → ошибка `queued-foreign-or-done` и карточка исключается
   из списка для проверки порядка; иначе `correctPlacements++` и карточка попадает в `ordered[]`.
4. Двойной цикл по `ordered[]`: каждая пара `i < j` — либо `correctPairs++`, либо ошибка
   `order-inversion` с обоими id. Пар не больше `C(12,2) = 66` — квадратичность здесь безобидна.
5. `score = 10 × correctPlacements + 5 × correctPairs`, `percent = round(score / maxScore × 100)`
   (при `maxScore === 0` → `percent = 100`, деления на ноль нет).

### 5.2 `index.ts`

- `init(container, config, callbacks)` строит DOM целиком внутри `container`, стили — из локального
  `style.css` (импортируется Vite'ом и инлайнится в бандл), все селекторы с префиксом `.ts-`, никаких
  глобальных правил и никаких обращений к `document.body` / `<head>`.
- Рендер карточки по `STYLE.md`: `<article class="ts-card">` → `<div class="ts-card__status">` (полоса),
  `<span class="ts-card__badge">` (исполнитель), `<p class="ts-card__text">`, `<span class="ts-card__id">`,
  4× `<i class="ts-card__corner">`, панель кнопок `<div class="ts-card__actions">`.
- Рендер зон: `<section class="ts-zone" data-zone="inbox|queue|archive">` с заголовком на цветной полосе.
  Зоны — drop-таргеты; принадлежность определяется через `data-zone` у ближайшего предка элемента,
  найденного `document.elementFromPoint` по центру перетаскиваемой карточки.
- Состояние — три массива id + `attemptsUsed` + `mistakeIds`. Единственная функция `render()` приводит DOM
  к состоянию; все обработчики только мутируют состояние и вызывают `render()`. Полный ререндер трёх зон
  на 30 карточках дешевле любой инкрементальной схемы и не даёт рассинхрона.
- Анимации — CSS-переходы 100–220 мс (`STYLE.md`), без пружин. Перетаскивание идёт через `transform`
  в `requestAnimationFrame` (одно обновление на кадр, координаты копятся в переменной из `pointermove`),
  что и даёт стабильные 60 FPS: layout при драге не трогается, двигается только слой карточки.
- `destroy()`: снять слушатели с `window` (`pointermove` / `pointerup` / `pointercancel`, вешаются
  только на время жеста), отменить `requestAnimationFrame` и таймеры фазы РАСКЛАДКА, остановить и
  освободить аудио, `container.innerHTML = ''`.
- Ровно один из `onComplete` / `onExit` вызывается один раз; флаг `finished` защищает от повторного
  вызова при быстром двойном клике по подтверждению.

### 5.3 Покрытие vitest (`engine.test.ts`)

Фикстура — компактный набор из ~6 задач (2 своих P1, 1 своя P2, 1 своя P3, 1 чужая активная, 1 выполненная),
чтобы ожидаемые числа считались в уме. Отдельный блок тестов — на дефолтном контенте из §6.

| # | Тест | Ожидание |
|---|---|---|
| 1 | Идеальная раскладка | `mistakes: []`, `perfect: true`, `score === maxScore`, `percent === 100` |
| 2 | Только ошибка типа 1 (своя активная в архиве) | ровно одна `archived-own-active`, `perfect: false`, размещение не засчитано |
| 3 | Только ошибка типа 2 (чужая в очереди) | ровно одна `queued-foreign-or-done` |
| 4 | Только ошибка типа 2 (выполненная своя в очереди) | тоже `queued-foreign-or-done` — «своя» не спасает от `done` |
| 5 | Только ошибка типа 3 (инверсия соседних) | одна `order-inversion`, оба id в `mistakeIds`, `correctPairs` меньше максимума ровно на 1 |
| 6 | Инверсия не соседних (карточка P4 заброшена наверх) | число ошибок = числу перепрыгнутых карточек, а не 1 |
| 7 | Равные приоритеты, все перестановки трёх P1 | во всех случаях `mistakes: []` |
| 8 | Комбинация 1+2 | обе ошибки, независимо |
| 9 | Комбинация 1+2+3 | все три типа в одном результате, `mistakeIds` без дублей |
| 10 | Лишняя карточка в очереди не порождает мнимых инверсий | ошибок ровно 1 (типа 2), `order-inversion` отсутствует |
| 11 | Регистр и пробелы в `assignee` (`" олег "`) | считается своей |
| 12 | Пустая очередь, всё в архиве | ошибок = числу своих активных, `correctPairs === 0`, `score > 0` за верно заархивированное |
| 13 | Пустой архив, всё в очереди | ошибок = числу лишних + инверсии среди правильных |
| 14 | `maxScoreFor` на дефолтном контенте | `630` |
| 15 | Задача не упомянута ни в одном массиве | ошибок не добавляет, очков не даёт |
| 16 | `styleTagFor` | `flawless` / `corrected` / `sloppy` по §3.5 |
| 17 | `shuffle(ids, seed)` детерминирован и сохраняет мультимножество | тот же seed → тот же результат, сортированные копии равны |
| 18 | `normalizeTasks` кламп `priority: 9 → 4`, `0 → 1`, отбрасывание пустого `text` | — |

Тесты `index.ts` не требуются (DOM-слой), но `evaluate` вызывается из UI ровно одной строкой — это
намеренно, чтобы всё, что стоит проверять, проверялось юнит-тестами без jsdom.

## 7. Edge cases

| Ситуация | Поведение |
|---|---|
| **Все входящие разобраны, но с ошибками** | Кнопка `ПОДТВЕРДИТЬ СМЕНУ` активна — условие ровно одно, `inbox.length === 0`. Игра не подсказывает превентивно и не блокирует заведомо неверную раскладку: право нажать «готово» и ошибиться — часть механики. |
| **На второй (последней) попытке снова ошибка** | Никаких третьих шансов и подсказок: `evaluate` считает финальный `score`, `won` определяется по §3.5 (при дефолтном пороге 100 — `false`), вызывается `onComplete`. Платформа уводит в `post_lose_dialogue_id`. Прогресс всё равно сохраняется (`attempts` инкрементируется, `bestScore` обновляется, см. `docs/platform.md` §6), так что переигровка после нового скана QR имеет смысл. |
| **Равные приоритеты** | Взаимный порядок карточек одного уровня не проверяется вообще. Все пары равных приоритетов засчитываются как верные (+5 каждая), инверсией не считаются никогда. |
| **В очереди одна карточка или ноль** | Проверка порядка тривиально проходит: пар нет, `correctPairs === 0`, ошибок типа 3 нет. `maxScore` при этом всё равно считается по числу своих активных задач, так что пустая очередь даёт низкий `percent` и ошибки типа 1 — как и должно быть. |
| **Пустой `tasks[]` в конфиге** | Некорректная настройка. Игра не падает и не зависает: рендерится панель-заглушка на месте зон — статусная полоса `ALERT` и текст `КОНФИГ ПУСТ · ЗАДАЧИ НЕ ЗАГРУЖЕНЫ`, плюс кнопка `ЗАВЕРШИТЬ`, вызывающая `onExit()`. `onComplete` в этом случае не вызывается — «победа на нуле задач» засчитала бы игру админу, который просто не заполнил форму. То же самое при `tasks`, где после `normalizeTasks` не осталось ни одной валидной записи. |
| **В конфиге нет ни одной задачи с `assignee === playerName && !done`** | Формально валидно (все карточки — в архив). Игра работает: очередь остаётся пустой, `maxScore = 10 × N`, идеальная раскладка достижима. Отдельной обработки не требуется. |
| **Опечатка в `playerName` (не совпадает ни с одним `assignee`)** | Вырождается в предыдущий случай — все задачи «чужие». Enum в `assignee` и дефолт `"Олег"` в обоих полях делают это маловероятным; ловить админа за руку игра не будет. |
| **Очень длинный текст задачи** | Текст карточки — `line-clamp: 4` (примерно 4 строки узкого шрифта), дальше многоточие. Полный текст доступен по наведению во всплывающей панели-досье (та же угловатая рамка, ширина шире карточки, появление сдвигом 160 мс) и в `title`/`aria-label` для доступности. Высота карточки при этом фиксирована — иначе стопка ВХОДЯЩИХ и слоты ОЧЕРЕДИ разъедутся и попадание при drag'е станет непредсказуемым. Рекомендация для админки — держаться 1–2 предложений, как в дефолтном контенте. |
| **Очень много задач в конфиге (50+)** | Зоны скроллятся вертикально (собственный скролл внутри панели, без скролла всей рабочей области). Во время перетаскивания у края зоны включается автоскролл со скоростью, пропорциональной близости к краю. Квадратичная проверка порядка при 50 своих активных даёт 1225 пар — по-прежнему незаметно. |
| **Карточка отпущена вне всех зон** | Возврат на исходное место анимацией 160 мс, состояние не меняется. То же при `pointercancel`. |
| **Двойное быстрое нажатие `ПОДТВЕРДИТЬ СМЕНУ`** | Флаг `checking` блокирует повторный вызов на время анимации проверки; флаг `finished` гарантирует, что `onComplete` вызовется ровно один раз. |
| **`destroy()` во время активного жеста** | Слушатели `window` снимаются безусловно (они вешаются на время жеста и хранятся в поле), `releasePointerCapture` в `try/catch` — элемент к этому моменту может быть уже удалён. |
