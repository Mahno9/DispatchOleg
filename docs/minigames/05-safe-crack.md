# Мини-игра 05: safe-crack (взлом сейфа)

**ID:** `safe-crack`
**Тип:** DOM (без canvas, без игрового цикла — только события и таймеры)
**Жанр:** комедийная головоломка с нарочито неудобным вводом

Игрок вскрывает банковский сейф с N ригелями. На каждом ригеле — вопрос, ответ на который известен
(или угадывается), но **ввести** ответ можно только через абсурдно неудобный виджет: слайдер на 10000
делений, выпадающий список на 800 пунктов без поиска, телефонный диск, перемешивающаяся клавиатура.

Основной комедийный приём — «говно-UX как фича». Игра не проверяет знания, она проверяет терпение.
Все виджеты честно работают и всегда позволяют ввести правильный ответ — сложность исключительно в
моторике и внимании, а не в случайности. Ни один виджет не имеет права быть непроходимым.

Визуально — по `STYLE.md`: дверь сейфа как техническая схема (контурный чертёж на почти чёрном фоне),
ригели — вертикальный ряд прямоугольных индикаторов справа, виджет ввода — механическая панель в центре
рабочей области, кнопка «ВВОД» — физическая квадратная кнопка терминала с янтарной подсветкой.

---

## 1. Геймплей и состояния

### 1.1 Общая модель

Сейф описывается массивом `locks[]` в конфиге админки. Каждый элемент — один ригель:

```ts
type Lock = {
  question: string;      // «Сколько этажей в здании мэрии?»
  widget: WidgetId;      // 'mega-slider' | 'haystack-dropdown' | ...
  answer: string;        // эталонный ответ, сравнение нормализованное (см. §5.3)
  points: number;        // очки за вскрытие этого ригеля
  params: object;        // плоский объект параметров виджета (см. §4.3)
};
```

Ригели вскрываются **строго последовательно**, от `locks[0]` к `locks[N-1]`. Пропустить ригель нельзя,
вернуться к вскрытому — тоже. Вскрытый ригель остаётся вскрытым до конца партии (ошибка на пятом ригеле
не закрывает первые четыре).

Поверх последовательности ригелей работают два необязательных глобальных ограничителя:

- **общий пул попыток** `maxAttempts` — одна общая касса ошибок на всю партию, не на замок.
  `maxAttempts: 0` — бесконечно, ошибки только вычитают очки;
- **таймер** `timeLimitSeconds` — общий на всю партию, тикает непрерывно, включая фазу `checking`.
  `timeLimitSeconds: 0` — без таймера.

Оба ограничителя независимы: можно включить только таймер, только пул, оба сразу или ничего
(в последнем случае игра — чистая комедия без давления, проиграть невозможно).

### 1.2 FSM

```
                         ┌──────────┐
                         │  intro   │   заставка: закрытая дверь сейфа,
                         └────┬─────┘   N ригелей, кнопка «НАЧАТЬ ВЗЛОМ»
                              │ клик игрока (или locks[] пуст → сразу victory)
                              ▼
        ┌──────────────────────────────────────────┐
        │              lock(i)                      │  активен виджет ввода,
        │  «РИГЕЛЬ i+1 / N» + question + widget     │  кнопка «ВВОД» доступна
        └────┬─────────────────────────────────────┘
             │ игрок нажал «ВВОД» (или selfSubmit-виджет сам подтвердил, см. §5.2)
             ▼
        ┌──────────────────────────┐
        │        checking           │  600 мс: анимация проворота лимба,
        │  (ввод заблокирован)      │  звук механики, никакой реакции на клики
        └────┬────────────────┬─────┘
             │ верно          │ неверно
             ▼                ▼
   ┌──────────────┐   ┌──────────────┐
   │   lockOpen    │   │   lockFail    │  +errorPenalty к счётчику ошибок,
   │  +points      │   │  −errorPenalty│  замок переинициализируется (§3.2)
   └──────┬────────┘   └──────┬────────┘
          │                   │
          │ i+1 < N           │ пул попыток не исчерпан
          ├──────────────┐    ├──────────────────┐
          ▼              │    ▼                  │
      lock(i+1)          │  lock(i)              │  тот же ригель,
                         │  (новое состояние)    │  новая расстановка
          i+1 == N       │    попытки кончились  │
          ▼              ▼    ▼                  ▼
     ┌──────────┐              ┌──────────┐
     │ victory  │              │  defeat  │
     └──────────┘              └──────────┘
          │                         │
          └────────► onComplete ◄───┘
```

Таймер (если включён) может выстрелить из любого состояния и переводит FSM в `defeat` — с одним
исключением, описанным в §3.5.

### 1.3 Состояния подробно

| Состояние | Длительность | Что видит игрок | Что доступно |
|---|---|---|---|
| `intro` | до клика | Закрытая дверь сейфа, ряд из N неподсвеченных ригелей, `title` игры, условия (лимит времени / попыток, если заданы), кнопка «НАЧАТЬ ВЗЛОМ» | клик по кнопке |
| `lock(i)` | до подтверждения | Заголовок «РИГЕЛЬ `i+1` / `N`», текст `question`, смонтированный виджет `widget` с параметрами `params`, кнопка «ВВОД» | взаимодействие с виджетом, «ВВОД» |
| `checking` | ровно 600 мс | Виджет затемнён (полупрозрачность + `pointer-events: none`), лимб проворачивается, статусная полоса «ПРОВЕРКА…», кнопка «ВВОД» в состоянии `disabled` | ничего |
| `lockOpen` | ~500 мс | Ригель `i` переключается в янтарный «OPEN» с коротким импульсом свечения, всплывает `+points` | ничего (авто-переход) |
| `lockFail` | ~500 мс | Оранжево-красная вспышка рамки, мигающий круглый маркер тревоги, `−errorPenalty`, счётчик оставшихся попыток дёргается | ничего (авто-переход) |
| `victory` | до `onComplete` | Дверь сейфа распахивается, показывается `prizeImage`, итоговый счёт | ничего |
| `defeat` | до `onComplete` | Дверь остаётся закрытой, статус «ТРЕВОГА» / «ВРЕМЯ ВЫШЛО», итоговый счёт | ничего |

`lockOpen` и `lockFail` — короткие «показательные» состояния, а не мгновенные переходы: игроку нужно
время увидеть результат. Реализуются как таймауты внутри DOM-слоя; чистая FSM в `engine.ts` считает
их отдельными состояниями, чтобы тесты могли проверять последовательность (см. §5.4).

### 1.4 Постоянно видимый HUD

Поверх любого состояния кроме `intro` в рабочей области держится служебная строка (по `STYLE.md` —
моноширинный текст на приглушённой полосе):

```
РИГЕЛЬ 3/6   ОЧКИ 240   ПОПЫТКИ 2/5   00:47
```

Блоки «ПОПЫТКИ» и таймер скрываются, если соответствующий лимит равен `0`.

Параллельно платформа получает `onProgress(text, percent)`:

```ts
onProgress(`Ригель ${i + 1} из ${N}`, Math.round((openedCount / N) * 100));
```

Вызывается при входе в каждый `lock(i)` и один раз при `victory`/`defeat`. Это то, что игрок видит
в слоте 2 нижней панели терминала (см. `docs/platform.md`, §3.1).

## 2. Управление

Все девять виджетов реализуют один интерфейс (§5.1) и различаются только внутренностями. Общее правило:
**виджет всегда имеет валидное текущее значение** — `getValue()` никогда не возвращает `undefined`.
Даже нетронутый виджет отдаёт своё стартовое значение, и игрок вправе нажать «ВВОД» немедленно.

### 2.1 `mega-slider` — «точное число»

Горизонтальный ползунок диапазона `[min, max]` (по умолчанию `0…10000`) с шагом 1. Игрок тянет ручку
мышью или трогает клавишами стрелок (`←`/`→` — ±1, что честнее, но медленнее). Текущее значение
выводится крупными цифрами над шкалой.

Издевательская механика — **дрейф**: если игрок не трогал ползунок дольше `driftIntervalMs`
(по умолчанию 800 мс), значение начинает уползать на `driftAmount` (по умолчанию ±1) за интервал,
в случайную сторону, перевыбираемую каждый тик. Дрейф не выходит за `[min, max]` (у границы отражается
внутрь). Любое действие игрока сбрасывает таймер дрейфа. Итог: подвести к точному числу можно,
но нельзя «навести и задуматься» — надо навести и сразу жать «ВВОД».

Дрейф останавливается на входе в `checking` — значение, отправленное на проверку, фиксируется
в момент нажатия «ВВОД», а не читается заново.

### 2.2 `haystack-dropdown` — «иголка в стоге»

Обычный нативный `<select>` (стилизованный под терминал, но именно `select` — с нативной прокруткой)
на несколько сотен пунктов из `params.options`. Ни поля поиска, ни группировки, ни фильтра — только
скролл. Порядок пунктов перемешивается при каждой инициализации виджета, поэтому «запомнить, что ответ
был третьим снизу» не работает.

Нативный `select` даёт браузерный type-ahead (набор первых букв прыгает к пункту) — это **допустимая
лазейка**, оставлена намеренно: игрок, который догадался, получает заслуженное облегчение.

### 2.3 `rotary-dial` — «телефонный диск»

Дисковый номеронабиратель с отверстиями под цифры `0–9`. Игрок зажимает мышью нужное отверстие,
тянет диск по дуге по часовой стрелке до упора-ограничителя и отпускает — диск возвращается сам,
с механической анимацией и щелчками, цифра добавляется в набранную строку.

Ключевая жестокость — **недокрут не засчитывается**: если игрок отпустил кнопку мыши, не доведя диск
до упора (порог `dialFullTurnDegrees`, по умолчанию 300° от позиции отверстия), диск отматывается назад
и цифра **не** добавляется. Никакого сообщения об ошибке — просто ничего не произошло.

Набранная строка отображается в окошке. Кнопка «СБРОС» рядом с диском очищает набор целиком
(посимвольного удаления нет — это было бы слишком гуманно). Ожидаемая длина набора — `params.digits`;
при достижении неё диск блокируется до сброса.

### 2.4 `shuffle-keyboard` — «прыгающая клавиатура»

Экранная клавиатура русского алфавита (+ пробел) — сетка кнопок, разложенная **в случайном порядке**.
Игрок кликает буквы, набирая слово (пример из ТЗ: ответ «2» надо ввести словом — «два»).

После **каждого** нажатия раскладка перемешивается заново: буквы перепрыгивают на другие клетки.
Мышечная память не работает, каждую следующую букву надо искать глазами с нуля.

Набранное слово показывается в поле-дисплее. Есть кнопка «⌫» (стирает последний символ) — она тоже
участвует в перемешивании и тоже прыгает по сетке.

### 2.5 `number-as-words` — «число прописью»

Число собирается **прописью** из барабанов-фрагментов, а не набирается цифрами. Барабанов —
`params.slots` (по умолчанию 3), каждый прокручивается независимо (колесо мыши над барабаном или
стрелки ▲/▼ по бокам). Барабаны содержат фрагменты русских числительных, разбитые по разрядам:

| Барабан | Содержимое |
|---|---|
| 1 (сотни) | `—`, `сто`, `двести`, `триста`, `четыреста`, `пятьсот`, … |
| 2 (десятки) | `—`, `десять`, `двадцать`, `тридцать`, `сорок`, `пятьдесят`, … |
| 3 (единицы) | `—`, `один`, `два`, `три`, `четыре`, `пять`, … |

Значение виджета — конкатенация непустых фрагментов через пробел: `двести` + `—` + `три` → `двести три`.
Пустой фрагмент `—` обязателен на каждом барабане, иначе «двести» набрать нельзя.

Комедия здесь в том, что числа вроде «двенадцать» ломают разрядную логику: они лежат на барабане
десятков как цельные пункты, и игроку приходится сначала сообразить, где именно искать нужный фрагмент.

### 2.6 `plus-minus` — «плюс-минус»

Крупное число, стартующее со случайного значения из `[startMin, startMax]`, и две квадратные кнопки:
`+1` и `−1`. Никакого ввода с клавиатуры, никакого «зажать и держать» (автоповтора нет — каждый клик
считается отдельно). Дойти от 3417 до 3500 — 83 клика, и это ожидаемое поведение.

Издевательская механика — **кнопки меняются местами каждые `swapEveryNClicks` кликов** (по умолчанию 5).
Свап анимируется быстрым сдвигом (по `STYLE.md` — 120–180 мс), но подписи на кнопках всегда честные:
игрок, который смотрит на подпись, а не на позицию, не ошибётся. Игрок, который вошёл в ритм, ошибётся
обязательно.

Счётчик до следующего свапа не показывается.

### 2.7 `safe-drum` — «барабан с инерцией»

Вертикальный барабан с буквами `params.alphabet`, вращаемый перетаскиванием мышью или колесом.
Барабан **физичен**: у него есть инерция и трение. Резкий бросок раскручивает его на десятки позиций,
после чего он долго затухает; довести до нужной буквы можно только осторожными короткими движениями.

Перелёт (overshoot) — норма: барабан не «примагничивается» к ближайшей позиции мгновенно, а доезжает
по инерции и лишь затем притягивается к центру ближайшей ячейки.

Если `params.targetWord` длиннее одного символа, барабан работает посимвольно: под ним кнопка
«ЗАФИКСИРОВАТЬ», добавляющая текущую букву в набранную строку и оставляющая барабан на месте
(перематывать от текущей позиции, а не от начала). Кнопка «СБРОС» очищает набор.

### 2.8 `hold-button` — «удержание» (selfSubmit)

Одна большая физическая кнопка «ДЕРЖАТЬ». Задача — удерживать её нажатой **ровно** `targetSeconds`
секунд с допуском `toleranceMs` (по умолчанию ±300 мс). Отпускание = подтверждение.

Рядом — аналоговый манометр со стрелкой, показывающий прошедшее время. Стрелка **отстаёт** от реального
времени на `gaugeLagMs` (по умолчанию 400 мс) и доезжает с инерционным сглаживанием: ориентироваться
по манометру буквально — гарантированный перелёт. Правильная стратегия — считать про себя, а на манометр
не смотреть; манометр существует, чтобы мешать.

**Это единственный selfSubmit-виджет** (§5.2): кнопка «ВВОД» для него не рендерится вовсе, подтверждение
происходит по `pointerup`/`pointercancel`. Значение виджета — строка `'hit'` или `'miss'`, вычисляемая
самим виджетом по попаданию длительности удержания в окно `[targetSeconds*1000 − toleranceMs,
targetSeconds*1000 + toleranceMs]`; поле `answer` в конфиге для этого виджета игнорируется движком
(движок сравнивает результат с константой `'hit'`).

Отпускание раньше 300 мс трактуется как случайный клик и **не** считается попыткой — виджет молча
сбрасывается.

### 2.9 `checkbox-wall` — «стена чекбоксов»

Сетка `gridSize × gridSize` (по умолчанию 6×6) квадратных чекбоксов. Нужно отметить ровно те клетки,
которые складываются в заданный `pattern` — обычно очертания цифры (ответ на вопрос «сколько…» рисуется,
а не пишется). Эталон в конфиге задаётся строкой из `0`/`1` по строкам сетки.

Издевательская механика — **клик мимо паттерна снимает случайную уже отмеченную клетку**. Не ту,
по которой кликнули, а случайную из отмеченных. Игрок видит, что где-то что-то погасло, и должен
сам искать, где именно. Клик по уже отмеченной клетке паттерна снимает её обычным образом (это не ошибка).

Ошибочный клик сопровождается коротким оранжевым импульсом на снятой клетке — чтобы внимательный
игрок мог заметить, а невнимательный собирал стену заново.

Значение виджета — строка `0`/`1` той же формы, что `pattern`; сравнивается с `pattern` напрямую,
поле `answer` для этого виджета игнорируется (аналогично `hold-button`).

### 2.10 Сводка управления

| Виджет | Ввод | Мешающий фактор | selfSubmit |
|---|---|---|---|
| `mega-slider` | драг ползунка, стрелки ±1 | дрейф ±1 при бездействии | нет |
| `haystack-dropdown` | нативный `select`, скролл | сотни пунктов, нет поиска, перемешивание | нет |
| `rotary-dial` | тянуть диск по дуге до упора | недокрут не засчитывается | нет |
| `shuffle-keyboard` | клики по буквам | раскладка перемешивается после каждой буквы | нет |
| `number-as-words` | прокрутка барабанов | число только прописью, разряды по барабанам | нет |
| `plus-minus` | клики `+1`/`−1` | кнопки меняются местами каждые N кликов | нет |
| `safe-drum` | драг/колесо по барабану | инерция и перелёт | нет |
| `hold-button` | зажать и отпустить | манометр отстаёт на 400 мс | **да** |
| `checkbox-wall` | клики по сетке 6×6 | ошибочный клик гасит случайную отмеченную | нет |

## 3. Победа и пенальти

### 3.1 Фаза `checking` — проворот

Между подтверждением ответа и показом результата всегда проходит **ровно 600 мс** фазы `checking`.
Это не «загрузка» (проверять нечего — сравнение строк мгновенно), а драматическая пауза: лимб
проворачивается, звучит механика, игрок ждёт щелчка.

В этой фазе:
- виджет визуально гасится и получает `pointer-events: none`;
- кнопка «ВВОД» переводится в `disabled` — **это защита от даблклика** (§6.4), а не косметика;
- дрейф `mega-slider`, инерция `safe-drum` и прочие внутренние таймеры виджетов останавливаются;
- значение уже зафиксировано в момент подтверждения и не перечитывается.

### 3.2 Ошибка → переинициализация замка

При неверном ответе замок **не** возвращается в то же состояние. Он переинициализируется целиком:
вызывается `widget.reset()`, который перегенерирует всё случайное содержимое виджета.

| Виджет | Что меняется при переинициализации |
|---|---|
| `mega-slider` | ползунок в новую случайную стартовую позицию внутри `[min, max]` |
| `haystack-dropdown` | новая случайная перестановка пунктов списка |
| `rotary-dial` | набор очищается |
| `shuffle-keyboard` | новая случайная раскладка, поле ввода очищено |
| `number-as-words` | все барабаны на новые случайные позиции |
| `plus-minus` | новое случайное стартовое число, счётчик до свапа обнулён |
| `safe-drum` | барабан в новую случайную позицию, набор очищен |
| `hold-button` | стрелка манометра на ноль |
| `checkbox-wall` | все отметки сняты |

Вопрос и правильный ответ при этом **остаются теми же** — переспрашивается тот же самый ригель.
Смысл в том, что игрок не может «повторить движения»: заученный путь к нужному пункту списка или
позиция ползунка обесцениваются. Мышечная память сгорает вместе с попыткой.

### 3.3 Очки

- Верный ответ на ригель `i` → `score += locks[i].points`.
- Ошибка → `score -= errorPenalty`. Итоговый `score` **никогда не отрицателен**: перед `onComplete`
  применяется `Math.max(0, score)` (контракт GameService требует целое `>= 0`).
- Очки за уже вскрытые ригели при последующих ошибках не отбираются сверх `errorPenalty`.

### 3.4 Лимиты

| Параметр | `0` означает | Поведение |
|---|---|---|
| `maxAttempts` | бесконечно | Общий пул на всю партию. Каждая ошибка на любом ригеле уменьшает остаток на 1. Остаток `0` в момент ошибки → `defeat` немедленно (после `lockFail`), даже если это первый ригель из десяти. |
| `timeLimitSeconds` | без таймера | Общий на партию, стартует при выходе из `intro`, тикает всегда, включая `checking`. Истечение → `defeat`. |

Оба лимита при значении `0` не отображаются в HUD вовсе — не «∞», а отсутствие блока.

### 3.5 Победа приоритетнее истёкшего таймера

Гонка условий разрешается в пользу игрока. Если последний ригель вскрыт и таймер истёк «в одну и ту же
секунду» — засчитывается **победа**.

Конкретно: тик таймера обрабатывается только в состояниях `lock(i)` и `checking`. В `lockOpen`,
`lockFail`, `victory` и `defeat` истёкший таймер не рассматривается вовсе. Поскольку успешная проверка
переводит FSM в `lockOpen` до того, как будет обработан следующий тик, победа физически не может
проиграть таймеру. Формально в редьюсере это одна строка приоритета: событие `ANSWER_CORRECT` /
`ANSWER_WRONG` обрабатывается раньше `TICK` в одном кадре, и терминальное состояние не переопределяется.

Обратное неверно: если таймер истёк во время `checking`, а ответ оказался **неверным**, игрок проигрывает
по таймеру (см. §6.6).

### 3.6 Результат

```ts
onComplete({
  score: Math.max(0, score),
  won: allLocksOpened,
  details: {
    locksOpened,          // сколько ригелей вскрыто
    locksTotal,           // сколько всего
    mistakes,             // сколько неверных вводов за партию
    timeSpentSeconds,     // сколько заняло
    styleTag              // см. ниже
  }
});
```

`styleTag` — для ветвления пост-диалога (`docs/platform.md`, §3.3):

| Условие | `styleTag` | Смысл для пост-диалога |
|---|---|---|
| `won && mistakes === 0` | `"medvezhatnik"` | Вскрыл без единой ошибки — профессионал |
| `won && mistakes > locksTotal` | `"grubaya-sila"` | Вскрыл, но перебором и матом |
| `won` (иначе) | `"vzlomshchik"` | Обычная победа |
| `!won` | — | При поражении `styleTag` не выставляется (платформа его всё равно не смотрит) |

## 5. Реализация

### 5.1 Интерфейс `LockWidget` и реестр

Все девять виджетов реализуют один интерфейс:

```ts
interface LockWidget {
  mount(container: HTMLElement, params: WidgetParams, onChange?: () => void): void;
  getValue(): string;
  reset(): void;
  destroy(): void;
}

type WidgetFactory = (ctx: WidgetContext) => LockWidget;

interface WidgetContext {
  answer: string;              // нужен для авто-подгонки (§6.2) и подстановки в options
  selfSubmit?: (value: string) => void;  // только для selfSubmit-виджетов (§5.2)
  playSound: (name: string) => void;     // виджет не лезет в config.sounds напрямую
}
```

| Метод | Контракт |
|---|---|
| `mount` | Отрисовать себя внутри `container`. Все обработчики вешаются на элементы **внутри** контейнера или на `window` с обязательным снятием в `destroy()` (драг у `rotary-dial`/`safe-drum` требует `window`-слушателей `pointermove`/`pointerup`) |
| `getValue` | Вернуть текущее значение как строку. **Всегда** валидная строка, даже для нетронутого виджета |
| `reset` | Перегенерировать случайное состояние (§3.2) без пересоздания DOM. Вызывается после ошибки |
| `destroy` | Снять все слушатели, остановить таймеры/RAF, очистить контейнер |
| `onChange` | Необязательный колбэк «игрок что-то сделал» — DOM-слой использует его для звука щелчка и сброса подсветки |

Реестр — обычный объект-словарь, без классов и абстрактных фабрик:

```ts
const WIDGETS: Record<WidgetId, WidgetFactory> = {
  'mega-slider': createMegaSlider,
  'haystack-dropdown': createHaystackDropdown,
  'rotary-dial': createRotaryDial,
  'shuffle-keyboard': createShuffleKeyboard,
  'number-as-words': createNumberAsWords,
  'plus-minus': createPlusMinus,
  'safe-drum': createSafeDrum,
  'hold-button': createHoldButton,
  'checkbox-wall': createCheckboxWall,
};
```

Неизвестный `widget` в конфиге → fallback на `mega-slider` с логом в консоль (игра не должна падать
от опечатки в админке).

### 5.2 Частный случай `hold-button` — selfSubmit

Восемь виджетов из девяти пассивны: они накапливают значение, а подтверждает его игрок кнопкой «ВВОД».
`hold-button` устроен иначе — сам акт ввода (отпускание кнопки) **является** подтверждением.

Обработка в FSM отличается в трёх местах:

1. **Кнопка «ВВОД» не рендерится.** Для `selfSubmit`-виджетов DOM-слой не создаёт кнопку вообще —
   не создаёт `disabled`, а просто не создаёт. Иначе игрок мог бы подтвердить «пустое» удержание.
2. **Событие подтверждения приходит от виджета.** Виджет получает в `WidgetContext` функцию
   `selfSubmit(value)` и вызывает её сам. DOM-слой прокидывает вызов в тот же редьюсер, что и клик
   по «ВВОД» — событие FSM одно и то же (`SUBMIT`), различается только источник.
3. **Защита от повторного сабмита — на стороне DOM-слоя.** Пока FSM в `checking`, все вызовы
   `selfSubmit` игнорируются (виджет уже погашен `pointer-events: none`, но `pointerup` может прилететь
   от уже начатого жеста). Это ровно тот же инвариант, что `disabled` у кнопки «ВВОД» (§6.4),
   реализованный другим механизмом.

Флаг `selfSubmit` — свойство **виджета**, а не конфига: он захардкожен в реестре как множество
`const SELF_SUBMIT: Set<WidgetId> = new Set(['hold-button'])`. Админ не может его переключить,
и это правильно — от него ничего не зависит, кроме одной строки в рендере.

Сама FSM про `selfSubmit` не знает вовсе: она принимает `SUBMIT { value }` и не спрашивает, откуда он.
Вся разница живёт в `index.ts`.

### 5.3 Сравнение ответов

```ts
export function normalize(s: string): string {
  return s.trim().toLowerCase().replace(/ё/g, 'е');
}

export function compareAnswer(input: string, answer: string): boolean {
  return normalize(input) === normalize(answer);
}
```

Три правила, ровно как согласовано: `trim` (лишние пробелы по краям — не ошибка игрока, а артефакт
виджета), `toLowerCase` (регистр не проверяется), `ё → е` (типовой источник ложных отказов в русском
тексте — «четыре» / «чётыре», «шёл» / «шел»).

Чего нормализация **не** делает намеренно:
- не схлопывает внутренние пробелы (`number-as-words` собирает значение сам и не может породить
  двойной пробел — если админ вписал его в `answer`, это его ошибка, видимая в тесте);
- не убирает знаки препинания;
- не приводит числа к каноничному виду («007» ≠ «7»).

Для `hold-button` и `checkbox-wall` сравнение идёт не с `answer`, а с внутренним эталоном виджета
(`'hit'` и `params.pattern` соответственно) — движок получает уже вычисленный виджетом результат
и сравнивает его тем же `compareAnswer`, просто с другой правой частью. Отдельной ветки в FSM
это не требует: `resolveExpected(lock)` возвращает нужный эталон, дальше всё едино.

Для `number-as-words` админ пишет `answer` цифрами («128»), а виджет выдаёт значение прописью —
`resolveExpected` переводит целый эталон из диапазона 0…999 через `numberToWords` («сто двадцать
восемь»). Ответ, записанный прописью, а также нецелые числа и значения вне диапазона остаются как есть.

### 5.4 `engine.ts` — чистая логика

`engine.ts` не импортирует ничего из DOM, не использует `Date.now()` напрямую и не создаёт таймеров.
Только редьюсер + чистые функции. Это и есть предмет `engine.test.ts` (vitest).

```ts
export type Phase = 'intro' | 'lock' | 'checking' | 'lockOpen' | 'lockFail' | 'victory' | 'defeat';

export interface State {
  phase: Phase;
  currentLock: number;      // индекс активного ригеля
  score: number;
  mistakes: number;
  attemptsLeft: number;     // Infinity при maxAttempts === 0
  timeLeft: number;         // Infinity при timeLimitSeconds === 0
  locksOpened: number;
}

export type Event =
  | { type: 'START' }
  | { type: 'SUBMIT'; value: string }
  | { type: 'CHECK_DONE' }        // истекли 600 мс проворота
  | { type: 'REVEAL_DONE' }       // истекла пауза lockOpen/lockFail
  | { type: 'TICK'; deltaSeconds: number };

export function createState(config: Config): State;
export function reduce(state: State, event: Event, config: Config): State;
export function normalize(s: string): string;
export function compareAnswer(input: string, answer: string): boolean;
export function resolveExpected(lock: Lock): string;
export function buildResult(state: State, config: Config): CompleteResult;
```

Обязательный набор тестов в `engine.test.ts`:

| # | Проверка |
|---|---|
| 1 | `normalize`: trim, регистр, `ё→е`; `compareAnswer('  ЧЁТЫРЕ ', 'четыре') === true` |
| 2 | Пустой `locks[]`: `START` из `intro` → сразу `victory`, `won: true` (§6.1) |
| 3 | Последовательное вскрытие: три верных `SUBMIT` → `victory`, `score === сумма points` |
| 4 | Ошибка: `currentLock` не меняется, `mistakes++`, `score -= errorPenalty` |
| 5 | `maxAttempts = 1`, ошибка на первом из трёх ригелей → `defeat` (§6.7) |
| 6 | `maxAttempts = 0`: десять ошибок подряд — всё ещё `lock`, `attemptsLeft` не убывает |
| 7 | `score` не уходит в минус: `buildResult` при `points=0, errorPenalty=100` даёт `score: 0` |
| 8 | Победа vs таймер: `SUBMIT`(верный) + `CHECK_DONE` на последнем ригеле, `timeLeft = 0` → `victory`, не `defeat` (§3.5) |
| 9 | `TICK` в `victory`/`defeat` не меняет состояние |
| 10 | `SUBMIT` в фазе `checking` игнорируется (инвариант даблклика, §6.4) |
| 11 | `TICK` до нуля в `checking` с неверным ответом → `defeat` (§6.6) |
| 12 | `resolveExpected`: для `hold-button` → `'hit'`, для `checkbox-wall` → `params.pattern`, иначе → `answer` |
| 13 | `buildResult.details.styleTag`: `medvezhatnik` при `mistakes === 0`, отсутствует при поражении |

### 5.5 `index.ts` — DOM-обвязка

Отвечает ровно за три вещи и ни за что больше:

1. **Каркас сейфа.** Дверь, ряд индикаторов ригелей, HUD, слот под виджет, кнопка «ВВОД»,
   кнопка mute. Экраны `intro`/`victory`/`defeat`. Всё по `STYLE.md`: угловатые панели, тонкие двойные
   рамки, срезанные углы, радиус `0–3px`, переходы `100–220 мс`, CRT-оверлей **не** дублируется
   (он платформенный, живёт уровнем выше).
2. **Мост FSM ↔ DOM.** Держит `State`, диспатчит события, перерисовывает по изменению фазы.
   Таймеры (`600 мс` на `checking`, `~500 мс` на reveal, секундный `TICK`) — здесь, через `setTimeout` /
   `requestAnimationFrame`. Все идентификаторы таймеров складываются в один массив и гасятся в `destroy()`.
3. **Монтирование виджетов.** По входу в `lock(i)`: взять фабрику из реестра, `mount()` в слот,
   при ошибке — `reset()`, при переходе к следующему ригелю — `destroy()` старого и `mount()` нового.
   Один смонтированный виджет одновременно, никакого пула.

Плюс вызовы платформенного контракта: `onProgress` при смене ригеля, ровно один `onComplete`
в терминальном состоянии, `destroy()` из `init()` (см. `minigame_contract.md`).

## 6. Edge cases

### 6.1 Пустой `locks[]` → мгновенная победа

Сейф без ригелей уже открыт. `START` из `intro` при `locks.length === 0` переводит FSM сразу в `victory`,
минуя `lock`/`checking`. Результат — `{ score: 0, won: true, details: { locksOpened: 0, locksTotal: 0 } }`.

Никакого экрана ошибки, никакого «игра не настроена». Это валидная (пусть и бессмысленная) конфигурация,
и она обязана честно завершаться — иначе игрок застревает в мини-игре без возможности выйти,
а платформа ждёт `onComplete`, которого не будет. DOM-слой при этом всё же показывает экран `victory`
с `prizeImage` — визуально это выглядит как «дверь была не заперта», что даже уместно.

### 6.2 `answer` вне `[min, max]` у `mega-slider`

Если админ задал `answer: "15000"` при `params: { min: 0, max: 10000 }`, слайдер физически не может
выдать правильное значение — ригель непроходим.

Решение: при `mount` виджет **автоматически расширяет диапазон**, чтобы включить `answer`:

```ts
const target = Number(ctx.answer);
if (Number.isFinite(target)) {
  min = Math.min(min, target);
  max = Math.max(max, target);
}
```

Расширение молчаливое, без предупреждения игроку (в консоль — `console.warn` для админа).
Если `answer` вообще не число (`"много"`), диапазон остаётся как задан — ригель непроходим, но это
уже не техническая, а смысловая ошибка конфига, и чинить её автоматикой нечем. Такой случай ловится
тест-запуском из админки (`docs/platform.md`, §7.7).

Аналогичная защита действует у `haystack-dropdown`: если `answer` отсутствует в `params.options`,
он **добавляется** в список перед перемешиванием. Список без правильного ответа — самая частая
опечатка админа и единственный по-настоящему непроходимый баг конфига.

### 6.3 Победа в гонке с таймером

Разобрано в §3.5. Кратко: `TICK` обрабатывается только в фазах `lock` и `checking`; терминальные
и «показательные» фазы к нему невосприимчивы. Победа, достигнутая в том же кадре, что и обнуление
таймера, выигрывает — потому что переход в `lockOpen` происходит на событии `CHECK_DONE`, а `TICK`
после этого уже не может ничего изменить.

### 6.4 Даблклик по «ВВОД» во время `checking`

Двойная защита, обе обязательны:

- **DOM:** кнопка «ВВОД» получает атрибут `disabled` на входе в `checking` и теряет его на входе
  в следующий `lock`. Плюс визуально погашенный виджет с `pointer-events: none`.
- **FSM:** событие `SUBMIT` в фазе `checking` возвращает состояние **без изменений** (тест №10 в §5.4).

Одной DOM-защиты недостаточно: `selfSubmit`-виджет (§5.2) вообще не имеет кнопки, и его
`pointerup` может прийти из жеста, начатого до входа в `checking`. Защита в редьюсере покрывает оба
случая единообразно и не зависит от того, ничего ли забыли задизейблить в вёрстке.

### 6.5 Серия ошибок на одном виджете

Игрок может ошибаться на одном ригеле сколько угодно раз (при `maxAttempts = 0` — буквально бесконечно).
Каждая ошибка вызывает `widget.reset()` с **новым** случайным состоянием (§3.2): новая перестановка
списка, новая раскладка клавиатуры, новая стартовая позиция ползунка. Два подряд одинаковых
расклада возможны только по случайности и не считаются багом.

Что при этом **не** меняется: `question`, `answer`, тип виджета, `params`. Игрок штрафуется на
`errorPenalty` каждый раз — это единственный накапливающийся эффект. Никакого «усложнения после
N ошибок» и никакого «упрощения из жалости» нет: игра не адаптируется, она просто ждёт.

Практическое следствие для админа: при `maxAttempts = 0` и `timeLimitSeconds = 0` проиграть
невозможно вообще — такая конфигурация уместна для сюжетно-обязательных сейфов, где важно только
дойти до конца.

### 6.6 Таймер истёк во время `checking`

`TICK` обрабатывается в фазе `checking` (в отличие от reveal-фаз) — таймер не «замораживается» на
600 мс, иначе игрок мог бы растягивать партию спамом сабмитов.

Порядок разрешения:

1. `timeLeft` достигает `0` в фазе `checking` → FSM **запоминает** флаг `timeExpired`, но фазу
   не меняет: проверка уже идёт, её результат надо дождаться.
2. Приходит `CHECK_DONE`:
   - ответ **верный** и это последний ригель → `victory` (§3.5, победа приоритетнее);
   - ответ **верный**, но ригели ещё остались → `defeat` (продолжать нечего, время вышло);
   - ответ **неверный** → `defeat`.

То есть истёкший таймер не убивает игрока посреди анимации, но и не прощается — он ждёт результата
проверки и добивает, если это была не победная проверка. Экран `defeat` в этом случае показывает
«ВРЕМЯ ВЫШЛО», а не «ТРЕВОГА».

### 6.7 `maxAttempts` исчерпан на среднем ригеле

Пул попыток общий, поэтому исчерпать его можно где угодно. Если `attemptsLeft` становится `0` на ошибке
третьего ригеля из десяти — это `defeat` немедленно, без каких-либо поблажек за уже вскрытые ригели.

Последовательность: `checking` → `lockFail` (показывается ~500 мс, счётчик попыток обнуляется) →
`defeat`, а не `lock(i)`. Игрок должен увидеть, что именно эта ошибка была последней — переход в `defeat`
сразу, без промежуточного показа, читается как баг.

Очки за вскрытые ригели **сохраняются** в результате: `onComplete({ score: 130, won: false, ... })` —
абсолютно легальный исход. Платформа запишет `bestScore` (`docs/platform.md`, §6), но `won` останется
`false`, и зависимые игры не разблокируются.

### 6.8 Прочие мелочи

| Ситуация | Поведение |
|---|---|
| `points` отрицательный или отсутствует | Трактуется как `0`; ригель вскрывается, очков не даёт |
| `errorPenalty` больше накопленных очков | `score` уходит в минус внутри состояния, но `buildResult` клампит к `0` (§3.3) |
| `gridSize² ≠ длине pattern` у `checkbox-wall` | `pattern` дополняется нулями / обрезается до `gridSize²`, `console.warn` |
| `params.options` содержит дубликаты | Дедуплицируются при монтировании — иначе два одинаковых пункта выглядят как баг рендера |
| `targetSeconds` меньше `toleranceMs/1000` у `hold-button` | Окно попадания начинается с нуля — любое отпускание засчитывается. Не чиним: это валидный «лёгкий режим» |
| Игрок вышел через платформенную кнопку «ВЫЙТИ» | `onExit()` вызывает платформа, не игра; игра получает `destroy()` и обязана погасить все таймеры и `window`-слушатели виджетов |
| `config.muted === true` | Ни один `playSound` не звучит; кнопка mute в UI стартует в положении «выкл» |

| Этап | Состав | Срок |

| **MVP** | FSM + `engine.test.ts`, каркас сейфа, 5 простых виджетов: `mega-slider`, `haystack-dropdown`, `shuffle-keyboard`, `plus-minus`, `checkbox-wall` | 2 дня |
| **Полная версия** | + 4 «физических» виджета с инерцией и жестами: `rotary-dial`, `safe-drum`, `hold-button`, `number-as-words` | 4–5 дней суммарно |

Разделение проходит ровно по границе «нужна ли виджету физика»: первые пять — это состояние плюс
обработчик клика, вторые четыре требуют RAF-петли, работы с углами/инерцией и `window`-слушателей драга.
MVP уже играбелен и содержит весь комедийный посыл; вторая четвёрка добавляет разнообразие,
без которого игра из шести ригелей становится однообразной.
