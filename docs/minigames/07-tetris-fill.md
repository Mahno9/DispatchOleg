# Мини-игра 07: tetris-fill (заполнение силуэта)

`minigame_id`: `tetris-fill`. Тип реализации — **DOM-сетка** (без canvas, без игрового цикла;
перерисовка по событиям ввода). Базовый контракт — `minigame_contract.md`, расширения платформы
(`onProgress`, `details`) — `docs/platform.md` §3. Оформление — `STYLE.md`.

Суть: админ рисует силуэт на сетке, движок при запуске сам разбивает силуэт на тетромино, игрок
по одной перетаскивает выданные детали на их места. Это не тетрис — падения, гравитации и линий тут
нет; это **jigsaw**: каждая деталь имеет ровно одно правильное место.

Репозиторий:

```
minigames/tetris-fill/
  schema.json
  vite.config.ts
  src/
    engine.ts        # чистая логика: парсинг силуэта, разбиение, повороты, сравнение, очки (vitest)
    engine.test.ts
    index.ts         # init/destroy, DOM-сетка, drag, лоток, подсказка
```

## 1. Геймплей и состояния

### 1.1 Экран

Рабочая область делится на две зоны:

| Зона | Содержимое |
|---|---|
| **Поле** (центр, основная площадь) | Сетка `width × height`. Клетки силуэта (`#`) — контурные ячейки с приглушённым бирюзовым бордюром и чуть более светлой поверхностью (`#0A3435`). Клетки вне силуэта (`.`) — фон терминала без рамки, они не участвуют ни в чём. Заполненные клетки закрашиваются цветом установленной детали. |
| **Лоток** (справа либо снизу — по месту, панель фиксированной ширины) | Ровно одна текущая деталь. Под ней — счётчик `ДЕТАЛЬ N / M`, счётчик ошибок и подсказка по управлению (`R — ПОВОРОТ`). |

Силуэт-мишень виден целиком с первого кадра — игрок сразу понимает масштаб задачи. Уже уложенные
детали остаются на поле закрашенными, с тонким разделителем по границе между соседними деталями
(чтобы читалось, что фигура собрана из кусков, а не залита сплошняком).

### 1.2 Порядок подачи

Детали выдаются **по одной**, в фиксированном порядке — снизу-вверх, слева-направо по нижней-левой
клетке каждой детали (см. §5b). Пока текущая деталь не установлена, следующая не появляется.
Очереди/превью «следующая деталь» нет — она была бы бесполезна, так как выбора у игрока нет.

Порядок подачи совпадает с порядком, в котором детали нашёл алгоритм разбиения, поэтому визуально
силуэт заполняется снизу вверх, слой за слоем.

### 1.3 Состояния

```
        ┌──────────────────────────┐
        │ ДЕТАЛЬ В ЛОТКЕ            │◀──── отклонена (возврат)
        │ (случайная ориентация)    │
        └────────────┬─────────────┘
             mousedown│
                      ▼
        ┌──────────────────────────┐
        │ ПЕРЕТАСКИВАНИЕ            │  R / ПКМ — поворот на 90° CW
        │ (деталь следует за курсором,│  подсветка клеток под деталью
        │  привязка к сетке)         │
        └────────────┬─────────────┘
              mouseup│
          ┌──────────┴──────────┐
          ▼                     ▼
  множество клеток        не совпало
  == место из разбиения   │
          │               ▼
          ▼        ┌────────────────────┐
  ┌────────────────┐│ ОТКЛОНЕНО           │
  │ УСТАНОВЛЕНА     ││ errors++            │
  │ (закрашена,     ││ янтарная вспышка    │
  │  звук place)    ││ звук error          │
  └───────┬────────┘│ возврат в лоток     │
          │         └────────────────────┘
          ▼
   осталось деталей? ── да ──▶ выдать следующую
          │ нет
          ▼
      ЗАВЕРШЕНИЕ
```

Промежуточных состояний «деталь лежит рядом с полем» нет: любое отпускание мыши — это попытка
установки (либо принята, либо отклонена с возвратом в лоток). Отпускание за пределами сетки
трактуется как отклонение **без** инкремента `errors` — это отмена, а не ошибка (иначе случайный
промах мимо поля наказывает игрока за моторику, а не за головоломку).

### 1.4 Завершение

Игра завершается, когда установлена последняя деталь — силуэт заполнен на 100 %. Проигрыша нет:
таймера обратного отсчёта, лимита ошибок и условий провала не существует. После установки последней
детали проигрывается `win`, вся фигура на ~400 мс подсвечивается бирюзовым свечением, затем
вызывается `onComplete({ score, won: true, details })`.

Прогресс во время игры уходит в нижнюю панель терминала:

```js
callbacks.onProgress?.(`СОБРАНО ${placed} / ${total}`, Math.round((placed / total) * 100));
```

Вызывается при старте и после каждой успешной установки (не каждый кадр — по контракту платформы).

## 2. Управление

Игра рассчитана на мышь ноутбука (терминал — десктопный, тач не целевой сценарий, но базовые
`pointer`-события дают тач бесплатно, поэтому используются `pointerdown/move/up`, а не `mouse*`).

| Действие | Ввод | Поведение |
|---|---|---|
| Взять деталь | `pointerdown` по детали в лотке | Деталь «прилипает» к курсору, звук `pickUp`, курсор `grabbing`. Точка захвата запоминается, чтобы деталь не прыгала центром под курсор. |
| Перемещать | движение указателя | Деталь рендерится поверх поля; её позиция округляется к ближайшей ячейке сетки (snap). Клетки поля под деталью подсвечиваются: бирюзовым — если попадают в силуэт и свободны, приглушённо-серым — иначе. Подсветка **не** сообщает, правильное ли это место (иначе jigsaw превращается в перебор по индикатору). |
| Повернуть | клавиша `R` **или** правая кнопка мыши | Поворот на 90° по часовой стрелке вокруг центра ограничивающего прямоугольника детали. Доступны 4 ориентации: 0°/90°/180°/270°. Работает и в лотке, и во время перетаскивания. `contextmenu` подавляется `preventDefault()` на контейнере игры. |
| Отпустить (попытка установки) | `pointerup` | См. §1.3. |
| Отменить взятие | `Esc` либо отпускание вне сетки | Деталь возвращается в лоток, `errors` не растёт. |

**Зеркалирования нет.** Доступны только повороты — 4 ориентации, не 8. Это принципиально: S/Z- и
J/L-тетромино являются зеркальными парами, и разрешённое отражение позволило бы подставить S вместо Z,
сделав часть мест взаимозаменяемыми. Отражение не назначено ни на какую клавишу и не поддерживается.

**Начальная ориентация.** При выдаче детали в лоток её ориентация выбирается случайно из 4
(`randomizeRotation: true`, значение по умолчанию) — игрок обязан довернуть деталь сам. При
`randomizeRotation: false` деталь выдаётся сразу в правильной ориентации (той, что в разбиении), и
задача сводится к чистому позиционированию — облегчённый режим для младшей аудитории.
Случайность здесь — единственный источник недетерминизма в игре и **не влияет** на разбиение силуэта
(§5b), поэтому набор мест и порядок подачи одинаковы при каждом запуске.

Клавиатурные обработчики вешаются на `container` (с `tabindex="0"` и фокусом при монтировании), а не на
`window`/`document` — по требованию изоляции контракта. Для надёжного завершения перетаскивания при
уходе курсора за пределы окна используется `setPointerCapture` на элементе детали, что также снимает
необходимость в глобальных слушателях.

## 3. Победа / пенальти

### 3.1 Поражения не бывает

`won` — всегда `true`. Игра заканчивается только одним способом: силуэт заполнен. Это осознанное
решение: `tetris-fill` — головоломка на аккуратность и скорость, а не на выживание; при этом `won`
управляет разблокировкой следующих игр (`required_game_ids`, `docs/platform.md` §5), и запирать цепочку
за пространственную задачку не нужно. Разница между хорошим и плохим прохождением выражается
исключительно в `score`.

`onExit()` вызывается только если платформа закрыла игру кнопкой «ВЫЙТИ» или конфиг оказался
невалидным (§6).

### 3.2 Очки

```
score = max(0, round(scoreForElapsed(scoreThresholds, elapsedSeconds)) - errorPenalty * errors)
```

- `elapsedSeconds` — время от монтирования игры (первый кадр после `init`) до установки последней
  детали. Пауз в игре нет.
- `scoreForElapsed` — **уже существующая функция**, переносится в `engine.ts` без изменений из
  `minigames/sliding-puzzle/src/engine.ts` (та же функция используется в `find-object`). Это
  кубический сплайн Эрмита по списку точек `{maxSeconds, points}`, отсортированному по времени, с той же
  математикой, что и редактор кривой в админке — то есть админ видит в редакторе ровно ту кривую, по
  которой начисляются очки. Вне диапазона кривой значение зажимается первым/последним значением:
  быстрее самой левой точки — максимум очков, медленнее самой правой — значение последней точки
  (чтобы «за очень медленное прохождение» давать 0, админ добавляет финальную точку с `points: 0`).
  Пустой список даёт 0. Смысл прост: **чем быстрее собран силуэт, тем больше очков**, причём кривая, а
  не ступеньки — резких обрывов на секунду позже порога не происходит.
- `errorPenalty * errors` вычитается из результата кривой. Итог зажимается снизу нулём — контракт
  требует `score >= 0`.

### 3.3 Ошибки

`errors` инкрементируется при **неверной попытке установки**: игрок отпустил деталь над сеткой, но
множество занимаемых ею клеток не равно множеству клеток её места из разбиения. Сюда попадают все
случаи: неверная позиция, неверный поворот, наложение на уже установленную деталь, выход за границы
силуэта. Реакция:

1. Деталь мгновенно возвращается в лоток (в той ориентации, в которой была, — переворачивать её обратно
   было бы издевательством).
2. Клетки, на которые метил игрок, дают янтарную вспышку (`#E9A928`, 160 мс, без сдвига layout —
   меняется только `border-color`/`background`, по `STYLE.md` «Ошибка или тревога»).
3. Проигрывается звук `error`.
4. `errors++`, счётчик в лотке обновляется.

Отмена (отпускание вне сетки, `Esc`) ошибкой не считается.

### 3.4 Подсказка-призрак

Когда **суммарное** число ошибок за партию достигает `hintAfterErrors` (по умолчанию 3), включается
режим подсказки: место текущей детали рисуется на поле призраком — пунктирный янтарный контур по
границе места, без заливки, с ориентацией, соответствующей разбиению. Дополнительно проигрывается звук
`hint` (один раз, в момент включения режима).

Порог считается по накопленным за всю партию ошибкам, а не по подряд идущим: как только он пройден,
подсказка остаётся включённой до конца игры и показывается для каждой следующей детали. Это
намеренно — игрок, у которого не получается, не должен снова уходить в тупик, «искупив» подсказку
парой удачных ходов. Подсказка не отменяет штрафа: `errors` уже начислены и продолжают начисляться,
если игрок промахивается даже с призраком.

`hintAfterErrors: 0` — подсказка включена с самого начала (обучающий режим). Значение больше
количества деталей практически отключает подсказку.

### 3.5 Результат

```js
callbacks.onComplete({
  score,
  won: true,
  details: {
    errors,                     // число ошибочных попыток
    pieces: total,              // сколько деталей было в разбиении
    elapsedSeconds,             // затраченное время, целое
    styleTag: errors === 0 ? 'precise' : 'rough',
  },
});
```

`details` сохраняется платформой в `gameResults[gameId].details`; `styleTag` может ветвить пост-диалог
через `style_dialogue_map` (`docs/platform.md` §3.3) — «собрал с первого раза, ни одной ошибки» против
«кое-как, но собрал». Если ветвление не настроено, поле просто игнорируется.

## 4. Настройки админки (`schema.json`)

| Поле | Тип | `x-type` | По умолчанию | Описание |
|---|---|---|---|---|
| `shape` | object | **`grid-paint`** | 4×4 «плюс» | Силуэт-мишень: `{width, height, rows}`. Уникальный виджет, см. §5a. Обязательное. |
| `scoreThresholds` | array | `curve` | см. ниже | Кривая очков от времени: точки `{maxSeconds, points}`. По оси X редактора — секунды, по оси Y — очки. Обязательное. |
| `errorPenalty` | integer | — | `5` | Сколько очков снимается за одну ошибочную попытку установки. `0` — штрафа нет. |
| `hintAfterErrors` | integer | — | `3` | После скольких суммарных ошибок включается призрак-подсказка. `0` — сразу. |
| `randomizeRotation` | boolean | — | `true` | Выдавать деталь в случайной из 4 ориентаций. `false` — деталь сразу повёрнута правильно. |
| `sounds.pickUp` | string | `asset:audio` | — | Взятие детали из лотка. |
| `sounds.place` | string | `asset:audio` | — | Успешная установка. |
| `sounds.error` | string | `asset:audio` | — | Отклонённая установка. |
| `sounds.hint` | string | `asset:audio` | — | Включение подсказки. |
| `sounds.win` | string | `asset:audio` | — | Силуэт собран. |

Все звуки — необязательные; отсутствующий звук просто не проигрывается. Значение поля `asset:audio` —
`WeightedAudio[]`, воспроизведение через `pickSound(val)` (базовый контракт). `config.muted`
учитывается при инициализации, кнопка mute присутствует в углу поля.

### 4.1 Формат `shape` в `config_json`

```json
{
  "shape": {
    "width": 4,
    "height": 4,
    "rows": [
      "####",
      "#..#",
      "#..#",
      "####"
    ]
  }
}
```

- `rows` — массив ровно из `height` строк, каждая длиной ровно `width`.
- Символ `#` — клетка силуэта (её нужно заполнить деталью), символ `.` — пустое место (не часть фигуры).
  Любой другой символ — ошибка конфигурации.
- Система координат: `x` — колонка `0..width-1` слева направо, `y` — строка `0..height-1` **сверху
  вниз**, то есть `rows[y][x]`. «Нижняя» клетка — с максимальным `y`.
- Ограничение: `1 ≤ width ≤ 16`, `1 ≤ height ≤ 16`, число `#` — от 1 до 60 (см. §5b про скорость).

Пример выше — рамка 4×4 с дыркой 2×2 в центре, 12 клеток, разбивается ровно на 3 тетромино:

```
Силуэт:        Разбиение (буква = деталь):
####           BBCC
#..#           B..C
#..#           B..C
####           AAAA
```

Ещё пример, 5×5, несвязная фигура (два острова) — валидна:

```
##...
##...
.....
..###
...##
```

Левый остров — 4 клетки (O-тетромино), правый — 5 клеток (тетромино + одиночная клетка).

## 5. Реализация

### 5a. Виджет `grid-paint` в SchemaForm админки

**Новое расширение `x-type` сверх базового контракта GameService.** В `minigame_contract.md`
перечислены `asset:image`, `asset:audio`, `asset:gif`, `curve`, `weighted-list` — виджета для
рисования сетки там нет, он вводится этой мини-игрой и добавляется в общий реестр виджетов
SchemaForm админки DispatchOleg (а значит, доступен и будущим играм, работающим с сетками).

Схема поля:

```json
"shape": {
  "type": "object",
  "title": "Силуэт",
  "x-type": "grid-paint",
  "x-max-size": 16,
  "required": ["width", "height", "rows"],
  "properties": {
    "width":  { "type": "integer", "minimum": 1, "maximum": 16 },
    "height": { "type": "integer", "minimum": 1, "maximum": 16 },
    "rows":   { "type": "array", "items": { "type": "string" } }
  }
}
```

Состав виджета:

1. **Контролы размера** — два числовых поля `Ширина` / `Высота` (1…16, верхняя граница берётся из
   `x-max-size`, дефолт 16). Изменение размера сохраняет уже нарисованное: сетка обрезается справа/снизу
   при уменьшении и дополняется пустыми клетками при увеличении. Уменьшение, которое отрежет
   закрашенные клетки, требует подтверждения (обычное inline-предупреждение в форме, не `confirm()`).
2. **Холст-сетка** — таблица `width × height` квадратных ячеек. Клик по ячейке переключает её
   `пусто ↔ заполнено`. Поддерживается «мазок»: `pointerdown` задаёт режим (закрашиваем или стираем — по
   исходному состоянию первой ячейки), протаскивание применяет этот режим ко всем задетым ячейкам.
   Оформление — по `STYLE.md`: заполненная ячейка — бирюзовая поверхность с контуром, пустая — фон
   терминала с еле заметной сеточной линией, радиус скругления 0.
3. **Кнопки** `ОЧИСТИТЬ` и `ИНВЕРТИРОВАТЬ` — мелочь, но экономит админу десятки кликов.
4. **Превью авторазбиения** — рядом с холстом вторая сетка того же размера, где показан результат
   того же самого алгоритма из `engine.ts` (§5b): каждая деталь залита своим цветом из
   палитры-циклички (бирюзовый / янтарный / оранжевый / бежевый и их приглушённые варианты, соседние
   детали гарантированно разных цветов в пределах цикла), номер над деталью — её порядковый номер
   подачи. Пересчитывается при каждом изменении холста (debounce ~120 мс). Под превью — строка
   `ДЕТАЛЕЙ: N (тетромино M, мелких K)`. Это единственный способ для админа заранее увидеть, во что
   превратится его силуэт: фигура из 13 клеток неизбежно даст «хвост» из мелкой детали, и это лучше
   увидеть до сохранения.
   Алгоритм разбиения импортируется из пакета мини-игры (`minigames/tetris-fill/src/engine.ts`) —
   одна реализация на админку и игру, расхождение превью и реальности исключено by construction.
5. **Валидация** — если закрашенных клеток нет вовсе, виджет показывает ошибку `СИЛУЭТ ПУСТ` и
   блокирует сохранение игры (§6). Если клеток больше 60 — предупреждение о возможной задержке
   разбиения (мягкое, не блокирующее — граница эмпирическая).

Значение, которое виджет пишет в `config_json` — ровно объект `{width, height, rows}` из §4.1
(строки, а не булев массив: так конфиг остаётся читаемым глазами в БД и в экспорте).

### 5b. `engine.ts` — разбиение и правила

Чистый модуль без DOM, полностью покрытый vitest. Публичное API:

```ts
export interface Shape { width: number; height: number; rows: string[] }
export interface Cell { x: number; y: number }
export interface Piece { index: number; cells: Cell[] }   // абсолютные координаты места

export function parseShape(shape: Shape): Cell[];          // бросает на невалидном силуэте
export function partition(cells: Cell[]): Piece[];         // порядок = порядок подачи
export function rotate(cells: Cell[], turns: number): Cell[];
export function sameCells(a: Cell[], b: Cell[]): boolean;
export function scoreForElapsed(thresholds: ScoreThreshold[], elapsedSeconds: number): number;
```

#### Разбиение — детерминированный backtracking с branch-and-bound

Разбиение **не хранится в конфиге** и **не редактируется админом**. Оно пересчитывается из `shape` при
каждом `init` (и при каждой перерисовке превью в админке). Алгоритм детерминирован — без RNG, без
зависимости от порядка ключей объекта, — поэтому один и тот же силуэт всегда даёт одно и то же
разбиение и один и тот же порядок подачи. Хранить его в БД было бы лишним состоянием, способным
разъехаться с `shape` при редактировании.

Ход алгоритма:

1. **Точка ветвления фиксирована**: на каждом шаге берётся **самая нижняя-левая непокрытая клетка**
   (максимальный `y`, при равенстве — минимальный `x`). Это ключевое ограничение: перебирать
   *какую* клетку покрывать не нужно — она обязана быть покрыта какой-то деталью, а значит перебор идёт
   только по деталям, содержащим её. Это срезает факториальную часть пространства поиска.
2. **Перебор деталей**: все связные (по стороне) подмножества непокрытых клеток размера `k`,
   содержащие якорную клетку. `k` перебирается в порядке **4 → 3 → 2 → 1**. Размеры 3/2/1
   рассматриваются только если ни один вариант с бо́льшим `k` не привёл к решению — так число деталей
   минимизируется, то есть доля настоящих тетромино максимизируется.
   Подмножества генерируются обычным наращиванием по соседям (DFS с дедупликацией по каноническому
   множеству клеток) — таблицы из 19 ориентаций семи тетромино не нужны, тот же код обслуживает и
   мелкие детали. Порядок обхода соседей фиксирован (вверх, влево, вправо, вниз), что и даёт
   детерминизм.
3. **Отсечения (branch-and-bound)**:
   - **Нижняя оценка по компонентам связности**: непокрытая область разбивается на компоненты
     флуд-филлом, оценка снизу = `Σ ceil(|компонента| / 4)`. Если `текущее_число_деталей + оценка >=
     лучшего_найденного`, ветка отбрасывается. Эта оценка сильно лучше наивной `ceil(остаток/4)`:
     компонента из 1–3 клеток немедленно штрафует ветку, отрезавшую «огрызок».
   - **Ранний выход по оптимуму**: если найдено решение с `ceil(всего_клеток / 4)` деталями, оно
     доказуемо оптимально — поиск останавливается немедленно. Для подавляющего большинства силуэтов
     (все, у которых существует полное покрытие тетромино) это происходит на первом же спуске, и
     backtracking фактически вырождается в жадный проход.
4. **Порядок подачи** — это порядок, в котором детали были зафиксированы в найденном решении, то есть
   ровно «снизу-вверх, слева-направо по нижним-левым клеткам деталей». Отдельная сортировка не нужна:
   якорь каждой следующей детали строго «позже» предыдущего в порядке сканирования снизу-вверх.
5. **Тупик при игре невозможен по построению**: детали не пересекаются и в сумме дают ровно силуэт,
   каждая ставится на своё место, места не мешают друг другу. Порядок подачи — вопрос эстетики
   (заполнение растёт снизу вверх), а не корректности: игра решаема при любом порядке.

**Скорость.** Глубина дерева ≤ `ceil(N/4)` (для `N = 60` это 15). Ветвление на шаге ограничено числом
тетромино, содержащих фиксированную клетку и лежащих в непокрытой области; в открытом поле это
несколько десятков, но на реальном силуэте (клетка — нижняя-левая, значит вся деталь лежит «выше и
правее» уже покрытого) — единицы. В сочетании с ранним выходом по оптимуму фигуры до 60 клеток
разбираются за единицы миллисекунд — задержки при `init` не заметны, Web Worker не нужен.

> `ponytail:` на всякий случай в поиск встроен счётчик посещённых узлов с потолком (≈200 000). При его
> исчерпании возвращается лучшее найденное на этот момент решение (оно всегда существует — первый
> спуск всегда доходит до конца, так как `k=1` покрывает любую клетку). Апгрейд, если когда-нибудь
> упрёмся: DP по профилю/broken profile для сеток ≤16 в ширину.

#### Jigsaw-сравнение

У каждой детали есть её место — множество абсолютных клеток `piece.cells`. Игрок держит деталь в
какой-то из 4 ориентаций и отпускает над какой-то ячейкой. Движок:

1. Берёт нормализованную форму детали (`rotate(piece.cells, turns)` — поворот `(x, y) → (−y, x)`
   нужное число раз с последующей нормализацией: вычитанием минимальных `x`/`y`).
2. Прибавляет смещение — координаты ячейки, в которую попал «якорь» детали при snap.
3. Сравнивает получившееся множество клеток с `piece.cells` (`sameCells` — равенство множеств:
   сравнение длин + сравнение отсортированных пар, порядок клеток внутри детали не важен).

Совпало — установка принимается, не совпало — отклонение. Из этого правила бесплатно следует нужное
поведение симметрий: у O-тетромино все 4 ориентации дают одно и то же множество, у I/S/Z повороты на
0° и 180° совпадают — любая из «одинаковых» ориентаций принимается автоматически, потому что
сравниваются клетки, а не индекс поворота. Отдельного кода для симметричных фигур нет.

Проверять попадание «в силуэт», «не поверх занятого», «не за границей» отдельно не требуется — все эти
случаи не проходят сравнение множеств и обрабатываются одной веткой «отклонено».

#### `index.ts` — DOM-слой

- **Монтирование**: `init` строит внутри `container` статическую разметку — панель поля и панель лотка
  (угловатые панели с двойной рамкой, `border-radius: 0`, по `STYLE.md`), сетку из `width × height`
  `<div>`-ячеек (при 16×16 это 256 элементов — DOM справляется без вопросов), кнопку mute. Размер
  ячейки вычисляется от размеров `container` (`ResizeObserver` на контейнере, ячейка квадратная,
  ограничена сверху ~48 px), чтобы поле вписывалось в рабочую область терминала без скролла.
- **Рендер**: полная перерисовка не нужна — точечно меняются классы затронутых ячеек. Игровой цикл
  и `requestAnimationFrame` отсутствуют: обновления происходят по событиям ввода, `rAF` используется
  только для троттлинга позиции детали при перетаскивании.
- **Деталь**: отдельный абсолютно позиционированный элемент из `k` квадратов; во время перетаскивания
  двигается через `transform: translate()` (без reflow), snap к сетке — округлением координат.
- **Подсказка-призрак**: слой поверх ячеек места текущей детали — пунктирный янтарный контур
  (`outline`/`box-shadow: inset`, чтобы не смещать layout), появляется мгновенным переходом ~150 мс.
- **Ошибка**: класс `.flash-error` на задетых ячейках со снятием по `animationend` (без таймеров,
  которые надо было бы чистить в `destroy`).
- **Звук**: `pickSound(config.sounds.*)` и один переиспользуемый `<audio>`-пул внутри контейнера;
  глушится при `config.muted` и по кнопке mute.
- **`destroy()`**: снимает `ResizeObserver`, отменяет висящий `rAF`, снимает `pointer capture`,
  очищает `container.innerHTML`, обнуляет ссылки на разбиение. Глобальных слушателей (`window`,
  `document`) не регистрируется вовсе, поэтому чистить в `destroy` практически нечего — это
  сознательное следствие §2.

#### Тесты (`engine.test.ts`, vitest)

| Что проверяем | Ожидание |
|---|---|
| Разбиение покрывает силуэт полностью | Объединение всех `piece.cells` == множество клеток силуэта, попарные пересечения пусты |
| Каждая деталь связна и имеет размер 1…4 | Проверка флуд-филлом внутри детали |
| Силуэт, кратный 4 и покрываемый тетромино (например, 4×4 квадрат, рамка из §4.1) | Все детали ровно по 4 клетки, число деталей == `N/4` |
| Несвязная фигура (два острова) | Валидна, детали не пересекают острова, покрытие полное |
| Фигура из 1 клетки | Ровно одна деталь размера 1 |
| Фигура из 2 клеток (смежных и несмежных) | Одна деталь размера 2 / две детали размера 1 |
| Фигура с дыркой (рамка 4×4) | Клетки дырки не входят ни в одну деталь; покрытие полное |
| Пустая фигура (нет `#`) | `parseShape` бросает `EmptyShapeError` |
| Невалидный формат (длина строки ≠ `width`, число строк ≠ `height`, посторонний символ) | `parseShape` бросает |
| Детерминизм | Два вызова `partition` на одном силуэте дают идентичный результат (включая порядок) |
| Порядок подачи | Якоря деталей монотонны по `(−y, x)` — снизу-вверх, слева-направо |
| Скорость | Силуэт 60 клеток (например, 6×10 сплошной) разбирается быстрее 50 мс |
| `rotate` | 4 поворота возвращают исходную нормализованную форму; O-тетромино инвариантен ко всем поворотам |
| `sameCells` | Не зависит от порядка клеток; различает S и Z |
| `scoreForElapsed` | Переносится вместе с существующим набором тестов из `sliding-puzzle` |

## 6. Edge cases

| Случай | Поведение |
|---|---|
| **Несвязная фигура** (несколько отдельных островов клеток) | Полностью валидна. Алгоритм не требует связности: он просто берёт самую нижнюю-левую непокрытую клетку, а к какому острову она относится — неважно. Острова разбираются последовательно, снизу вверх; порядок подачи проходит остров за островом. Оценка снизу по компонентам связности (§5b) на несвязных фигурах работает особенно хорошо. |
| **Фигура из 1–2 клеток** | Тривиально корректна: одна деталь размера 1 (или 2, если клетки смежны; несмежные дают две детали по 1). Игра из одного хода — законная конфигурация, годится для обучающего QR-кода. Никаких особых веток в коде нет — `k` просто опускается до подходящего размера. |
| **Полностью пустая фигура** (ни одного `#`) | **Ошибка конфигурации.** Два рубежа: (1) виджет `grid-paint` показывает `СИЛУЭТ ПУСТ` и не даёт сохранить игру в админке — это основной барьер; (2) на случай конфига, залитого мимо формы (импорт, ручная правка БД, старая запись), `parseShape` при `init` бросает; `index.ts` ловит, рисует в контейнере угловатую панель тревоги «ОШИБКА КОНФИГУРАЦИИ: СИЛУЭТ ПУСТ» (оранжево-красная, по `STYLE.md`) и вызывает `onExit()`. Именно `onExit`, а не `onComplete({won:false})`: игрок не проиграл, игра не состоялась — попытка не должна попасть в статистику `attempts`. Тем же путём обрабатываются прочие ошибки формата (несовпадение длин строк, посторонние символы, размер > 16, клеток > 60). |
| **Дырки внутри силуэта** (`.`, окружённые `#`) | Поддерживаются без специального кода: движок работает с множеством клеток, а не с прямоугольником. Дырка — это просто отсутствие клеток; детали никогда её не займут, потому что перебираются только подмножества клеток силуэта. На поле дырка рисуется как фон, без рамки ячейки, чтобы визуально не путалась с незаполненной клеткой силуэта. Единственный практический нюанс: узкие «перешейки» шириной 1 вокруг дырки повышают шанс появления мелких деталей (3/2/1) — админ видит это в превью разбиения до сохранения. |
| **Симметричная деталь (deuce-случай)** — несколько ориентаций дают одинаковый результат на данном месте | Все принимаются. Проверка — равенство **множеств клеток**, а не совпадение индекса поворота, поэтому O-тетромино подходит во всех 4 ориентациях, I/S/Z — в двух парах, а игрок не может «угадать место, но не угадать поворот» там, где поворот физически ничего не меняет. Ситуаций, когда деталь визуально легла верно, но игра её отвергла, не существует по построению. |
| Отпускание детали вне сетки | Отмена, не ошибка: возврат в лоток, `errors` не растёт (§1.3). |
| Силуэт крупнее рабочей области | Размер ячейки уменьшается через `ResizeObserver` до минимума ~16 px; при 16×16 это всё ещё помещается в рабочую область терминала. Скролла у поля нет — вся фигура обязана быть видна целиком, иначе теряется смысл силуэта-мишени. |
| `scoreThresholds` пуст | `scoreForElapsed` возвращает 0; со штрафом за ошибки `score` остаётся 0. Игра проходима, `won: true`, просто без очков. Отдельной ошибкой не считается — админ мог намеренно сделать «зачётную» игру без очков. |

## 7. Оценка трудоёмкости

**~3–4.5 дня**, включая новый виджет админки:

| Работа | Оценка |
|---|---|
| Виджет `grid-paint` (холст, размеры, мазок, превью разбиения, валидация) | 1–1.5 дня |
| `engine.ts` + `engine.test.ts` (разбиение, повороты, сравнение, перенос `scoreForElapsed`) | 1–1.5 дня |
| `index.ts` (DOM-сетка, drag, поворот, лоток, подсказка, звуки, оформление по `STYLE.md`) | 1–1.5 дней |
| `schema.json`, `vite.config.ts`, сборка, прогон из тест-запуска админки | ~0.5 дня |

Основной риск — не алгоритм (он локализован и покрыт тестами), а виджет `grid-paint`: это первое
расширение реестра `x-type` в DispatchOleg, и его придётся аккуратно вписать в существующую SchemaForm.
