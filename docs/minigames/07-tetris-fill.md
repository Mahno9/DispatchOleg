# Мини-игра 07: tetris-fill (заполнение силуэта)

`minigame_id`: `tetris-fill`. Тип реализации — **DOM-сетка** (без canvas) с игровым циклом на
`requestAnimationFrame`: детали падают, поэтому кадр нужен. Базовый контракт — `minigame_contract.md`,
расширения платформы (`onProgress`, `details`) — `docs/platform.md` §3. Оформление — `STYLE.md`.

Суть: админ рисует силуэт на сетке, движок при запуске сам разбивает силуэт на тетромино и роняет
детали сверху по одной. Это **тетрис-jigsaw**: падение и гравитация есть, линий и проигрыша нет, а у
каждой детали ровно одно правильное место — совпало, значит встала.

Репозиторий:

```
minigames/tetris-fill/
  schema.json
  vite.config.ts
  src/
    engine.ts        # чистая логика: парсинг, разбиение, порядок подачи, падение/фиксация, очки (vitest)
    engine.test.ts
    index.ts         # init/destroy, DOM-сетка, rAF-цикл, панель управления, подсказка
```

## 1. Геймплей и состояния

### 1.1 Экран

Рабочая область делится на три зоны, сверху вниз:

| Зона | Содержимое |
|---|---|
| **Поле** (основная площадь) | Сетка `width × height` плюс ~2 строки «неба» сверху, в котором появляется деталь (`overflow: hidden`, поле не скроллится). Клетки силуэта (`#`) — контурные ячейки с приглушённым бирюзовым бордюром и чуть более светлой поверхностью (`#0A3435`). Клетки вне силуэта (`.`) — фон терминала без рамки; деталь пролетает сквозь них насквозь, они не препятствие. Заполненные клетки закрашиваются цветом установленной детали. Под падающей деталью — пунктирная янтарная тень в месте приземления. |
| **Строка состояния** | `ДЕТАЛЬ N / M` слева, `ОШИБОК: K` справа. |
| **Панель управления** (низ, во всю ширину) | Четыре крупные кнопки `◀ ▶ ↻ ⤓` — см. §2. |

Силуэт-мишень виден целиком с первого кадра — игрок сразу понимает масштаб задачи. Уже уложенные
детали остаются на поле закрашенными, с тонким разделителем по границе между соседними деталями
(чтобы читалось, что фигура собрана из кусков, а не залита сплошняком).

### 1.2 Порядок подачи

Детали выдаются **по одной**, в фиксированном порядке. Пока текущая деталь не зафиксирована,
следующая не появляется. Очереди/превью «следующая деталь» нет — выбора у игрока всё равно нет.

Порядок задаёт `orderForGravity()` (§5b): топологическая сортировка отношения «A должна лечь раньше
B, если есть колонка, где клетка A строго **ниже** клетки B». Ничьи разрешаются прежним порядком по
якорю (снизу-вверх, слева-направо), поэтому визуально силуэт по-прежнему заполняется снизу вверх,
слой за слоем.

Порядок из самого `partition()` для этого **не годится**: он идёт по нижней-левой клетке детали, а
это не гравитационный порядок — деталь может оказаться погребена под уже уложенной. Репро:
силуэт `['##','##','.#']`, разбиение даёт деталь `{(0,1),(1,0),(1,1),(1,2)}` и одиночную клетку
`(0,0)` — по якорю первой подаётся четвёрка, её клетка `(0,1)` перекрывает путь одиночке в колонку 0.

### 1.3 Состояния

```
        ┌──────────────────────────┐
        │ SPAWN                     │◀──── та же деталь, та же ориентация
        │ целиком над строкой 0,    │
        │ случайная ориентация      │
        └────────────┬─────────────┘
                      ▼
        ┌──────────────────────────┐
        │ FALL                      │  ◀ ▶ — сдвиг, ↻ — поворот 90° CW,
        │ шаг вниз раз в            │  ⤓ — мягкий спуск / мгновенный сброс
        │ fallIntervalMs            │
        └────────────┬─────────────┘
          ┌──────────┴──────────────────────┐
          ▼                                 ▼
  клетки детали ==                  упёрлась в пол/уложенное
  её место (магнит,                 и это не её место
  проверяется ДО столкновений)      │  копится lockTimer
          │                         ▼  (успешный сдвиг обнуляет)
          ▼                  ┌────────────────────┐
  ┌────────────────┐         │ REJECTED            │
  │ PLACED          │         │ через lockDelayMs:  │
  │ (закрашена,     │         │ errors++, янтарная  │
  │  звук place)    │         │ вспышка, звук error,│
  └───────┬────────┘         │ деталь рассыпается  │
          │                   └──────────┬─────────┘
          ▼                              │
   осталось деталей? ── да ──▶ SPAWN ◀───┘
          │ нет
          ▼
      ЗАВЕРШЕНИЕ
```

**Магнитная фиксация** — ключевое правило: совпадение с местом проверяется каждый кадр **до**
проверки столкновений, поэтому деталь встаёт на своё место, даже если под ней пусто и она могла бы
падать дальше. Без этого силуэт `['###','...','###']` непроходим: верхняя полоса легла бы на нижнюю
и никогда не дошла бы до своей строки.

Промежуточного состояния «деталь ждёт решения игрока» нет: исход всегда решает физика — либо магнит,
либо истёкшая задержка фиксации. Мгновенный сброс (`⤓` коротким тапом / `Пробел`) просто пропускает
задержку: деталь доезжает до места приземления и сразу фиксируется или рассыпается.

### 1.4 Завершение

Игра завершается, когда установлена последняя деталь — силуэт заполнен на 100 %. Проигрыша нет:
таймера обратного отсчёта, лимита ошибок и условий провала не существует. После установки последней
детали проигрывается `win`, вся фигура на ~400 мс подсвечивается бирюзовым свечением, затем
вызывается `onComplete({ score, won: true, details })`.

Прогресс во время игры уходит в нижнюю панель терминала:

```js
callbacks.onProgress?.(`СОБРАНО ${placed} / ${total}`, Math.round((placed / total) * 100));
```

Вызывается при старте и после каждой успешной установки (не каждый кадр — по контракту платформы).

## 2. Управление

Игра рассчитана на телефон: основной ввод — **панель из четырёх кнопок под полем**, клавиатура
работает параллельно и ничего не дублирует лишнего. Кнопки крупные, `touch-action: none`,
`-webkit-tap-highlight-color: transparent`, обработчики — `pointerdown/up/cancel/leave`.

| Действие | Кнопка | Клавиша | Поведение |
|---|---|---|---|
| Сдвиг влево / вправо | `◀` `▶` | `←` / `→` | Сдвиг на клетку. При удержании кнопки — автоповтор каждые ~120 мс (`setInterval`, снимается на `pointerup/cancel/leave`). Удачный сдвиг обнуляет таймер фиксации — деталь, лежащую не на месте, можно успеть поправить. |
| Поворот 90° CW | `↻` | `↑`, `R`, `К` | Пробуется текущая колонка, затем сдвиг на клетку влево и вправо (одноклеточный кик). Если не влезает нигде — поворот отклоняется, звука нет. Доступны 4 ориентации: 0°/90°/180°/270°. |
| Мягкий спуск | удержание `⤓` дольше 250 мс | удержание `↓` | Интервал падения делится на `softDropFactor`. Отпускание возвращает обычную скорость. |
| Мгновенный сброс | тап `⤓` короче 250 мс | `Пробел` | Деталь доезжает до места приземления и фиксируется/рассыпается сразу, минуя `lockDelayMs`. |

Тень приземления (пунктирный янтарный контур) считается той же функцией `landingY()`, что и
мгновенный сброс, — обещание тени всегда совпадает с результатом.

**Зеркалирования нет.** Доступны только повороты — 4 ориентации, не 8. Это принципиально: S/Z- и
J/L-тетромино являются зеркальными парами, и разрешённое отражение позволило бы подставить S вместо Z,
сделав часть мест взаимозаменяемыми. Отражение не назначено ни на какую клавишу и не поддерживается.

**Начальная ориентация и колонка.** Новая деталь появляется целиком над строкой 0 в случайной из 4
ориентаций (`randomizeRotation: true`, значение по умолчанию) — игрок обязан довернуть её сам. При
`randomizeRotation: false` деталь выдаётся сразу в правильной ориентации (той, что в разбиении), и
задача сводится к чистому позиционированию — облегчённый режим для младшей аудитории. Колонку задаёт
`spawnColumn`: `center` (по центру поля) или `target` (сразу над своим местом — заметно проще).
Отступ над полем берётся по **самой высокой** из 4 ориентаций, поэтому поворот сразу после появления
никогда не упирается в уже уложенное. После рассыпания деталь возвращается той же и в той же
ориентации — переворачивать её обратно было бы издевательством.
Случайность здесь — единственный источник недетерминизма в игре и **не влияет** на разбиение силуэта
(§5b), поэтому набор мест и порядок подачи одинаковы при каждом запуске.

Клавиатурные обработчики вешаются на корневой элемент игры (с `tabindex="0"` и фокусом при
монтировании), а не на `window`/`document` — по требованию изоляции контракта. Кнопки панели
возвращают фокус на корень при нажатии, чтобы клавиатура продолжала работать после тапа.

## 3. Победа / пенальти

### 3.1 Поражения не бывает

`won` — всегда `true`. Игра заканчивается только одним способом: силуэт заполнен. Это осознанное
решение: `tetris-fill` — головоломка на аккуратность и скорость, а не на выживание; при этом `won`
управляет разблокировкой следующих игр (`required_game_ids`, `docs/platform.md` §5), и запирать цепочку
за пространственную задачку не нужно. Разница между хорошим и плохим прохождением выражается
исключительно в `score`.

`onExit()` вызывается только если платформа закрыла игру кнопкой «ВЫЙТИ» или конфиг оказался
невалидным (§6).

### 3.2 Очки

```
score = max(0, round(scoreForElapsed(scoreThresholds, elapsedSeconds)) - errorPenalty * errors)
```

- `elapsedSeconds` — время от монтирования игры (первый кадр после `init`) до установки последней
  детали. Пауз в игре нет.
- `scoreForElapsed` — **уже существующая функция**, переносится в `engine.ts` без изменений из
  `minigames/sliding-puzzle/src/engine.ts` (та же функция используется в `find-object`). Это
  кубический сплайн Эрмита по списку точек `{maxSeconds, points}`, отсортированному по времени, с той же
  математикой, что и редактор кривой в админке — то есть админ видит в редакторе ровно ту кривую, по
  которой начисляются очки. Вне диапазона кривой значение зажимается первым/последним значением:
  быстрее самой левой точки — максимум очков, медленнее самой правой — значение последней точки
  (чтобы «за очень медленное прохождение» давать 0, админ добавляет финальную точку с `points: 0`).
  Пустой список даёт 0. Смысл прост: **чем быстрее собран силуэт, тем больше очков**, причём кривая, а
  не ступеньки — резких обрывов на секунду позже порога не происходит.
- `errorPenalty * errors` вычитается из результата кривой. Итог зажимается снизу нулём — контракт
  требует `score >= 0`.

### 3.3 Ошибки

`errors` инкрементируется, когда деталь **улеглась не на своё место**: она упёрлась в пол или в уже
уложенное, пролежала так `lockDelayMs`, и множество занимаемых ею клеток не равно множеству клеток её
места из разбиения. Мгновенный сброс приводит к тому же исходу сразу, без задержки. Сюда попадают все
случаи: неверная позиция, неверный поворот, посадка поверх уже установленной детали, посадка мимо
силуэта. Реакция:

1. Деталь рассыпается и подаётся заново — та же самая, в той же ориентации.
2. Клетки, на которые она легла, дают янтарную вспышку (`#E9A928`, 160 мс, без сдвига layout —
   меняется только `border-color`/`background`, по `STYLE.md` «Ошибка или тревога»).
3. Проигрывается звук `error`.
4. `errors++`, счётчик в строке состояния обновляется.

Пока деталь ещё летит или лежит менее `lockDelayMs`, ошибки нет: удачный сдвиг обнуляет таймер
фиксации, так что промах можно исправить на весу. `lockDelayMs: 0` убирает эту поблажку.

### 3.4 Подсказка-призрак

Когда число ошибок **по текущей детали** достигает `hintAfterErrors` (по умолчанию 3), включается
режим подсказки: место текущей детали рисуется на поле призраком — пунктирный янтарный контур по
границе места, без заливки, с ориентацией, соответствующей разбиению. Дополнительно проигрывается звук
`hint` (один раз, в момент включения режима).

Порог считается по ошибкам той детали, которая выдаётся сейчас (`state.pieceErrors`): после успешной
подстановки счётчик обнуляется и подсказка гаснет — следующая деталь снова идёт без призрака, пока
игрок не начнёт промахиваться уже по ней. Подсказка не отменяет штрафа: `errors` (суммарные за
партию) уже начислены и продолжают начисляться, если игрок промахивается даже с призраком.

`hintAfterErrors: 0` — подсказка включена с самого начала (обучающий режим). Значение больше
количества деталей практически отключает подсказку.

### 3.5 Результат

```js
callbacks.onComplete({
  score,
  won: true,
  details: {
    errors,                     // число ошибочных попыток
    pieces: total,              // сколько деталей было в разбиении
    elapsedSeconds,             // затраченное время, целое
    styleTag: errors === 0 ? 'precise' : 'rough',
  },
});
```

`details` сохраняется платформой в `gameResults[gameId].details`; `styleTag` может ветвить пост-диалог
через `style_dialogue_map` (`docs/platform.md` §3.3) — «собрал с первого раза, ни одной ошибки» против
«кое-как, но собрал». Если ветвление не настроено, поле просто игнорируется.

## 4. Настройки админки (`schema.json`)

| Поле | Тип | `x-type` | По умолчанию | Описание |
|---|---|---|---|---|
| `levels` | array | — | `[]` | Уровни подряд, см. §4.2. Каждый элемент — `{shape, fallIntervalMs?, lockDelayMs?, hintAfterErrors?, randomizeRotation?, spawnColumn?}`; заданные поля перекрывают одноимённые верхнего уровня. Пусто — играется один силуэт из `shape`. |
| `shape` | object | **`grid-paint`** | 4×4 «плюс» | Силуэт-мишень, если `levels` пуст: `{width, height, rows}`. Уникальный виджет, см. §5a. Обязательное. |
| `scoreThresholds` | array | `curve` | см. ниже | Кривая очков от времени: точки `{maxSeconds, points}`. По оси X редактора — секунды, по оси Y — очки. Обязательное. |
| `errorPenalty` | integer | — | `5` | Сколько очков снимается за одну ошибочную попытку установки. `0` — штрафа нет. |
| `hintAfterErrors` | integer | — | `3` | После скольких ошибок по текущей детали включается призрак-подсказка. `0` — сразу. |
| `randomizeRotation` | boolean | — | `true` | Выдавать деталь в случайной из 4 ориентаций. `false` — деталь сразу повёрнута правильно. |
| `fallIntervalMs` | integer | — | `700` | Сколько мс деталь проводит на одной строке. Диапазон 150…3000: больше — медленнее и проще. |
| `softDropFactor` | number | — | `6` | Во сколько раз быстрее падает деталь при мягком спуске. Диапазон 1…20. |
| `lockDelayMs` | integer | — | `500` | Сколько деталь лежит на препятствии не на своём месте до рассыпания. Диапазон 0…2000, `0` — мгновенно. |
| `spawnColumn` | string (enum) | — | `center` | Где появляется деталь: `center` («По центру») или `target` («Над своим местом (проще)»). Подписи — через `x-enumLabels`. |
| `sounds.rotate` | string | `asset:audio` | — | Удавшийся поворот детали. |
| `sounds.place` | string | `asset:audio` | — | Успешная установка. |
| `sounds.error` | string | `asset:audio` | — | Деталь рассыпалась мимо места. |
| `sounds.hint` | string | `asset:audio` | — | Включение подсказки. |
| `sounds.win` | string | `asset:audio` | — | Силуэт собран. |

Все звуки — необязательные; отсутствующий звук просто не проигрывается. Значение поля `asset:audio` —
`WeightedAudio[]`, воспроизведение через `pickSound(val)` (базовый контракт). `config.muted`
учитывается при инициализации, кнопка mute присутствует в углу поля.

### 4.1 Формат `shape` в `config_json`

```json
{
  "shape": {
    "width": 4,
    "height": 4,
    "rows": [
      "####",
      "#..#",
      "#..#",
      "####"
    ]
  }
}
```

- `rows` — массив ровно из `height` строк, каждая длиной ровно `width`.
- Символ `#` — клетка силуэта (её нужно заполнить деталью), символ `.` — пустое место (не часть фигуры).
  Любой другой символ — ошибка конфигурации.
- Система координат: `x` — колонка `0..width-1` слева направо, `y` — строка `0..height-1` **сверху
  вниз**, то есть `rows[y][x]`. «Нижняя» клетка — с максимальным `y`.
- Ограничение: `1 ≤ width ≤ 16`, `1 ≤ height ≤ 16`, число `#` — от 1 до 60 (см. §5b про скорость).

Пример выше — рамка 4×4 с дыркой 2×2 в центре, 12 клеток, разбивается ровно на 3 тетромино:

```
Силуэт:        Разбиение (буква = деталь):
####           BBCC
#..#           B..C
#..#           B..C
####           AAAA
```

Ещё пример, 5×5, несвязная фигура (два острова) — валидна:

```
##...
##...
.....
..###
...##
```

Левый остров — 4 клетки (O-тетромино), правый — 5 клеток (тетромино + одиночная клетка).

### 4.2 Уровни

`levels` — список силуэтов, которые играются подряд, обычно по нарастанию сложности. Каждый уровень
берёт настройки верхнего уровня и перекрывает своими (`levelsOf()` в `engine.ts`), так что сложность
крутится ровно теми же ручками: `fallIntervalMs`, `lockDelayMs`, `hintAfterErrors`,
`randomizeRotation`, `spawnColumn`.

```json
{
  "levels": [
    { "shape": { "width": 5, "height": 3, "rows": [".###.", "#####", ".###."] },
      "fallIntervalMs": 950, "spawnColumn": "target", "randomizeRotation": false },
    { "shape": { "width": 7, "height": 5, "rows": ["..###..", ".#####.", "#######", ".#####.", "..###.."] },
      "fallIntervalMs": 800 }
  ]
}
```

- Силуэт следующего уровня проверяется вместе с остальными при `init`: битый силуэт третьего уровня
  даёт панель `ОШИБКА КОНФИГУРАЦИИ` («уровень 3: …») и `onExit()` сразу, а не через две минуты игры.
- Между уровнями — пауза `LEVEL_MS` (900 мс) с подсветкой собранного силуэта, потом поле
  перестраивается под следующий.
- Время, ошибки и штраф — сквозные на весь прогон: `scoreThresholds` считается по суммарному времени,
  `errors` в `details` — сумма по всем уровням. `pieces` — сумма деталей всех уровней.
- Нижняя панель и строка состояния получают префикс `ПРОБОИНА i / n`, процент — доля пройденных
  уровней плюс прогресс текущего.
- `levels` пуст или отсутствует — всё работает как раньше, один силуэт из `shape`.

## 5. Реализация

### 5a. Виджет `grid-paint` в SchemaForm админки

**Новое расширение `x-type` сверх базового контракта GameService.** В `minigame_contract.md`
перечислены `asset:image`, `asset:audio`, `asset:gif`, `curve`, `weighted-list` — виджета для
рисования сетки там нет, он вводится этой мини-игрой и добавляется в общий реестр виджетов
SchemaForm админки DispatchOleg (а значит, доступен и будущим играм, работающим с сетками).

Схема поля:

```json
"shape": {
  "type": "object",
  "title": "Силуэт",
  "x-type": "grid-paint",
  "x-max-size": 16,
  "required": ["width", "height", "rows"],
  "properties": {
    "width":  { "type": "integer", "minimum": 1, "maximum": 16 },
    "height": { "type": "integer", "minimum": 1, "maximum": 16 },
    "rows":   { "type": "array", "items": { "type": "string" } }
  }
}
```

Состав виджета:

1. **Контролы размера** — два числовых поля `Ширина` / `Высота` (1…16, верхняя граница берётся из
   `x-max-size`, дефолт 16). Изменение размера сохраняет уже нарисованное: сетка обрезается справа/снизу
   при уменьшении и дополняется пустыми клетками при увеличении. Уменьшение, которое отрежет
   закрашенные клетки, требует подтверждения (обычное inline-предупреждение в форме, не `confirm()`).
2. **Холст-сетка** — таблица `width × height` квадратных ячеек. Клик по ячейке переключает её
   `пусто ↔ заполнено`. Поддерживается «мазок»: `pointerdown` задаёт режим (закрашиваем или стираем — по
   исходному состоянию первой ячейки), протаскивание применяет этот режим ко всем задетым ячейкам.
   Оформление — по `STYLE.md`: заполненная ячейка — бирюзовая поверхность с контуром, пустая — фон
   терминала с еле заметной сеточной линией, радиус скругления 0.
3. **Кнопки** `ОЧИСТИТЬ` и `ИНВЕРТИРОВАТЬ` — мелочь, но экономит админу десятки кликов.
4. **Превью авторазбиения** — рядом с холстом вторая сетка того же размера, где показан результат
   того же самого алгоритма из `engine.ts` (§5b): каждая деталь залита своим цветом из
   палитры-циклички (бирюзовый / янтарный / оранжевый / бежевый и их приглушённые варианты, соседние
   детали гарантированно разных цветов в пределах цикла), номер над деталью — её порядковый номер
   подачи. Пересчитывается при каждом изменении холста (debounce ~120 мс). Под превью — строка
   `ДЕТАЛЕЙ: N (тетромино M, мелких K)`. Это единственный способ для админа заранее увидеть, во что
   превратится его силуэт: фигура из 13 клеток неизбежно даст «хвост» из мелкой детали, и это лучше
   увидеть до сохранения. Номера — это порядок **после** `orderForGravity()`, тот же, что в игре.
   Кросс-воркспейсный импорт из `minigames/tetris-fill/src/engine.ts` невозможен, поэтому в
   `GridPaintField.tsx` лежат компактные копии `partition()` и `orderForGravity()` — при правке
   алгоритма надо править обе.
5. **Валидация** — если закрашенных клеток нет вовсе, виджет показывает ошибку `СИЛУЭТ ПУСТ` и
   блокирует сохранение игры (§6). Если клеток больше 60 — предупреждение о возможной задержке
   разбиения (мягкое, не блокирующее — граница эмпирическая).

Значение, которое виджет пишет в `config_json` — ровно объект `{width, height, rows}` из §4.1
(строки, а не булев массив: так конфиг остаётся читаемым глазами в БД и в экспорте).

### 5b. `engine.ts` — разбиение и правила

Чистый модуль без DOM, без таймеров и без `Math.random`, полностью покрытый vitest; функции падения
мутируют только переданный им объект `FallState`. Публичное API:

```ts
export interface Shape { width: number; height: number; rows: string[] }
export interface Cell { x: number; y: number }
export interface Piece { index: number; cells: Cell[] }   // абсолютные координаты места

export function parseShape(shape: Shape): Cell[];          // бросает на невалидном силуэте
export function partition(cells: Cell[]): Piece[];         // разбиение, порядок «по якорю»
export function orderForGravity(pieces: Piece[]): Piece[]; // порядок подачи
export function rotate(cells: Cell[], turns: number): Cell[];
export function sameCells(a: Cell[], b: Cell[]): boolean;
export function scoreForElapsed(thresholds: ScoreThreshold[], elapsedSeconds: number): number;

// падение
export type SpawnColumn = 'center' | 'target';
export interface FallRules { fallIntervalMs: number; softDropFactor: number; lockDelayMs: number; spawnColumn: SpawnColumn }
export interface Active { shape: Cell[]; x: number; y: number; turns: number }  // y может быть < 0
export type FallEvent = 'placed' | 'rejected' | 'won';

export function createFallState(shape: Shape, rules: FallRules): FallState;  // parseShape + partition + orderForGravity
export function spawn(state: FallState, turns: number): void;                // целиком над строкой 0
export function collides(state: FallState, shape: Cell[], x: number, y: number): boolean;
export function matchesTarget(state: FallState, active: Active): boolean;
export function move(state: FallState, dx: -1 | 1): boolean;                 // успех обнуляет lockTimer
export function rotateActive(state: FallState): boolean;                     // x, затем x−1 / x+1
export function setSoftDrop(state: FallState, on: boolean): void;
export function update(state: FallState, dtMs: number): FallEvent[];
export function hardDrop(state: FallState): FallEvent[];
export function landingY(state: FallState): number;                          // для тени
```

#### Разбиение — детерминированный backtracking с branch-and-bound

Разбиение **не хранится в конфиге** и **не редактируется админом**. Оно пересчитывается из `shape` при
каждом `init` (и при каждой перерисовке превью в админке). Алгоритм детерминирован — без RNG, без
зависимости от порядка ключей объекта, — поэтому один и тот же силуэт всегда даёт одно и то же
разбиение и один и тот же порядок подачи. Хранить его в БД было бы лишним состоянием, способным
разъехаться с `shape` при редактировании.

Ход алгоритма:

1. **Точка ветвления фиксирована**: на каждом шаге берётся **самая нижняя-левая непокрытая клетка**
   (максимальный `y`, при равенстве — минимальный `x`). Это ключевое ограничение: перебирать
   *какую* клетку покрывать не нужно — она обязана быть покрыта какой-то деталью, а значит перебор идёт
   только по деталям, содержащим её. Это срезает факториальную часть пространства поиска.
2. **Перебор деталей**: все связные (по стороне) подмножества непокрытых клеток размера `k`,
   содержащие якорную клетку. `k` перебирается в порядке **4 → 3 → 2 → 1**. Размеры 3/2/1
   рассматриваются только если ни один вариант с бо́льшим `k` не привёл к решению — так число деталей
   минимизируется, то есть доля настоящих тетромино максимизируется.
   Подмножества генерируются обычным наращиванием по соседям (DFS с дедупликацией по каноническому
   множеству клеток) — таблицы из 19 ориентаций семи тетромино не нужны, тот же код обслуживает и
   мелкие детали. Порядок обхода соседей фиксирован (вверх, влево, вправо, вниз), что и даёт
   детерминизм.
3. **Отсечения (branch-and-bound)**:
   - **Нижняя оценка по компонентам связности**: непокрытая область разбивается на компоненты
     флуд-филлом, оценка снизу = `Σ ceil(|компонента| / 4)`. Если `текущее_число_деталей + оценка >=
     лучшего_найденного`, ветка отбрасывается. Эта оценка сильно лучше наивной `ceil(остаток/4)`:
     компонента из 1–3 клеток немедленно штрафует ветку, отрезавшую «огрызок».
   - **Ранний выход по оптимуму**: если найдено решение с `ceil(всего_клеток / 4)` деталями, оно
     доказуемо оптимально — поиск останавливается немедленно. Для подавляющего большинства силуэтов
     (все, у которых существует полное покрытие тетромино) это происходит на первом же спуске, и
     backtracking фактически вырождается в жадный проход.
4. **Собственный порядок `partition()`** — тот, в котором детали были зафиксированы в найденном
   решении, то есть «снизу-вверх, слева-направо по нижним-левым клеткам деталей». Это порядок «по
   якорю», он определяет только внешний вид и **не** является гравитационным (§1.2).

**Скорость.** Глубина дерева ≤ `ceil(N/4)` (для `N = 60` это 15). Ветвление на шаге ограничено числом
тетромино, содержащих фиксированную клетку и лежащих в непокрытой области; в открытом поле это
несколько десятков, но на реальном силуэте (клетка — нижняя-левая, значит вся деталь лежит «выше и
правее» уже покрытого) — единицы. В сочетании с ранним выходом по оптимуму фигуры до 60 клеток
разбираются за единицы миллисекунд — задержки при `init` не заметны, Web Worker не нужен.

> `ponytail:` на всякий случай в поиск встроен счётчик посещённых узлов с потолком (≈200 000). При его
> исчерпании возвращается лучшее найденное на этот момент решение (оно всегда существует — первый
> спуск всегда доходит до конца, так как `k=1` покрывает любую клетку). Апгрейд, если когда-нибудь
> упрёмся: DP по профилю/broken profile для сеток ≤16 в ширину.

#### `orderForGravity()` — порядок подачи

Топологическая сортировка (алгоритм Кана) отношения «A раньше B, если есть колонка `x`, где клетка A
строго ниже клетки B». Из готовых к выдаче узлов всегда берётся самый ранний в исходном порядке по
якорю — так сохраняется и детерминизм, и прежний вид «заполняется снизу вверх». Индексы деталей
перенумеровываются по новому порядку (они же задают цикл цветов). Тот же порядок применяется в
превью админки, иначе номера в превью разъедутся с игрой.

> `ponytail:` цикл в отношении (A ниже B в одной колонке, B ниже A в другой) означает, что
> гравитационного порядка не существует вовсе — такой силуэт непроходим при любом порядке. Вместо
> зависания оставшиеся детали дописываются в порядке по якорю. Апгрейд: отлавливать это в виджете
> `grid-paint` и не давать сохранить.

#### Падение и фиксация — FSM

`update(dt)` — единственная точка, где идёт время. `dt` зажимается сверху 100 мс (возврат во вкладку
не должен телепортировать деталь сквозь поле). Порядок правил строго такой:

1. **Магнит.** `matchesTarget()` → фиксация как `placed` (плюс `won`, если деталь была последней).
   Проверяется **до** столкновений — именно поэтому деталь встаёт на место, даже когда под ней пусто.
2. **Упор.** `collides(shape, x, y+1)` → копится `lockTimer`; на `lockDelayMs` — `errors++`, деталь
   рассыпается, событие `rejected`. Удачный `move` обнуляет таймер.
3. **Гравитация.** `fallTimer += dt`; шаг вниз на строку каждые `fallIntervalMs / (softDrop ?
   softDropFactor : 1)`; после каждой строки магнит перепроверяется.

`hardDrop()` опускает деталь до места приземления (`landingY()` — тот же расчёт) и фиксирует или
рассыпает немедленно, минуя задержку. Политика вызывающей стороны: после `placed` — следующая деталь
со свежим случайным поворотом, после `rejected` — та же деталь в той же ориентации.

`collides()` учитывает стены, пол и уже уложенные клетки; `y < 0` свободен всегда, а клетки **вне**
силуэта не препятствие — деталь пролетает сквозь дырки и пустоты, иначе фигуры вроде
`['###','...','###']` были бы непроходимы.

Сравнение с местом — по-прежнему равенство множеств (`sameCells(абсолютные клетки, piece.cells)`).
Отсюда бесплатно следует нужное поведение симметрий: у O-тетромино все 4 ориентации дают одно и то же
множество, у I/S/Z повороты на 0° и 180° совпадают — любая из «одинаковых» ориентаций принимается
автоматически, потому что сравниваются клетки, а не индекс поворота.

**Почему силуэт всегда решаем.** Деталь появляется целиком над строкой 0 (с запасом на самую высокую
из 4 ориентаций), где ничего не заперто, — значит её можно свободно повернуть и подвести к любой
колонке. Гравитационный порядок гарантирует, что ни одна уже зафиксированная клетка не находится выше
клеток текущего места в той же колонке, — значит спуск в правильной ориентации и колонке доходит до
места, где срабатывает магнит. Оба утверждения покрыты тестом-харнессом (§ниже).

#### `index.ts` — DOM-слой

- **Монтирование**: `init` строит внутри `container` статическую разметку — панель поля, строку
  состояния и панель из четырёх кнопок (угловатые панели, `border-radius: 0`, по `STYLE.md`), сетку из
  `width × height` `<div>`-ячеек (при 16×16 это 256 элементов — DOM справляется без вопросов), кнопку
  mute. Размер ячейки вычисляется от размеров поля (`ResizeObserver`, ячейка квадратная, 16…48 px) с
  запасом на 2 строки «неба» сверху: под сетку резервируется `H + 2` строки, а верхний паддинг поля
  задан как `calc(8px + var(--c) * 2)`. У поля `overflow: hidden`, скролла нет.
- **Игровой цикл**: `requestAnimationFrame` с дельтой по `performance.now()` → `update(state, dt)` →
  разбор событий (звук, закраска уложенных клеток, `reportProgress`, порог подсказки, победа) →
  `renderActive()`. Сетка целиком не перерисовывается — точечно меняются классы затронутых ячеек.
- **Деталь и тень**: два абсолютно позиционированных элемента из `k` квадратов внутри поля; DOM
  квадратов пересобирается только при смене детали/ориентации/размера ячейки, позиция — `transform:
  translate()` относительно `gridEl.offsetLeft/offsetTop` (без reflow). Тень рисуется в `landingY()`
  пунктиром и прячется, когда совпадает с самой деталью.
- **Подсказка-призрак**: пунктирный янтарный контур на ячейках места текущей детали
  (`box-shadow: inset`, чтобы не смещать layout).
- **Ошибка**: класс `.tf-flash` на клетках, куда легла рассыпавшаяся деталь, со снятием по
  `animationend` (без таймеров, которые надо было бы чистить в `destroy`).
- **Звук**: `pickSound(config.sounds.*)` и один переиспользуемый `<audio>`-пул внутри контейнера;
  глушится при `config.muted` и по кнопке mute.
- **`destroy()`**: снимает `ResizeObserver`, отменяет висящий `rAF` и интервал автоповтора кнопок,
  чистит таймеры и аудио, очищает `container.innerHTML`. Глобальных слушателей (`window`, `document`)
  не регистрируется вовсе — сознательное следствие §2.

| Что проверяем | Ожидание |
|---|---|

| Магнитная фиксация | На `['###','...','###']` верхняя полоса фиксируется на своей строке, хотя под ней пусто |
| `hardDrop` мимо места | Ровно одно `rejected`, `errors === 1`, `current` не меняется |
| **Харнесс проходимости** | Для таблицы силуэтов (`['###','...','###']`, `['##','##','.#']`, `['####','....']`, рамка 4×4, два острова, плита 6×10) прогоняется полное прохождение: перебором ищется ориентация/колонка, совпадающая с местом, деталь доводится `move`/`rotateActive` и сбрасывается `hardDrop` — каждый раз ожидается `placed`. В конце `state.done === true` и `state.errors === 0` |
| `rotate` | 4 поворота возвращают исходную нормализованную форму; O-тетромино инвариантен ко всем поворотам |
| `sameCells` | Не зависит от порядка клеток; различает S и Z |
| `scoreForElapsed` | Переносится вместе с существующим набором тестов из `sliding-puzzle` |

## 6. Edge cases

| Случай | Поведение |
|---|---|
| **Несвязная фигура** (несколько отдельных островов клеток) | Полностью валидна. Алгоритм не требует связности: он просто берёт самую нижнюю-левую непокрытую клетку, а к какому острову она относится — неважно. Оценка снизу по компонентам связности (§5b) на несвязных фигурах работает особенно хорошо. Подача идёт по гравитационному порядку, а не остров за островом: деталь верхнего острова может пойти раньше, если ни одна её клетка не висит над клетками другой детали. |
| **Висящий остров** (клетки над пустотой) | Работает: клетки вне силуэта не препятствие, деталь пролетает сквозь них, а место фиксируется магнитом ровно там, где оно есть, — падать дальше она не будет. Именно этот случай ломал бы игру без магнита. |
| **Цикл в гравитационном порядке** (A ниже B в одной колонке, B ниже A в другой) | Гравитационного порядка не существует; такой силуэт непроходим при любом порядке подачи. Kahn останавливается, остаток дописывается в порядке по якорю (см. `ponytail:` в §5b) — игра запустится, но одна из деталей может не дойти до места и будет рассыпаться. На практике разбиение из деталей ≤ 4 клеток такого не даёт; отдельного барьера в админке пока нет. |
| **Фигура из 1–2 клеток** | Тривиально корректна: одна деталь размера 1 (или 2, если клетки смежны; несмежные дают две детали по 1). Игра из одного хода — законная конфигурация, годится для обучающего QR-кода. Никаких особых веток в коде нет — `k` просто опускается до подходящего размера. |
| **Полностью пустая фигура** (ни одного `#`) | **Ошибка конфигурации.** Два рубежа: (1) виджет `grid-paint` показывает `СИЛУЭТ ПУСТ` и не даёт сохранить игру в админке — это основной барьер; (2) на случай конфига, залитого мимо формы (импорт, ручная правка БД, старая запись), `parseShape` при `init` бросает; `index.ts` ловит, рисует в контейнере угловатую панель тревоги «ОШИБКА КОНФИГУРАЦИИ: СИЛУЭТ ПУСТ» (оранжево-красная, по `STYLE.md`) и вызывает `onExit()`. Именно `onExit`, а не `onComplete({won:false})`: игрок не проиграл, игра не состоялась — попытка не должна попасть в статистику `attempts`. Тем же путём обрабатываются прочие ошибки формата (несовпадение длин строк, посторонние символы, размер > 16, клеток > 60). |
| **Дырки внутри силуэта** (`.`, окружённые `#`) | Поддерживаются без специального кода: движок работает с множеством клеток, а не с прямоугольником. Дырка — это просто отсутствие клеток; детали никогда её не займут, потому что перебираются только подмножества клеток силуэта. На поле дырка рисуется как фон, без рамки ячейки, чтобы визуально не путалась с незаполненной клеткой силуэта. Единственный практический нюанс: узкие «перешейки» шириной 1 вокруг дырки повышают шанс появления мелких деталей (3/2/1) — админ видит это в превью разбиения до сохранения. |
| **Симметричная деталь (deuce-случай)** — несколько ориентаций дают одинаковый результат на данном месте | Все принимаются. Проверка — равенство **множеств клеток**, а не совпадение индекса поворота, поэтому O-тетромино подходит во всех 4 ориентациях, I/S/Z — в двух парах, а игрок не может «угадать место, но не угадать поворот» там, где поворот физически ничего не меняет. Ситуаций, когда деталь визуально легла верно, но игра её отвергла, не существует по построению. |
| **Поворот у самого края / у стены** | Пробуется текущая колонка, затем одноклеточный кик влево и вправо. Не влезло — поворот молча отклоняется (ни ошибки, ни звука). У только что появившейся детали поворот не блокируется никогда: отступ над полем берётся по самой высокой из 4 ориентаций. |
| **Ориентация шире поля** (узкий силуэт + случайный поворот) | `spawn()` при выдаче перебирает ориентации вперёд и берёт первую, влезающую по ширине, — деталь физически не может появиться в невозможном повороте. |
| **Возврат во вкладку / лаг кадра** | `dt` зажимается 100 мс, поэтому деталь не проваливается сквозь поле за один кадр после `visibilitychange`. |
| Силуэт крупнее рабочей области | Размер ячейки уменьшается через `ResizeObserver` до минимума ~16 px, с учётом 2 строк «неба» сверху; при 16×16 это всё ещё помещается в рабочую область терминала. Скролла у поля нет — вся фигура обязана быть видна целиком, иначе теряется смысл силуэта-мишени. |
| `scoreThresholds` пуст | `scoreForElapsed` возвращает 0; со штрафом за ошибки `score` остаётся 0. Игра проходима, `won: true`, просто без очков. Отдельной ошибкой не считается — админ мог намеренно сделать «зачётную» игру без очков. |

## 7. Оценка трудоёмкости

**~3–4.5 дня**, включая новый виджет админки:

| Работа | Оценка |
|---|---|
| Виджет `grid-paint` (холст, размеры, мазок, превью разбиения, валидация) | 1–1.5 дня |
| `engine.ts` + `engine.test.ts` (разбиение, повороты, сравнение, перенос `scoreForElapsed`) | 1–1.5 дня |
| `index.ts` (DOM-сетка, rAF-цикл, панель управления, тень, подсказка, звуки, оформление по `STYLE.md`) | 1–1.5 дней |
| `schema.json`, `vite.config.ts`, сборка, прогон из тест-запуска админки | ~0.5 дня |

Основной риск — не алгоритм (он локализован и покрыт тестами), а виджет `grid-paint`: это первое
расширение реестра `x-type` в DispatchOleg, и его придётся аккуратно вписать в существующую SchemaForm.
