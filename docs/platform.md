# Платформа DispatchOleg — оболочка терминала

Этот документ описывает несущую конструкцию проекта: layout терминала, экраны и переходы между ними,
расширенный контракт мини-игр, схему БД и логику прогресса/блокировок. Специфика конкретных мини-игр —
в `docs/minigames/`. Формат диалогов — в `docs/dialogue-system.md`. QR — в `docs/qr-flow.md`.

Стиль оформления — везде по `STYLE.md` (палитра, CRT-оверлей, угловатые панели, карточки-досье).
Референс layout — `Windows.png` (4 кадра: МЕТА, окно чтения QR, начало игры/диалог, мини-игра).

---

## 1. Layout терминала

Экран приложения (`web/player`) всегда состоит из двух вертикальных зон:

```
┌─────────────────────────────────────────────────────────┐
│                                                           │
│                РАБОЧАЯ ОБЛАСТЬ (центр)                   │
│        (мета-сцена / QR-сканер / диалог / мини-игра)     │
│                                                           │
├─────────────────────────────────────────────────────────┤
│  [ КАМЕРА ]   [       КОНТЕКСТНЫЙ СЛОТ (центр)     ]  [ КНОПКА ]│
└─────────────────────────────────────────────────────────┘
```

Нижняя панель **постоянна** — она не размонтируется при смене экрана, меняется только содержимое трёх
слотов. Это отдельный React-компонент `BottomBar`, живущий на уровень выше стейт-машины экранов.

### 1.1 Слот 1 — камера (слева)

- До завершения обучалки: заглушка «NO SIGNAL» (статичный паттерн шума/CRT-рамка, по STYLE.md — контурная
  иконка камеры + текст на янтарной статусной полосе).
- После обучалки: `<video>` из `CameraPanel`, стрим из singleton-модуля `camera.ts` (см. §4 плана,
  раздел «Камера игрока» — детали в `docs/qr-flow.md`, т.к. стрим совместно используется со сканером).
- Если стрим пропал (устройство отключено) — «SIGNAL LOST» + кнопка «ПЕРЕПОДКЛЮЧИТЬ».
- Размер слота фиксирован во всех экранах — камера не меняет размер и позицию, меняется только то, что
  происходит в центральной рабочей области.

### 1.2 Слот 2 — контекстный (центр)

Это единственный слот, чьё содержимое зависит от текущего экрана:

| Экран | Содержимое слота 2 |
|---|---|
| meta | Прогресс по всей игре: `N / M игр пройдено` + горизонтальная полоса-индикатор |
| qr-scan | (по Windows.png третий слот пустой/декоративный — рамка без текста; можно отобразить подсказку «НАВЕДИТЕ КАМЕРУ НА КОД») |
| dialogue | Текстовое окно диалога — реплика говорящего с typewriter-эффектом, см. `docs/dialogue-system.md` |
| minigame | Прогресс внутри мини-игры — рендерится по колбэку `onProgress(text, percent?)` от самой игры (см. §3.1) |

Слот 2 — единственная часть нижней панели, которую могут «арендовать» и мета, и диалог, и мини-игра.
Компонент физически один (`ContextSlot`), контент передаётся через проп в зависимости от активного экрана.

### 1.3 Слот 3 — контекстная кнопка (справа)

| Экран | Содержимое слота 3 |
|---|---|
| meta | Кнопка **START** — открывает qr-scan |
| qr-scan | Кнопка «ОТМЕНА» — возврат в meta |
| dialogue | Пусто (клик для продолжения — по всей области диалога, не по кнопке) либо не рендерится вовсе |
| minigame | По умолчанию пусто/скрыт; мини-игра **не может** писать в этот слот (изоляция контракта — см. §3), но
  платформа может показать здесь кнопку «ВЫЙТИ» (вызывающую `onExit()` со стороны платформы, не игры) |

## 2. Экраны и переходы

Роутинг — состоянием (finite state), без клиентского роутера (в SPA терминала нет multi-page навигации,
URL не меняется). Состояние экрана хранится в верхнем компоненте `Terminal` (или сторе state-machine типа
`useReducer`/xstate-подобного редьюсера — конкретная реализация на усмотрение фазы кодирования).

```
        ┌────────────┐
        │ onboarding │  (один раз, до onboarded=true)
        └─────┬──────┘
              │ успешный скан QR обучалки
              ▼
   ┌────────────────────┐        START           ┌──────────┐
   │        meta         │ ─────────────────────▶ │ qr-scan  │
   │ (персонажи, прогресс)│ ◀───────────────────── │          │
   └─────────┬────────────┘   отмена / ошибка скана└─────┬────┘
             ▲                                            │ валидный QR открытой игры
             │                                            ▼
             │                                    ┌────────────────┐
             │                                    │ dialogue (pre)  │  (если у игры задан pre-диалог;
             │                                    └───────┬────────┘   иначе шаг пропускается)
             │                                            ▼
             │                                    ┌────────────────┐
             │                                    │    minigame     │
             │                                    └───────┬────────┘
             │                                            │ onComplete({score, won, details?})
             │                                            ▼
             │                                    ┌────────────────┐
             │                                    │ dialogue (post) │  (post-win / post-lose /
             │                                    └───────┬────────┘   styleTag-ветка, см. §3.2)
             │                                            │
             └────────────────────────────────────────────┘
                        возврат в meta (обновлённый прогресс)
```

Также кликабельны персонажи меты — клик открывает их `meta_dialogue_id` без перехода в qr-scan/minigame
(диалог → meta напрямую, ветка «болталка», не влияет на прогресс).

### 2.1 onboarding

Платформенный сценарий, не мини-игра из общего бандла (см. `docs/minigames/01-onboarding.md`). Идёт первым
запуском приложения, пока `users.onboarded = false`. Итог — `onboarded = true` в sync-состоянии, включённая
камера, переход в meta.

### 2.2 meta

Мета-сцена: персонажи на фоне (позиционируются по `characters.meta_position`), список игр как карточки
(по STYLE.md — досье), прогресс-бар в слоте 2 нижней панели, кнопка START в слоте 3. Закрытые
(`required_game_ids` не все `won`) игры показываются силуэтом с иконкой замка — по клику не запускают
скан, а поясняющий тултип/текст «недоступно» (сам скан всё равно верифицируется на сервере, см. §5).

### 2.3 qr-scan

Общий компонент `QrScanner` (см. `docs/qr-flow.md`) в рабочей области. Успешный декод → POST
`/api/qr/verify` → при успехе сохраняем `gameId` в стейт и переходим к `dialogue(pre)` либо сразу к
`minigame`, если pre-диалог не задан. При отказе (запрещённая игра / битая подпись) — экран отказа поверх
сканера с текстом причины, кнопка «ОК» возвращает в meta (сканер не перезапускается автоматически).

### 2.4 dialogue

Рендерер `DialogueScene` (детали — `docs/dialogue-system.md`) в рабочей области, реплики зеркалятся в
текстовое окно слота 2 нижней панели. Три точки использования диалога в этом переходе:
- **pre** — перед мини-игрой (`games.pre_dialogue_id`);
- **post-win** — после победы (`games.post_win_dialogue_id`), может быть переопределён styleTag-веткой;
- **post-lose** — после поражения (`games.post_lose_dialogue_id`).

Диалог без узлов (не задан в админке) — экран пропускается автоматически, без «пустого» показа.

### 2.5 minigame

Рабочая область целиком передаётся под `container` мини-игры (см. §3). Нижняя панель остаётся
платформенной: слот 1 (камера) не трогается игрой, слот 2 обновляется через `onProgress`, слот 3
управляется платформой, а не игрой.

## 3. Расширенный контракт мини-игр

База — `minigame_contract.md` (GameService): `init(container, config, callbacks)`, обязательный `destroy()`,
изоляция (никаких `localStorage`/`window.*`/глобальных стилей), звук через `config.muted`, 60 FPS,
`schema.json` для конфигурации. Всё это остаётся без изменений. Платформа DispatchOleg добавляет три
расширения.

### 3.1 `onProgress(text, percent?)`

Необязательный колбэк в объекте `callbacks`, наравне с `onComplete`/`onExit`:

```ts
callbacks.onProgress(text: string, percent?: number): void
```

- Игра может вызывать его произвольное число раз за время своей работы (в отличие от `onComplete`/`onExit`,
  которые вызываются ровно один раз и завершают жизненный цикл).
- Платформа рендерит `text` и, если передан, `percent` (полоса-индикатор 0–100) в слоте 2 нижней панели —
  это ровно раздел «Прогресс внутри мини-игры» на Windows.png.
- Колбэк — не обязателен к вызову; игра, которой нечего показать (например, `tetris-fill` может просто
  слать «Собрано: N/M деталей»), не обязана вызывать его каждый кадр — платформа не сбрасывает текст
  автоматически, последний переданный `text` остаётся до следующего вызова или до конца игры.
- Вызов `onProgress` **не входит** в правило «ровно один из колбэков» — это самостоятельный, многократный,
  не завершающий канал.

### 3.2 `onComplete({score, won, details?})`

Результат расширяется необязательным полем `details`:

```ts
{
  score: number,
  won: boolean,
  details?: Record<string, number | string>
}
```

- `details` — произвольная статистика конкретной игры, не влияющая на контракт напрямую. Пример:
  `three-mazes` возвращает `{ wallsBroken: 2, totalBreakable: 5, styleTag: "breaker" }`.
- `details` сохраняется целиком в `gameResults[gameId].details` через offline-sync (см. §6) и доступен
  платформе после завершения игры — в первую очередь для ветвления пост-диалога (см. ниже) и для админки
  (вкладка «Игроки» может показать `details` как есть, для отладки/аналитики).
- Игры, которым нечего возвращать в `details`, просто не указывают это поле — обратная совместимость с
  базовым контрактом полная.

### 3.3 Ветвление пост-диалога по `styleTag`

У игры (таблица `games`), помимо `post_win_dialogue_id`, есть опциональная карта
`style_dialogue_map: Record<string, dialogueId>` (хранится в `config_json` игры либо отдельным JSON-полем —
на усмотрение схемы миграции, семантически это часть конфигурации игры, не диалоговой системы).

Логика выбора пост-диалога при `won = true`:
1. Если `details.styleTag` присутствует **и** для него в `style_dialogue_map` есть запись → показывается
   диалог из этой записи.
2. Иначе → показывается `post_win_dialogue_id` как обычно.
3. Если `won = false` → всегда `post_lose_dialogue_id`, `styleTag` не рассматривается (ветвление стиля
   имеет смысл только для победных исходов — «как именно ты выиграл», а не «как проиграл»).

Так результат «какого персонажа отыгрывал игрок» (например, «призрак» vs «крушитель» в `three-mazes`)
влияет на сюжетную реакцию мета-персонажей, не меняя саму механику разблокировки прогресса.

### 3.4 Плейсхолдер `{player}` в конфиге

Перед `init` лоадер проходит по собранному конфигу (дефолты мини-игры ⊕ переопределения игры) и заменяет
во **всех строках, на любой глубине**, подстроку `{player}` на имя игрока из профиля (`ГОСТЬ` без имени —
подставляется `Олег`). Мини-игра плейсхолдера не видит и ничего про него не знает: ей приходит готовое имя.

- В админке в любое текстовое поле конфига пишется `{player}` — например `playerName: "{player}"` и
  `tasks[].assignee: "{player}"` в `task-sort`, чтобы «свои» задачи были своими для любого игрока.
- Замена рекурсивная и по всем вхождениям (`replaceAll`), потому что подставлять надо не только в
  верхнеуровневые поля, но и внутрь массивов объектов.
- Совпадение имени игрока с именем NPC в конфиге (игрок назвался «Стас», а `Стас` — чужой исполнитель)
  ничем не разруливается: чужая задача станет своей. Отдельного экранирования не заводили.

### 3.5 Инструктаж перед запуском

Шаги — в `web/player/src/game/tutorials.ts`, ключ `minigameId`. Игра под инструктажем уже смонтирована,
но заморожена (`setPaused`), поэтому оверлей измеряет её живой DOM, а не хранит выверенные координаты:

- Шаг — это `{ target: 'CSS-селектор', text }`. Стрелка садится на найденный элемент, направление и точку
  внутри цели считает `resolveStep`: цель в левой трети экрана — стрелка смотрит влево и подпись уходит
  вправо, в правой — зеркально, посередине — вверх/вниз. Подпись всегда уезжает к центру.
- Проценты рабочей области были бы враньём: игры вписывают поле с полями по краям, и одна и та же точка
  на мониторе и на телефоне попадает в разные места. Было ровно так — три стрелки `task-sort` на широком
  экране втыкались в одну колонку.
- `aspect` — для игр целиком на `<canvas>` (`rescue-catch`, `three-mazes`): холст растянут на всю область,
  а мир рисуется по центру, и без пропорции стрелка целится в холст, а не в картинку. Там же оставлены
  ручные `x`/`y`: это точки мира, отдельных элементов под них нет.
- Подписи после размещения расталкиваются по вертикали и зажимаются внутрь области — двигается **текст**,
  стрелка остаётся на цели. Поэтому новый шаг обычно не требует подгонки координат вообще.
- Раскладка проверена скриптом Playwright на шести играх в пяти пропорциях: подпись не выходит за край и
  не наезжает на соседнюю. Единственное известное касание — `safe-crack` на узком экране, 10 px рамок.

### 3.6 Что не меняется

- Мини-игра не имеет доступа к слоту 1 и слоту 3 нижней панели — они не часть `container`.
- `container`, передаваемый мини-игре — это рабочая область экрана `minigame`, без нижней панели.
  Технически это собственный `position:absolute; inset:0` узел запуска внутри неё, а не сама рабочая
  область: под StrictMode эффект монтируется дважды, и отменённый запуск, дорезолвившись после живого,
  вычищал общий контейнер — экран гас через раз. Свой узел каждый запуск сносит только за собой.
- Изоляция (destroy, отсутствие глобальных side-effect'ов), звук (`config.muted`), тестовый изолированный
  запуск из админки — всё как в базовом контракте, `onProgress` в изолированном режиме — no-op с логом в
  консоль (аналогично заглушкам `onComplete`/`onExit` в тестовом режиме).

## 4. Схема БД

SQLite, миграции последовательные (как `server/src/db/migrate.ts` в GameService). Ниже — логическая схема,
без конкретного SQL DDL (это задача фазы «Каркас»).

### `users`
| Поле | Тип | Описание |
|---|---|---|
| `id` | INTEGER PK | |
| `name` | TEXT UNIQUE COLLATE NOCASE | Регистрация по имени, без пароля |
| `onboarded` | BOOLEAN | Флаг завершения обучалки |
| `created_at` | TIMESTAMP | |

### `game_states`
| Поле | Тип | Описание |
|---|---|---|
| `user_id` | INTEGER PK, FK → users.id | |
| `payload` | JSON | `{ gameResults: { [gameId]: { won, bestScore, attempts, details? } }, onboarded }` |
| `client_updated_at` | TIMESTAMP | Метка клиента — для client-authoritative merge |
| `synced_at` | TIMESTAMP | Метка сервера — последняя синхронизация |

### `games`
| Поле | Тип | Описание |
|---|---|---|
| `id` | TEXT PK (slug-подобный) | Используется в QR-payload |
| `slug` | TEXT | Человекочитаемый идентификатор |
| `title` | TEXT | Название для админки/меты |
| `minigame_id` | TEXT | Ссылка на директорию в `/minigames/` (`rescue-catch`, `task-sort`, …) |
| `config_json` | JSON | Конфиг по `schema.json` игры + `style_dialogue_map` (см. §3.3) |
| `character_id` | INTEGER, FK → characters.id, nullable | Персонаж, связанный с игрой (для пост-диалога «начало игры») |
| `pre_dialogue_id` | INTEGER, FK → dialogues.id, nullable | |
| `post_win_dialogue_id` | INTEGER, FK → dialogues.id, nullable | |
| `post_lose_dialogue_id` | INTEGER, FK → dialogues.id, nullable | |
| `required_game_ids` | JSON (массив id) | Условие разблокировки — все перечисленные должны быть `won` |
| `qr_secret` | TEXT | Секрет для HMAC-подписи QR (см. `docs/qr-flow.md`) |
| `sort_order` | INTEGER | Порядок в списке меты |
| `is_tutorial` | BOOLEAN | `true` для обучалки — не показывается в обычном списке игр меты |

### `characters`
| Поле | Тип | Описание |
|---|---|---|
| `id` | INTEGER PK | |
| `name` | TEXT | |
| `portrait_asset` | TEXT (URL) | |
| `meta_dialogue_id` | INTEGER, FK → dialogues.id, nullable | Диалог по клику на мете |
| `meta_position` | JSON `{x, y}` или enum слотов | Позиция персонажа на мета-сцене |
| `description` | TEXT, по умолчанию `''` | Сводка для игрока: всплывает по наведению на портрет (в диалоге и на мете). Пустая — подсказки нет |

### `dialogues`
| Поле | Тип | Описание |
|---|---|---|
| `id` | INTEGER PK | |
| `title` | TEXT | Для списка в админке |
| `nodes_json` | JSON | Формат узлов — см. `docs/dialogue-system.md` |

### `assets`, `settings`
Как в GameService без изменений: `assets` — метаданные загруженных файлов (upload/serve),
`settings` — key-value для глобальных настроек (звуки интерфейса и т.п.).

## 5. Блокировки

- У каждой игры — `required_game_ids: string[]`. Игра доступна для скана, если для **каждого** id из списка
  `gameResults[id].won === true` в текущем прогрессе пользователя.
- Проверка выполняется на сервере при `POST /api/qr/verify` (клиент не может обойти проверку, подделав
  локальный стейт) — детали протокола в `docs/qr-flow.md`.
- Отражение в мете: закрытая игра рисуется силуэтом с иконкой замка (контурная, по STYLE.md), без доступа к
  QR-подсказке; сам скан её QR-кода (если физически показать код раньше времени) всё равно получит отказ от
  сервера — фронтовое затемнение не единственная защита.
- Пустой `required_game_ids` (`[]`) — игра открыта всегда (обычно так у первых игр цепочки).

## 6. Прогресс и синхронизация

- Клиент-авторитетный sync — копия механизма GameService (`resolveSync` в `server/src/repos/sync.ts`,
  `state/localState.ts` + `state/sync.ts` на клиенте): локальный стейт — источник истины на устройстве,
  сервер мержит по `client_updated_at`, тумбстоуны позволяют админке форс-сбросить прогресс игрока
  (аналог `UserProgressModal` в GameService), не боясь, что клиент «оживит» сброшенное значение
  устаревшим локальным кэшем.
- Единица прогресса — `gameResults[gameId] = { won, bestScore, attempts, details? }`. `attempts`
  инкрементируется при каждом `onComplete` (успешном или нет), `bestScore` — максимум по всем попыткам,
  `won` — булев OR по всем попыткам (однажды пройдено — навсегда пройдено, не сбрасывается повторным
  проигрышем).
- Мета-прогресс-бар — `count(won=true среди игр, is_tutorial=false) / count(всего игр, is_tutorial=false)`.
- «Прогресс в других играх» как условие разблокировки — только `won`, не `bestScore` и не `attempts`
  (допущение из плана, зафиксированное с пользователем).

## 7. Админка — вкладки (обзор)

Подробности форм — в соответствующих доках (`docs/dialogue-system.md` для вкладки «Диалоги»,
`docs/qr-flow.md` для генерации QR на вкладке «Игры»). Здесь — только состав:

1. **Игры** — CRUD игры: выбор мини-игры (тип), конфиг через SchemaForm по `schema.json` выбранной игры,
   персонаж, 3 диалога (pre/post-win/post-lose) + `style_dialogue_map`, требования разблокировки
   (мультиселект существующих игр), кнопка генерации/печати QR.
2. **Персонажи** — CRUD: имя, портрет (asset), мета-диалог, позиция на мета-экране.
3. **Диалоги** — редактор узлов + импорт/экспорт JSON (см. `docs/dialogue-system.md`).
4. **Игроки** — список пользователей, их прогресс (`gameResults` + `details`), сброс/форс-завершение
   отдельной игры или всего прогресса.
5. **Ассеты** — загрузка/список файлов, как в GameService (`server/src/routes/assets.ts`).
6. **Настройки** — глобальные звуки интерфейса и прочие KV-настройки платформы.
7. **Тест-запуск мини-игры** — изолированный прогон любой игры с текущим конфигом, без прохождения меты
   (аналог `MinigamesSection` в GameService); также используется как превью при отладке `schema.json`.
