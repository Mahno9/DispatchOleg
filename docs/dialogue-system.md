# Диалоговая система

Собственная реализация визуальной новеллы: узлы диалога хранятся в JSON (`dialogues.nodes_json`),
рендерятся компонентом `DialogueScene`, редактируются в админке (форма по узлам + импорт/экспорт файла).
i18n не нужен — весь текст на русском (допущение плана).

Точки использования диалога: pre/post-win/post-lose у мини-игры (`games.*_dialogue_id`, см.
`docs/platform.md` §2.4, §3.3) и мета-диалог персонажа (`characters.meta_dialogue_id`, кликабелен на
мета-сцене).

---

## 1. Формат узла (JSON)

Хранится целиком в одном поле `dialogues.nodes_json`:

```json
{
  "start": "n1",
  "nodes": {
    "n1": {
      "speaker": "oleg",
      "side": "left",
      "text": "Диспетчерская, слушаю. Что у вас?",
      "next": "n2",
      "choices": null
    },
    "n2": {
      "speaker": "char_vera",
      "side": "right",
      "text": "Тут кот на тополе третий час сидит. Опять.",
      "next": null,
      "choices": [
        { "text": "Присылаю бригаду.", "next": "n3" },
        { "text": "Сам снимет, не маленький.", "next": "n4" }
      ]
    }
  }
}
```

### 1.1 Поля документа

| Поле | Тип | Описание |
|---|---|---|
| `start` | string | id узла, с которого начинается показ |
| `nodes` | `Record<string, Node>` | Все узлы диалога, ключ — произвольный id (уникальный внутри диалога) |

### 1.2 Поля узла

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `speaker` | `"oleg" \| <characterId>` | да | Кто говорит. `"oleg"` — специальный идентификатор игрока-диспетчера, не требует записи в `characters` |
| `side` | `"left" \| "right"` | да | Портрет говорящего рисуется с этой стороны рабочей области |
| `text` | string | да | Реплика. Показывается typewriter-эффектом |
| `next` | `string \| null` | да | Следующий узел. `null` — конец диалога (только если `choices` тоже отсутствует/пусто) |
| `choices` | `Choice[] \| null` | нет | Если задано — вместо автоперехода по `next` показываются карточки вариантов; `next` в этом случае игнорируется (взаимоисключение — см. валидацию §4) |

### 1.3 Поля варианта (`Choice`)

| Поле | Тип | Описание |
|---|---|---|
| `text` | string | Текст кнопки-карточки варианта ответа |
| `next` | string | id узла, куда ведёт выбор (обязателен — вариант без продолжения не имеет смысла) |

### 1.4 Терминальный узел

Узел без `choices` и с `next: null` — последний. После его показа (по клику) диалог завершается, платформа
переходит к следующему экрану по стейт-машине (`docs/platform.md` §2).

---

## 2. Рендерер (`web/player/src/dialogue/DialogueScene.tsx`)

- Портреты говорящих персонажей отображаются по сторонам, заданным полем `side`. Портрет **говорящего**
  подсвечен (яркая рамка/лёгкое бирюзовое свечение по STYLE.md), портрет **молчащего** собеседника —
  затемнён (если он есть в кадре одновременно, например при попеременных репликах в одном диалоге).
- Имя персонажа выводится под портретом (узкий прописной шрифт, как заголовки по STYLE.md).
- Текст реплики рендерится в **центральном слоте нижней панели** (см. `docs/platform.md` §1.2) с
  typewriter-эффектом (посимвольное появление). Клик по области — либо доигрывает текст мгновенно (если
  анимация ещё идёт), либо, если текст уже полностью показан, переходит к `next`/показывает `choices`.
- Варианты ответа (`choices`) — кнопки-карточки в рабочей области (не в нижней панели — там нет места на
  несколько карточек), в стиле угловатых панелей STYLE.md с рамкой и hover-подсветкой.
- Портрет Олега (`speaker: "oleg"`) — либо статичный аватар-плейсхолдер, либо (если камера уже включена)
  живой кадр с `CameraPanel` в качестве портрета диспетчера — конкретный выбор фиксируется в фазе
  реализации меты, оба варианта укладываются в контракт рендерера (источник картинки для стороны
  `"oleg"` — деталь конфигурации сцены, не формата диалога).

### 2.1 Жизненный цикл диалоговой сцены

1. Монтируется с `dialogueId`, грузит узел `start`.
2. По клику проигрывает/долистывает текст текущего узла.
3. При наличии `choices` — ждёт клика по варианту, затем переходит к его `next`.
4. При отсутствии `choices` и наличии `next` — переходит к нему по клику.
5. При `next: null` и отсутствии `choices` — по клику завершает сцену, вызывая колбэк завершения диалога
   (платформенный, не путать с контрактом мини-игр) — управление возвращается в стейт-машину экранов.

## 3. Редактор в админке (вкладка «Диалоги»)

Список диалогов (заголовок = `dialogues.title`) + форма редактирования выбранного:

- **Список узлов** — таблица/список id узлов диалога, кнопка «+ узел», кнопка удаления узла (с
  предупреждением, если на него ссылаются другие узлы — см. валидацию).
- **Форма узла**: выбор `speaker` (селект: «Олег» + список `characters`), `side` (переключатель
  лево/право), textarea `text`, выбор `next` (селект существующих узлов диалога + «— конец —» = `null`),
  редактор списка `choices` (текст + переход, добавление/удаление строк).
- **Выбор стартового узла** — отдельный селект `start` над списком узлов.
- Переключение режима «обычный переход» / «варианты ответа» для узла — взаимоисключающее (см. §1.2):
  включение `choices` скрывает поле `next` формы и наоборот.

### 3.1 Импорт/экспорт JSON

- Кнопка «Экспорт» — скачивает текущий `nodes_json` файлом (`<title>.json`).
- Кнопка «Импорт» — файловый инпут, загружает JSON, **валидирует** (см. §4) перед применением; при ошибке
  валидации — список проблем, импорт не применяется (не сохраняется частично).
- Импорт полностью заменяет `nodes_json` диалога (не мержит с существующими узлами).

## 4. Валидация

Выполняется и при сохранении формы, и при импорте файла:

1. **Наличие `start`** — узел с id из `start` должен существовать в `nodes`.
2. **Отсутствие битых ссылок** — каждый `next` (в узле и в каждом `choices[].next`) должен указывать на
   существующий id в `nodes`, либо быть `null` (только для `next` узла, не для `choices[].next`, который
   обязателен).
3. **Достижимость узлов** — обход графа от `start` по всем `next`/`choices[].next`; узлы, недостижимые из
   `start`, — предупреждение (не блокирует сохранение, но подсвечивается в списке узлов как «висячий»,
   т.к. это, вероятно, ошибка автора, а не намеренный дизайн).
4. **Отсутствие циклов не требуется проверять как ошибку** — циклы в диалоге допустимы (например,
   «рассказать другую байку» → назад к тому же узлу с выбором), ограничивается только логикой автора.
5. **Взаимоисключение `next`/`choices`** — узел с непустым `choices` не должен полагаться на `next`
   (поле может присутствовать, но игнорируется рендерером; валидатор может предупреждать, если оба
   заданы одновременно, как источник путаницы).
6. **Пустой диалог** (`nodes: {}`) — допустим только как «диалог не задан»; в схеме это скорее
   представлено отсутствием `*_dialogue_id` (см. `docs/platform.md` §2.4), а не диалогом с пустыми узлами.

---

## 5. Привязка диалогов

| Место привязки | Поле |
|---|---|
| Перед мини-игрой | `games.pre_dialogue_id` |
| После победы в мини-игре | `games.post_win_dialogue_id` (может быть переопределён `style_dialogue_map` по `styleTag`, см. `docs/platform.md` §3.3) |
| После поражения в мини-игре | `games.post_lose_dialogue_id` |
| Клик по персонажу на мете | `characters.meta_dialogue_id` |

Все четыре поля — `nullable`: отсутствие диалога означает, что соответствующий экран пропускается (для
pre/post) или клик по персонажу ничего не делает (для меты — впрочем, для персонажа с назначенной ролью
в мете отсутствие `meta_dialogue_id` не имеет практического смысла, обычно всегда задан).
