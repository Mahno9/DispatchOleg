# QR-поток: генерация, печать, сканирование, верификация

Физические QR-коды — единственный способ запустить мини-игру из меты (кроме тестового изолированного
запуска из админки, см. `docs/platform.md` §7 п.7). Документ описывает весь путь: от генерации кода в
админке до открытия игры на терминале.

---

## 1. Формат содержимого QR

```
dispatch:<gameId>:<hmac>
```

- `dispatch:` — фиксированный префикс, отличает коды платформы от случайных сторонних QR (защита от
  «шумовых» декодов и явная маркировка при отладке).
- `<gameId>` — значение `games.id` (строковый slug-подобный идентификатор).
- `<hmac>` — подпись `HMAC-SHA256(gameId, games.qr_secret)` (или единый серверный секрет — деталь
  реализации; на уровне контракта важно, что подпись **проверяема на сервере** и не подделываема без
  секрета), в виде hex/base64url-строки.

Формат подписи выбран по аналогии с admin-auth HMAC-cookie GameService (`server/src/plugins/auth.ts`) —
тот же примитив, тот же способ проверки на сервере, отдельного крипто-модуля заводить не требуется.

Почему подпись, а не просто `gameId` открытым текстом: без неё игрок мог бы написать/сгенерировать
произвольный QR с любым `gameId` мимо админки (например, обойти печать) — HMAC гарантирует, что код
физически выпущен админкой.

---

## 2. Генерация в админке

На вкладке «Игры» (см. `docs/platform.md` §7 п.1), в карточке редактирования игры — кнопка **«Сгенерировать
QR»**:

1. Сервер (или клиент админки, если секрет доступен только там — реализационная деталь) считает
   `hmac = HMAC-SHA256(gameId, secret)` и формирует строку `dispatch:<gameId>:<hmac>`.
2. Строка кодируется в QR-изображение (`qrcode` npm-пакет либо canvas-генерация — берётся стандартная
   готовая библиотека, свой QR-энкодер не пишется).
3. Результат — превью QR в карточке игры + кнопка **«Печать»**, открывающая отдельную print-страницу:
   крупный QR + подпись (название игры человекочитаемо, для сортировки распечаток на столе оператора),
   с CSS `@media print` (без CRT-оверлея и тёмной темы — печать должна экономить тонер и быть читаемой).
4. Секрет (`games.qr_secret`) генерируется один раз при создании игры (случайная строка), не меняется при
   правках конфигурации — иначе уже отпечатанные коды перестанут проходить верификацию.

Повторная генерация (кнопка нажата ещё раз) даёт тот же QR, пока `qr_secret` не менялся — детерминированная
функция от `(gameId, secret)`, идемпотентна.

## 3. Сканер (`QrScanner`, общий компонент)

Используется на экране `qr-scan` (см. `docs/platform.md` §2.3) и в обучалке (`docs/minigames/01-onboarding.md`).

### 3.1 API

```ts
function start(): { stream: MediaStream, onDecode: (cb: (text: string) => void) => void, stop: () => void }
```

(сигнатура ориентировочная — суть контракта: единая точка получения `MediaStream` + подписки на декод +
явная остановка).

### 3.2 Пайплайн декодирования

1. `getUserMedia({ video: true })` — запрос доступа к камере. Один запрос permission за сессию (см. §3.3).
2. Основной путь — нативный `BarcodeDetector('qr_code')` (Chrome/Chromium), если поддерживается
   (`'BarcodeDetector' in window`) — распознавание кадров `<video>` через `requestVideoFrameCallback`/
   `requestAnimationFrame`.
3. Фолбэк — `jsQR`, подключаемый **динамическим `import()`** (не в основной бандл, т.к. нужен только
   браузерам без `BarcodeDetector`, например Firefox/Safari на момент написания) — снимок кадра в offscreen
   `<canvas>`, передача `ImageData` в `jsQR`.
4. При успешном декоде — вызов подписчика `onDecode(text)` с сырой строкой из QR (проверка формата и HMAC —
   на сервере, не в сканере; сканер декодирует и передаёт как есть).

### 3.3 Переиспользование `MediaStream`

Стрим, полученный сканером, — тот же самый, что показывается в слоте 1 нижней панели (`CameraPanel`, см.
`docs/platform.md` §1.1). Оба потребителя работают через singleton-модуль `camera.ts`:
- Модуль хранит единственный активный `MediaStream` и счётчик подписчиков/иначе кэш промиса
  `getUserMedia`.
- `QrScanner` не запрашивает permission повторно, если стрим уже получен обучалкой (`camera.ts` уже
  проинициализирован) — переиспользует существующий трек.
- Результат: **один** permission-prompt браузера за всю сессию использования терминала, а не на каждый
  вход в `qr-scan`.
- При остановке сканера (`stop()`) сам трек камеры не останавливается — им ещё пользуется `CameraPanel`;
  останавливается только цикл декодирования (`requestAnimationFrame`/`requestVideoFrameCallback`).

## 4. Верификация — `POST /api/qr/verify`

### 4.1 Запрос

```json
{ "code": "dispatch:<gameId>:<hmac>" }
```

### 4.2 Проверки на сервере (по порядку, до первого отказа)

1. **Формат** — строка соответствует `dispatch:<gameId>:<hmac>`, иначе отказ «код не опознан».
2. **Существование игры** — `games.id = gameId` найден, иначе отказ «код не опознан» (не различать
   «неверная подпись» и «нет такой игры» в ответе пользователю — не давать подсказок для подбора).
3. **Подпись** — пересчитать `HMAC-SHA256(gameId, games.qr_secret)`, сравнить константным по времени
   способом с `<hmac>` из запроса; несовпадение → отказ «код не опознан».
4. **Прогресс/разблокировка** — для каждого `id` из `games.required_game_ids` проверить
   `gameResults[id].won === true` в состоянии пользователя (`game_states.payload`, см.
   `docs/platform.md` §5–6); если хоть один не пройден → отказ «доступ запрещён: требуется прогресс в …»
   с перечислением недостающих игр по названию.

### 4.3 Ответ

```json
// успех
{ "ok": true, "gameId": "rescue-catch" }

// отказ
{ "ok": false, "reason": "not_found" | "invalid_signature" | "locked", "missingGameIds"?: string[] }
```

Клиент на успехе переходит к `dialogue(pre)`/`minigame` (см. `docs/platform.md` §2.3), на отказе — к экрану
причины отказа (см. §5).

## 5. Экраны отказа

Показываются поверх/вместо сканера (сканер не продолжает работать во время экрана отказа — иначе
повторный кадр того же кода тут же вызовет повторный запрос):

| Причина | Текст |
|---|---|
| `not_found` / `invalid_signature` | «КОД НЕ ОПОЗНАН» — единый текст для обоих случаев (см. §4.2 п.2) |
| `locked` | «ДОСТУП ЗАПРЕЩЁН: требуется прогресс в …» + список недостающих игр по названию (`missingGameIds` → `games.title`) |

Кнопка «ОК»/«Назад» возвращает в meta. Повторный скан требует нового захода в `qr-scan` со стороны кнопки
START — сканер не перезапускается автоматически после отказа (см. `docs/platform.md` §2.3).

### 5.1 Дебаунс повторных декодов

Пока пользователь держит камеру наведённой на один и тот же (уже отклонённый или уже принятый) QR, декодер
продолжает регулярно возвращать тот же текст. Компонент дебаунсит одинаковый декод (не шлёт повторный
`POST /api/qr/verify` для того же `code`, пока пользователь не уберёт код из кадра или не пройдёт заданный
интервал) — иначе это лишняя нагрузка на сеть/сервер и мерцающий UI при дрожании кадра.

## 6. Использование в обучалке

Экран сканирования QR в `01-onboarding` использует тот же `QrScanner`, но с двумя отличиями:
- Успешный скан **любого** валидного (по подписи) QR — не обязательно конкретной «стартовой» игры — либо
  строго кода, привязанного к обучающей игре (`is_tutorial=true`), решает конкретика сценария обучалки
  (см. `docs/minigames/01-onboarding.md`); в любом случае верификация идёт через тот же
  `/api/qr/verify`, разблокировки на этом этапе ещё нет смысла проверять отдельно.
- Ошибки декодирования камеры (`NotFoundError`/`NotAllowedError`/`NotReadableError` из `getUserMedia`) —
  зона ответственности обучалки, не общего сканера (общий `QrScanner` их прокидывает наверх, тексты
  ошибок настраиваются в `schema.json` обучалки).
