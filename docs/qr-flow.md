# QR-поток: генерация, печать, сканирование, верификация

Физические QR-коды — единственный способ запустить мини-игру из меты (кроме тестового изолированного
запуска из админки, см. `docs/platform.md` §7 п.7). Документ описывает весь путь: от генерации кода в
админке до открытия игры на терминале.

---

## 1. Формат содержимого QR

```
dispatch:<gameId>:<hmac>
```

Регулярка приёма — `/^dispatch:(\d+):([0-9a-f]+)$/` (`server/src/routes/qr.ts`).

- `dispatch:` — фиксированный префикс, отличает коды платформы от случайных сторонних QR (защита от
  «шумовых» декодов и явная маркировка при отладке).
- `<gameId>` — значение `games.id`, **целое число** (INTEGER PK, см. `docs/platform.md` §4).
- `<hmac>` — `HMAC-SHA256(String(gameId), QR_SECRET)`, hex, **первые 16 символов** (64 бита — для
  наклейки на стене более чем достаточно).

Секрет **один на весь сервер** — переменная окружения `QR_SECRET`, по умолчанию равная
`COOKIE_SECRET` (`server/src/config.ts`). Пер-игрового секрета нет: колонки `games.qr_secret` в схеме
не существует. Смена `QR_SECRET` инвалидирует все напечатанные коды разом.

Формат подписи выбран по аналогии с admin-auth HMAC-cookie (`server/src/plugins/auth.ts`) — тот же
примитив, тот же способ проверки на сервере, отдельного крипто-модуля заводить не требуется.

Почему подпись, а не просто `gameId` открытым текстом: без неё игрок мог бы написать/сгенерировать
произвольный QR с любым `gameId` мимо админки (например, обойти печать) — HMAC гарантирует, что код
физически выпущен админкой.

## 2. Генерация в админке

На вкладке «Игры» (см. `docs/platform.md` §7 п.1) у каждой строки есть кнопка **«QR-код»** — она
открывает модалку с превью. Картинку рисует сервер:

```
GET /api/admin/games/:id/qr.svg        (только под админ-сессией)
```

Хендлер (`server/src/routes/qr.ts`) считает `qrPayload(gameId)` и кодирует строку пакетом `qrcode`
(`QRCode.toString`, `type: 'svg'`, `margin: 1`, `width: 512`); свой QR-энкодер не пишется. Нет такой
игры — 404.

Кнопка печати внутри модалки открывает отдельное окно с одним QR крупным планом и сразу вызывает
`window.print()` (браузер может заблокировать попап — тогда попапы для admin-адреса надо разрешить).
Тот же SVG можно просто открыть по ссылке и распечатать любым другим способом.

Генерация идемпотентна: `dispatch:<gameId>:<hmac>` — детерминированная функция от `(gameId,
QR_SECRET)`, повторный запрос даёт тот же код. Хранить его негде и незачем — в БД он не лежит.

## 3. Сканер (`QrScanner`, общий компонент)

Используется на экране `qr-scan` (см. `docs/platform.md` §2.3) и в обучалке (`docs/minigames/01-onboarding.md`).

### 3.1 API

```ts
function start(): { stream: MediaStream, onDecode: (cb: (text: string) => void) => void, stop: () => void }
```

(сигнатура ориентировочная — суть контракта: единая точка получения `MediaStream` + подписки на декод +
явная остановка).

### 3.2 Пайплайн декодирования

Часть носителей напечатана в **инвертированной полярности**: светлые модули на тёмно-бирюзовом фоне,
без светлой quiet zone. Штатные декодеры такие коды не находят (finder-паттерн 1:1:3:1:1 читается
наоборот), поэтому сканер прогоняет каждый кадр через конвейер вариантов препроцессинга
(`web/player/src/camera/qrPipeline.ts`), останавливаясь на первом успехе:

1. Кадр даунскейлится до ~640 px по длинной стороне, grayscale по luma.
2. Варианты, от дешёвых к дорогим: сырой кадр → сырой инвертированный → Otsu-бинаризация →
   Otsu + инверсия → растяжение контраста (перцентили 2/98) + Otsu + инверсия. Ко всем
   бинаризованным вариантам добавляется **синтетическая белая quiet zone** (≥ 4 модулей) — у
   напечатанных кодов светлых полей нет, без рамки детектор не находит границы кода.
3. Индекс сработавшего варианта кешируется и пробуется первым на следующем кадре.
4. Инверсия выполняется до бинаризации своими руками: `inversionAttempts` jsQR инвертирует уже после
   собственной бинаризации, чего на низкоконтрастной цветной печати не хватает.

Организация выполнения:

1. `getUserMedia` — запрос доступа к камере. Один запрос permission за сессию (см. §3.3).
2. Нативный `BarcodeDetector('qr_code')` (Chrome/Chromium) — только быстрый путь для обычных кодов;
   jsQR-конвейер всегда остаётся за ним (в Safari `BarcodeDetector` нет, инверсию он не читает).
3. Пиксельная обработка — в Web Worker (`qrScanWorker.ts`) с `OffscreenCanvas`; на слабых телефонах
   конвейер в главном потоке роняет fps превью. Без поддержки воркера — инлайн-фолбэк. `jsQR`
   подключается динамическим `import()` и в основной бандл не попадает.
4. Попытки декодирования троттлятся до ~10/с (не каждый rAF-тик).
5. При успешном декоде — вызов подписчика `onDecode(text)` с сырой строкой из QR (проверка формата и
   HMAC — на сервере, не в сканере); наружу также отдаётся сработавший вариант (`variant`) — для
   отладки и подсказки оператору, что код инвертированный.

**Фолбэка «декодировать картинку без камеры» нет.** Модуль `qrImage.ts` (загрузка файла,
drag-and-drop, вставка из буфера) удалён и не вернётся: в зале у игрока камера есть по условию
задачи, а форма загрузки файла на терминале — лишний путь, который надо чинить и тестировать.
Реальные способы пройти без сканирования два, оба служебные:

- **рычаг «Пропустить сканирование»** в обучалке (`allowSkipScan` в конфиге обучающей игры) —
  шаг скана засчитывается кнопкой; в тест-режиме `?test=onboarding` и при `NO_QR=1` включается
  принудительно;
- **режим `NO_QR=1`** (см. §6) — экрана скана нет вообще, операцию выдаёт жребий.

Если камера отказала или пропала посреди скана, экран `qr-scan` показывает панель с причиной и
кнопкой **«ПЕРЕПОДКЛЮЧИТЬ»** (`scanErrorText` в `screens/QrScanScreen.tsx`), а не предлагает
загрузить файл.

### 3.3 Переиспользование `MediaStream`

Стрим, полученный сканером, — тот же самый, что показывается в слоте 1 нижней панели (`CameraPanel`, см.
`docs/platform.md` §1.1). Оба потребителя работают через singleton-модуль `camera.ts`:
- Модуль хранит единственный активный `MediaStream` и счётчик подписчиков/иначе кэш промиса
  `getUserMedia`.
- `QrScanner` не запрашивает permission повторно, если стрим уже получен обучалкой (`camera.ts` уже
  проинициализирован) — переиспользует существующий трек.
- Результат: **один** permission-prompt браузера за всю сессию использования терминала, а не на каждый
  вход в `qr-scan`.
- При остановке сканера (`stop()`) сам трек камеры не останавливается — им ещё пользуется `CameraPanel`;
  останавливается только цикл декодирования (`requestAnimationFrame`/`requestVideoFrameCallback`).

## 4. Верификация — `POST /api/qr/verify`

### 4.1 Запрос

```json
{ "payload": "dispatch:<gameId>:<hmac>", "userId": "<users.id>" }
```

Оба поля обязательны (схема тела в маршруте). `userId` нужен, чтобы проверить разблокировку по
прогрессу именно этого игрока.

### 4.2 Проверки на сервере (по порядку, до первого отказа)

1. **Формат и подпись** — `parseQrPayload`: строка матчится регуляркой, `hmac` пересчитывается и
   сравнивается константным по времени способом (`timingSafeEqual`). Любая беда здесь — один и тот же
   отказ `bad-signature`: «неверная подпись» и «мусор вместо кода» для клиента неразличимы.
2. **Существование игры** — `games.id = gameId` найден, иначе `not-found`.
3. **Прогресс/разблокировка** — для каждого `id` из `required_game_ids_json` проверяется
   `gameResults[id].won === true` в состоянии пользователя (`game_states.payload`, см.
   `docs/platform.md` §5–6); если хоть один не пройден → `locked` со списком названий недостающих игр.

### 4.3 Ответ

```json
// успех
{ "ok": true, "game": { "id": 42, "title": "Восточный мост", "minigameId": "rescue-catch", "isTutorial": false } }

// отказ
{ "ok": false, "reason": "bad-signature" | "not-found" }
{ "ok": false, "reason": "locked", "requiredTitles": ["Разбор ночной смены"] }
```

`requiredTitles` — сразу человекочитаемые названия (`games.title`, для пропавшей игры — `#<id>`), а не
id: клиенту всё равно оставалось бы только показать их игроку. `isTutorial` в успешном ответе нужен
плееру, чтобы отличить коробочный код обучалки от боевого (см. §5 и §6).

Клиент на успехе переходит к `launch` → `dialogue(pre)`/`minigame` (см. `docs/platform.md` §2.3),
на отказе — к экрану причины (см. §5).

## 5. Экраны отказа

Разбор ответа — `verifyVerdict` в `screens/QrScanScreen.tsx`. Отказы делятся на два класса.

**Вспышка, скан продолжается** — короткое сообщение поверх кадра, сканер не останавливается:

| Случай | Текст |
|---|---|
| строка не начинается с `dispatch:` | `scanFailText` («КОД НЕ ОПОЗНАН») — до сервера запрос даже не идёт |
| `bad-signature` / `not-found` | тот же `scanFailText`: подделку и опечатку игроку не различают |
| `ok`, но `game.isTutorial` | «ОБУЧЕНИЕ УЖЕ ПРОЙДЕНО» — у системной игры нет бандла, запуск обернулся бы «Сбоем запуска» |
| сеть не ответила | `netFailText` |

**Панель, сканер встаёт** — иначе повторный кадр того же кода тут же вызовет повторный запрос:

| Случай | Панель |
|---|---|
| `locked` | «Доступ запрещён» + «Требуется прогресс в: …» из `requiredTitles`, кнопка «ОК» → meta |
| камера отказала или пропала (`SignalLost`) | причина отказа + кнопка «ПЕРЕПОДКЛЮЧИТЬ», которая просит стрим заново |

После `locked` повторный скан требует нового захода в `qr-scan` со стороны кнопки START — сканер
автоматически не перезапускается (см. `docs/platform.md` §2.3). Панель камеры, в отличие от неё,
снимается сама, как только стрим ожил.

### 5.1 Дебаунс повторных декодов

Пока пользователь держит камеру наведённой на один и тот же (уже отклонённый или уже принятый) QR, декодер
продолжает регулярно возвращать тот же текст. Компонент дебаунсит одинаковый декод (не шлёт повторный
`POST /api/qr/verify` для того же `code`, пока пользователь не уберёт код из кадра или не пройдёт заданный
интервал) — иначе это лишняя нагрузка на сеть/сервер и мерцающий UI при дрожании кадра.

## 6. Использование в обучалке

Экран сканирования QR в `01-onboarding` использует тот же сканер, но с тремя отличиями:
- Ворота открывает **только код обучающей игры**: `res.ok && res.game.isTutorial`. Валидный код любой
  другой игры даёт ту же вспышку `scanFailText`, что и чужой QR, — иначе им можно было бы перепрыгнуть
  регистрацию и настройку камеры.
- Ошибки декодирования камеры (`NotFoundError`/`NotAllowedError`/`NotReadableError` из `getUserMedia`) —
  зона ответственности обучалки, не общего сканера (тексты ошибок настраиваются в `schema.json`
  обучалки, `server/system-minigames/onboarding/`).
- Есть аварийный рычаг **«Пропустить сканирование»** (`allowSkipScan` в конфиге обучалки): шаг
  засчитывается кнопкой. В `?test=onboarding` и при `NO_QR=1` он включается принудительно.

Отдельно от `?test=…` (см. «Тестовый режим плеера» в корневом README) — режим `NO_QR=1` (переменная
сервера, см. README «Переменные окружения»): плеер вообще не показывает сканер, кнопка START сама берёт
случайную доступную мини-игру, онбординг проходится без сканирования QR. Сервер только отдаёт флаг
(`GET /api/settings` → `no_qr`); сама логика переключения — на стороне плеера.
